# 技术章节专项规则

本文档覆盖现行的技术方法论型(沉淀 + 深水区合并)。它把原技术方法论型的框架、机制、量化推演和落地路径,与原深水区风格的工程现场、决策链和工具沉淀放在同一条路由里。原架构原理深度型的量化和边界工具继续保留,技术思辨型的独立规则见 `tech_polemic_rules.md`。

技术章节的核心原则:**有事实托住的判断 + 能复查的机制 + 能迁移的动作,但即使再硬的题材也不能写得太冷太晦涩。**

可读性是顶层约束,凌驾于专业度与文学性之上。

## 二、真正干货的五个落点

技术章节的"干货"不是"信息量大",是"读完之后读者获得了一个原本没有的判断框架"。具体落点:

### 1. 反直觉的核心判断

每篇必须有一个能改变读者判断的核心判断。它可以指出好东西的隐藏成本、常见问题背后的机制,或最佳实践的适用边界。

如果一篇文章的核心结论是行业共识,这篇文章就不该写。或者要重写到能挑战共识的角度上。

### 2. 机制 > 现象

不停在"会发生什么",必须解释"为什么会这样"。这是技术文章与新闻报道的本质区别。

### 3. 量化 > 形容

延迟说毫秒,资源说 MB 和核数,频次说每周几次,故障域大小说集群规模。

```
× 这种设计会显著影响性能。
✓ 这种设计在 5 跳调用链上引入 5-20ms 的额外延迟,占 P99 预算的 10%-40%。
```

### 4. 拆解 > 结论

把一个判断拆成 2-4 个可独立验证的子论点。读者可以单独反驳其中任何一个,但每个子论点本身都站得住。

```
× Service Mesh 在中等规模团队里不划算。
✓ Service Mesh 在中等规模团队里大概率负收益,理由有三层:
   (1) 性能成本:每次调用增加两次本地跳转,占延迟预算 10%-40%
   (2) 认知成本:排查路径从 3 层扩展到 6-7 层,集中压在 1-2 名资深工程师身上
   (3) 故障域成本:多个隔离故障域合并为共享故障域,无独立 SRE 团队消化
```

### 5. 承认边界

讲清楚这个判断在什么规模、什么条件下成立,在什么情况下不成立。**没有边界条件的技术判断,几乎都是错的。**

```
× 单体架构比微服务架构更适合中小团队。
✓ 在团队规模 < 15 人、单一业务线、不需要多语言栈的情况下,单体架构的总体维护成本
   通常低于微服务架构。这条结论在团队跨越 20 人或同时维护 3 条以上业务线时,会反转。
```

## 三、专业但不晦涩的六个具体落点

第 9 条反馈("即使技术部分也不能写得太冷太晦涩")的落点。

### 1. 每节开头一句白话点题

进入术语化论证之前,先用一句白话说清楚"这一节要讲什么、为什么值得讲"。

```
× ## 二、衰退机制
   半自动化卡点的衰退路径遵循一个相对稳定的统计模式……

✓ ## 二、它为什么会衰退
   半自动化卡点的衰退路径相当稳定。我在不同公司、不同团队的至少 6 个样本里,
   观察到的时间分布几乎一致……
```

### 2. 关键术语第一次出现配 15 字以内白话翻译

```
× Service Mesh 的标准架构由控制平面和数据平面组成……
✓ Service Mesh 的标准架构由控制平面和数据平面组成。说人话就是,业务容器旁边
   再起一个小容器,所有进出流量都先经过这个小容器,治理逻辑全部交给它。
```

### 3. 每节末尾一句无术语的喘息句

让读者在硬术语段之后回到地面。

```
[节中:大量延迟数字、资源消耗数据、扩张机制分析]

对面向 C 端的同步链路,这笔预算消耗很难忽略。
```

### 4. 术语密集段落单句不超过 35 字

每出现一个新术语,前后必须有一句非术语句缓冲。不能两句术语句连排。

### 5. 每段最多引入 2 个新术语

超过就拆段。这是认知带宽的物理限制——人脑在阅读时无法同时消化 3 个以上新概念。

### 6. 通读折返检查

写完之后,通读全文。如果任何一段读到一半需要折返才能读懂,这段就要重写。**这是 L2 自检的硬指标。**

### 7. 场景化生动性

生动感不靠抒情,靠读者能看见一个动作,并看见动作如何改变判断。技术方法论型按以下顺序推进:

```
可见现场 → 动作或产物 → 阻力或转折 → 机制解释 → 取舍或下一步
```

- **一条主场景贯穿**——选一条能承载核心判断的工程现场作为主线,其他案例只保留能改变判断或解释机制的细节。

- **场景卡五项**——时间或阶段、参与者或系统、可见动作或产物、阻力或转折、结果或代价。主场景至少写出三项,资料不足时删掉场景或标明待核实,不补造细节。

- **每段至少落一项**——抽象判断前后,尽量放一个可指认的日志、文档、命令、数据、对话或操作。连续两段纯抽象解释后,必须回到具体材料。

- **对话只写决策线**——只保留真正改变判断的问答。没有原话就用转述,不补造对话。

- **动词优先**——写「打开评审文档」「拉到第三页」「重新跑测试」「查看 P99」,少写「深入分析」「充分认识」「积极推进」。

- **隐喻按需使用**——一个主要章节最多保留一个能缩短解释的工程隐喻,没有合适隐喻就不用。

冷读时逐段问一句,「读者能否在脑中截出一帧画面」。不能就补事实或删段,不要用形容词和副词救场。

## 四、反直觉判断生成法(三个提问模板)

落笔之前如果作者没有现成的独特视角,用以下三个提问模板帮助挖掘。这三个提问对应 SKILL.md 写作执行流程的第二步「独特视角询问」。

### 提问 1:好东西的阴面

> "大家都觉得 X 是好的,有没有什么情况下它其实是坏的?"

例子:

- X = 微服务架构 → 在团队 < 15 人时,微服务的协调成本可能超过它带来的解耦收益

- X = AI Code Review → 在代码风格高度统一的小团队里,AI Review 反而会引入噪声

- X = 流水线人工卡点 → 看起来是"安全兜底",实际是 6 周后就会失效的设计

### 提问 2:问题背后的问题

> "大家都在抱怨 Y 是问题,有没有可能 Y 其实是某个更深问题的症状,而非问题本身?"

例子:

- Y = 流水线越来越慢 → 先查流程治理结构,再查单点性能

- Y = 测试不稳定 → 真问题可能是测试设计依赖了不该依赖的全局状态

- Y = 团队抗拒新工具 → 真问题可能是没人愿意承担"试错失败"的政治成本

### 提问 3:最佳实践的反例

> "行业最佳实践 Z 在什么规模 / 什么条件下其实是负收益的?"

例子:

- Z = 服务网格 → 在中等规模团队里负收益

- Z = 单元测试覆盖率 100% → 在快速迭代的早期产品里,可能锁死设计自由度

- Z = GitOps 全量声明式 → 在需要频繁灰度和回滚的业务里,声明式反而限制了运营灵活性

### 使用方式

每篇技术文章动笔之前,主动问作者:

> "这个题材你心里有没有一个反直觉的判断、或者跟主流看法不太一样的角度?
> 如果有,讲一下我帮你展开。
> 如果没有,我可以用三个提问模板帮你挖一下,挖完你来选。"

## 五、机制解释五层法

技术章节要求"机制 > 现象",但机制本身也分深浅。把因果链推到第几层,决定文章的深度。

```
第 1 层:现象——发生了什么
第 2 层:直接原因——为什么发生
第 3 层:原因的原因——为什么会有这个原因
第 4 层:系统性根因——这背后的系统模式是什么
第 5 层:不可改变的物理 / 认知 / 组织约束——为什么这个模式无法被简单修复
```

不是每篇都要推到第 5 层,但要清楚自己写到了哪一层。**停在第 2 层就发的文章,大概率是水文。**

### 完整示例:半自动化流水线卡点的五层推演

```
第 1 层:半自动化卡点上线 2 个月后,人工审批退化为机械点击
第 2 层:审批人对高频告警建立了直觉判断,逐渐跳过实质审查
第 3 层:重复决策模式下,人脑会自动压缩决策路径以节省认知资源
第 4 层:任何"高频 + 低风险 + 预期结果偏态"的人工决策都会经历同样的衰退
第 5 层:这是前额叶皮层在重复刺激下的生物学约束,无法通过流程设计绕开
```

**第 5 层的价值:** 一旦推到这一层,读者就理解了"为什么换个人来审、加个 KPI 考核都没用"——因为问题不在人,在系统的认知边界。

### 写作落点

技术方法论型推到第 3-4 层。架构原理深度型推到第 4-5 层。如果题材本身不支持推到第 4 层(比如纯工具使用类的小话题),要么改写题材,要么承认"这篇只写到第 2 层,目的是介绍而非分析"。

## 六、数量级推演四步

架构原理深度型大量用"延迟 0.5-2ms / 5 跳 / 10%-40% 预算"这种推演。这是一个可教的方法。

### 四步骤

1. **找一个基础事实**——单次操作的开销(延迟、内存、CPU)
2. **找一个乘数**——频次 / 链长 / 规模
3. **算出总量**——基础事实 × 乘数
4. **把总量和某个基准比**——预算 / 容量 / 阈值

### 输出格式要求

- **必须给出区间**(0.5-2ms),不要只报一个数字,让不确定性留在纸面上

- **必须标注数字来源**或"经验估计"(避免读者把估计当成实测)

- **必须给出对比基准**,纯数字没有意义,与基准比较才有意义

### 完整示例

```
基础事实:Sidecar 每次本地代理引入 0.5-2ms 延迟(基于 Envoy 公开 benchmark)
乘数:典型内部调用链 5 跳,每跳两次代理(出站 + 入站)= 10 次代理操作
总量:5-20ms 额外延迟
对比基准:业务 P99 延迟 50ms
结论:Service Mesh 直接吃掉延迟预算的 10%-40%
```

### 反例

```
× Service Mesh 会带来一定的性能开销。
× Service Mesh 的延迟增加大约 15ms。
   (没有区间,没有来源,没有对比)
✓ 用上面的完整示例
```

## 七、典型案例三要素

技术章节的案例不是主体,只是论据。但作为论据必须足够有说服力。**案例类型不限——踩坑、优秀实践、对比观察、失败复盘均可。**

### 三要素

1. **可识别的真实情境**——具体的时间、规模、技术栈、组织结构,让读者相信这是真发生的
2. **关键转折点**——什么时候、因为什么,事情走向了一个意外的方向
3. **多一层的认知**——现在回头看,比当时多了什么理解。如果"现在的理解"等于"当时的理解",这个案例不值得写

### 反例(只有要素 1)

```
× 我之前在一家公司用过 Service Mesh,后来去掉了。
```

只有真实情境,没有转折点,没有认知增量。这是流水账,不是案例。

### 反例(只有要素 1 和 2)

```
× 我之前在一家公司用过 Service Mesh,后来因为延迟问题去掉了。
```

有转折点,但没有认知增量——读者只知道"延迟有问题",不知道"为什么这个团队没预见到延迟问题"。

### 正例(三要素齐全)

```
✓ 三年前我在一个团队帮他们上 Service Mesh。当时我们大概 40 个服务,3 种主要技术栈,
   2 个交付团队。引入后第二个月,业务方开始抱怨某个核心接口的 P99 从 45ms 涨到 80ms。
   排查了两周,定位到 Sidecar 引入的 5 跳代理把延迟预算吃完了。
   
   现在回头看,盲区在评估方法。我们看到了 Service Mesh 的功能收益,
   却没有为"延迟预算"这一项单独立账。
   
   这一次踩坑之后,我后来评估任何基础设施引入,都会专门列一张"它消耗了哪些隐性预算"
   的表。这张表如果空着,这个评估就不算做完。
```

三要素齐全:具体规模、关键转折(延迟暴涨)、认知增量(从此多了一张"隐性预算表")。

### 案例使用边界

技术章节里案例的占比上限:

- 技术方法论型(沉淀 + 深水区合并):场景和案例按论证需要使用,不超过全文 25%;场景型文章可以提高比例,但每个场景都要改变判断或解释机制

超过这个比例,文章就从"方法论 / 原理分析"变成了"故事 + 总结",失去技术章节的定位。

## 八、第一人称的按需集中原则

技术章节的第一人称频率降到中低,而且不平均分布。**按需集中**:

- **可以集中在结尾的"承认段"**——只留下一个真实的限制或未解决问题,不连续铺陈自述(适合技术方法论型)

- **可以集中在某一节的过渡段**——用一句话交代判断如何改变,不要让每段都以「我」开头

- **可以集中在案例展开时**——写清做了什么、看到什么、为何取舍,其余句子交给具体主体和动作

**不要求固定句式,不要求固定位置,按需使用。合并路由通常保留 2-4 处「我」;技术思辨型按其独立规则保留 1-2 处。**

技术方法论型通常保留 2-4 处第一人称,让读者知道判断从哪里来。文章没有真实亲历时,不硬塞「我」,改用具体主体、来源和作者判断保持说话位置;完全没有作者位置的技术文章才会变成 wiki。

### 8.1 重点句与短句

- 开头三段内直接给出核心判断,不要让读者读完整篇才知道文章要解决什么。

- 每个主要章节至少留一个重点句,用来钉住事实、机制或取舍。整篇保留 3-6 个有材料支撑的金句或行动句即可,不把每段都写成断言。

- 技术文章单句优先不超过 35 字,超过 45 字拆分,超过 60 字必须拆。复杂因果用两句或两个段落承接,不要把多个判断塞进一个长句。

- 段落通常控制在 2-5 句。重点句可以单独成段,但必须给出新的事实、判断或后果。

## 九、技术章节的结构模板

### 合并路由标准结构(沉淀 + 深水区)

```
【标题】反直觉判断 + 方法论关键词
  例:「AI 写代码的成本,常常落在分诊失败」
  例:「vibe coding 的深水区,从工具使用走到工程治理」
  ↓
【可选名言起手】一句能概括全文主题(冷 / 短 / 张力对位)
  ↓
## 1. 从一个真实工程场景开始
  - 直接写「正在处理什么 / 想解决什么问题 / 现场出现什么变化 / 哪个产物或数据让判断改变」
  - 第一章末尾优先落出一次判断变化,不强制套用固定翻案句
  - 避免暴露公司名、内部系统、真实项目名和敏感链路
  ↓
## 2. 从现场抽出核心判断
  - 用直接陈述写出核心判断,再补事实、机制和取舍
  - 可引入外部文章或理论框架,但只为论点服务
  ↓
## 3. 建立概念框架(分类 4-8 类)
  - 每类:人的状态 / 本质问题 / 常见错误 / 正确角色 / 推荐措施(五选二即可,建议给三项)
  - 分类名称像问题,不像学术术语
  - 分类多时最后给一个总结表
  ↓
```

### 场景侧重与默认硬约束的对照

技术方法论型的场景侧重是「**从一个具体工程问题进入,再把现场抽象成方法论**」。它保留沉淀风格的框架、机制和落地路径,也保留深水区风格的决策链、工具沉淀和工程现场感。相对 SKILL.md 主文件的默认硬约束:

| 默认硬约束          | 合并路由的偏离                                                                    |
| -------------- | -------------------------------------------------------------------------- |
| 「具体即真实」        | **强化**——场景是骨架,不是辅助;必须有具体可感的工程场景(项目启动 / 工具使用 / 流程优化 / 踩坑复盘 / 需求设计),不写空泛行业背景 |
| 「活人在场」         | **按需使用**——第一人称通常 2-4 处,集中在亲历动作、取舍、困惑和复盘;不要让每段都以「我」开头                       |
| 价值观第 5 条「文艺」必带 | **中段去文学化**——开头保留,中段框架/分类章节去文学化,结尾回到人能力迁移时克制不抒情                             |
| 极短句独立成段 3-5 处  | **拉到 5-8 处**——集中在反转判断与金句位置                                                 |
| 反 AI 终审 L4     | **强化**——这是此原型最强的反 AI 鸡汤防线,任何「赋能 / 闭环 / 未来已来」一类表达直接打回                       |
| 落地清单           | **可选**——以方法论框架呈现,而非「步骤 1/2/3」清单;如果介绍 skill / 工具,按第五章结构走                    |
| 升维             | **不要求升维宏大叙事**——结尾回到工程师能力迁移,不拔高到时代                                          |

## 十、落地路径模块

落地路径模块是技术章节独有的,不与理论章节并列。

### 10.1 三条硬规则(不可违反)

落地路径的内部组织方式不强制,但必须满足以下三条:

1. **每个落地动作必须有一个加粗的核心句作为视觉锚点**——读者扫读时只看加粗部分就能拿走核心动作,不需要读完整段。段内的关键概念、并列维度、动作词也可以按需加粗,但要遵守全局加粗规则(单段加粗密度不超过 15%)
2. **落地路径占全文不超过 25%**——超过就要砍掉次要动作或拆成系列文章
3. **每个动作的篇幅不超过 1 个屏幕**(中文约 200-300 字)——超过说明这个动作可以再拆成两件事

第 1 条是落地路径写好的关键。落地路径之所以容易写糟,就是因为多个动作平铺、缺少视觉层次。加粗的核心句解决两个问题——一是给读者扫读锚点,二是逼写作者把每个动作的「最核心一句」提炼出来。如果一个动作提炼不出加粗的核心句,说明这个动作本身没想清楚。

### 10.2 加粗核心句的写法

加粗的位置默认放在段落末尾,作为「结论锤」。少数情况下也可以放在段落开头,作为「行动亮相」。

**段尾锤式(推荐):**

```
不用追求完美。先写五节最关键的,构建命令、测试命令、部署流程、代码规范、已知陷阱。每节三五条。总长度控制在一屏以内。

这件事看起来不起眼,但只要存在,它就会开始被维护。第一版只要存在,后面每次 PR 就会有人补一行、改一行。

**今天就做的事:在 repo 根目录 touch AGENTS.md,先把构建命令写进去。**
```

**亮相式(用于动作非常明确的情况):**

```
**把上下文审计做成定时钩子,不要做成人工流程。**

具体做法是配一个每周跑一次的脚本,自动扫描最近被频繁修改但 AGENTS.md 没动的文件、注释覆盖率异常低的模块、if-else 分支密度过高的代码段。把扫描结果发到团队群,只让人做「要不要修」的决策。
```

每个落地动作选一种,不要两种混用。

### 10.3 组织方式(四选一,按题材选)

**按读者处境分类**——题材有明显的「读者所处阶段」差异时用。判定信号:你能想象出至少三类不同的读者,他们面对这个题材时处境完全不同。

```
### 如果你今天就想动手,从这一件事开始
[一段说明 + 段尾加粗动作]

### 如果你已经在做,但想让它别在三个月后过期
[一段说明 + 段尾加粗动作]

### 如果你想系统性地清掉存量
[一段说明 + 段尾加粗动作]
```

**按步骤分类**——题材是一个明确的动作流时用。判定信号:读者无论处境,要走的都是同一条线性路径。

```
### 第一步:[动作名]
[一段说明 + 段尾加粗动作]

### 第二步:[动作名]
[一段说明 + 段尾加粗动作]

### 第三步:[动作名]
[一段说明 + 段尾加粗动作]
```

**按判定结果分类**——题材是判断题时用。判定信号:不同条件下读者应该走完全不同的方案。

```
### 如果满足条件 A → 走方案 1
[一段说明 + 段尾加粗动作]

### 如果满足条件 B → 走方案 2
[一段说明 + 段尾加粗动作]

### 如果两者都不满足 → 暂时不动
[一段说明 + 段尾加粗动作]
```

**单一核心动作**——题材只有一件最重要的事时用。最克制的形式,直接写一段。

```
[一段说明 + 段尾加粗动作]
```

### 10.4 补充模块(可选,放在主动作之后)

**检查清单**——用问题逼读者自己回答,不是陈述。

```
### 动手前的自检清单

1. 你的目标读者是谁
2. 这件事失败了你能承担吗
3. 三个月后你打算用什么指标衡量它
4. 谁来负责这件事的持续运营
5. 你今天就能拿到的最小验证样本是什么

**任何一题答不出,这件事就别启动。**
```

**速查表**——放在最末尾,作为可截图保存的资产。

```
### 核心结论速查表

| 维度 | 条件 A | 条件 B |
|------|------|------|
| 维度 1 | ... | ... |
| 维度 2 | ... | ... |
```

速查表不是必需的,但对方法论型文章是加分项——读者可以截图保存,跨越文章生命周期持续使用。

### 10.5 落地路径的反例

下面是这次规则更新前常见的踩雷写法。

**反例 1:动作平铺,没有加粗锚点**

```
### 如果你正在评估

做三件事。第一,统计你团队当前的服务数量。第二,统计你团队的技术栈种类。第三,数你团队的独立交付团队数量。

### 如果你已经引入了

做三件事。第一,统计 Sidecar 引发的故障次数。第二,统计实际使用的治理功能比例。第三,估算排查时长变化。
```

问题:两段长得一样,读者扫读时抓不到重点。修复:每段补一个段尾加粗的核心动作句。

**反例 2:加粗密度超标,什么都是重点**

```
### 如果你正在**评估**

先**统计**你团队当前的**服务数量**、**技术栈种类**和**独立交付团队数量**这**三个维度**,然后用**经验阈值**(**100/3/5**)**对照判断**。
```

问题:一段约 50 字加粗了 8 处共 22 字,密度 44%,远超 15% 上限,且多处是纯强调,视觉拥堵。修复:保留 1-2 处真重点(例如「**100 / 3 / 5** 这三个阈值」作并列维度),其余去掉,段尾补一句完整动作的加粗结论锤。

**反例 3:落地路径超长,占全文 40%**

问题:超过 25% 上限。修复:砍掉次要动作,或者拆成系列文章。一篇文章只承载一个理论框架 + 与之最紧密关联的落地动作,其余次要动作单独成篇。

## 十一、技术章节专属禁区

除了 SKILL.md 主文件和 `ai_fingerprint_blacklist.md` 里的通用禁区,技术章节额外禁止:

1. **含糊副词**——"显著""明显""大幅""极大""相当"等。所有副词必须替换为具体数字。
2. **没有数据时下结论**——任何"我认为 X 比 Y 好"的判断都必须有数据或机制支撑,不能只凭直觉。
3. **把"行业最佳实践"作为论据**——"业界普遍认为""主流方案是"不是论据。要么给出具体来源,要么自己重新论证。
4. **回避边界条件**——"这套方法适用于所有团队"几乎都是错的。必须明确什么规模 / 什么条件下成立。
5. **抽象动词替换具体动作**——"实现""构建""打造""赋予"等。要说具体怎么做。
6. **用术语堆叠掩盖空洞**——把简单的事用术语包装成复杂的事。如果一段话去掉术语后变成废话,这段就是废话。
7. **翻案腔家族句式**——现行合并路由按 `human-writing` 规则直接清除,见下文 11.1。

### 11.1 翻案腔家族句式直接清除

现行的技术方法论型合并路由沿用 `human-writing` 的硬规则。正文禁用「不是 X,而是 Y」及其同类翻案句,直接给判断,再给依据。旧版「全文不超过 3 处」只作迁移记录,不再是当前写法。

家族范围:

- 「不是 X,而是 Y」

- 「不在于 X,而在于 Y」

- 「不再是 X,而是 Y」

- 「不是 X 的问题,是 Y 的问题」

- 「看起来像 X,真正麻烦的是 Y」

- 「问题不在于 A。问题在于 B。」「这不是 X。这是 Y。」(短句版)

**当前要求**:

- 正文与小标题清零。原话命中时改成转述或删掉,不能靠引号保留。

- 先找到这句话要下的判断,从正面写出来,再把事实、机制或取舍放在旁边。

- 只有文章真的用材料走过从误解到修正的过程,作者的自我修正才可以出现,也不能套用固定翻案句。

**改写路径**(按优先级):

1. 直接断言:「Y 才是关键。」「真正的成本在 B。」「重点是 C。」
2. 反问:「那真正的问题是什么?是 B。」
3. 短句断开:把一个复合判断拆成两句,每句只写一个可验证的结论,中间留一行无主句做喘息。
4. 改成案例:用具体场景代替抽象反差。

**判别自检**:写完后,把所有先立误解再推翻的句子列出来。现行合并路由应当清零;发现命中就回到直接判断。

## 十二、技术章节可读性自检

L2 自检里专门为技术章节加的一项。

### 折返测试

通读全文。如果任何一段读到一半,需要回去重读才能理解,标记这段。

### 术语密度测试

每段统计"新术语数"。超过 2 个的段落必须拆。

### 喘息句测试

每节末尾必须有一句无术语的喘息句。没有的节,在末尾补一句。

### 白话注释测试

每个关键术语第一次出现时,后面 15 字内必须有白话注释。没有的,补上。

### 通读情绪测试

通读时,问自己:"如果我是一个对这个话题感兴趣但不是专家的工程师,我会不会读到第三节就走神?"如果答案是"会",这篇文章太冷了,需要回炉。

### 翻案腔句式测试

把全文里「不是 X,而是 Y」及其同类翻案句全列出来。现行合并路由应当**清零**,逐句改成直接断言、事实说明或案例推进。详见 11.1。

## 十三、技术章节的开头与结尾

### 开头

优先用名言起手,且优先引技术权威(Fred Brooks、Edsger Dijkstra、Donald Knuth、Werner Vogels、Tony Hoare、Leslie Lamport 等)。名言不预设清单,根据论点实时搜索最贴切的。

如果题材本身天然适合"问题陈述"起手,可以不用名言,但在第二段或第三段补上一句名言或一个跨界引用,保持泥巴猪文风的稳定锚点。

### 结尾

理论章节的"写在最后"用 SKILL.md 主文件中结尾七种里的任一种,推荐:

- **眩晕收束**(博尔赫斯式)——让人愣一下,世界被悄悄重组

- **回环呼应**——回到开头的名言或核心比喻,但视角已经不同

- **哲思余韵**——一个短句留白

落地路径模块结尾,不用文学性收束,用"速查表"或一句实操级的总结性建议结束即可。

- [ ] 是否有 3-6 个有材料支撑的重点句?

- [ ] 落地路径是否满足三条硬规则(每个动作有加粗锚点 / 占全文 ≤25% / 每动作 ≤1 屏)?

**字数与密度**

- [ ] 字数是否在 4500-7000(框架型收敛在 5500 字内)?

- [ ] 第一人称是否 2-4 处,集中在亲历动作、取舍、困惑和复盘?

**反 AI 鸡汤与功能列表化**

- [ ] 没有出现「赋能 / 闭环 / 抓手 / 底层逻辑 / 范式革命 / 颠覆 / 降本增效 / 未来已来 / 强烈推荐」等营销话术

- [ ] 工程隐喻服务于解释,有材料再用,不硬塞

- [ ] 翻案腔句式清零(见 11.1)
