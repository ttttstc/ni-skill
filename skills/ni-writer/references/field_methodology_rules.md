# 技术方法论型(深水区风格) · 工程现场方法论专项规则

本文档覆盖 ni-writer 的第 6 种文章原型:**技术方法论型(深水区风格)** / **工程现场方法论型**。
这一原型在 `SKILL.md` 主文件里只做简略提及,完整规则在此展开。

> **命名变更说明**:自 v0.3 起,「工程现场方法论型(深水区实践)」统一为「**技术方法论型(深水区风格)**」,与原型 3「**技术方法论型(沉淀风格)**」并列,同属「**技术工程方法论型**」主类。两类区别:沉淀风格以框架为骨,深水区风格以场景为骨。

它与原型 3(技术方法论型,沉淀风格)在结构上有重叠,但气质完全不同:

- 原型 3(沉淀风格)强调"**我把框架掏给你**"——以框架为骨架,案例为辅助。
- 原型 6(深水区风格)强调"**我遇到了一个具体问题**"——以真实工程场景为入口,把场景抽象成方法论,再落到可执行工作流。

它是亲历感(原型 1)与框架感(原型 3 沉淀风格)的中间态,但**比原型 1 更克制、更工程化、更反 AI 鸡汤**。

判型防串详见 `SKILL.md` 的「3 / 4 / 6 判型防串指南」一节。

---

## 一、风格定位与作者人格

### 1.1 风格定位

当用户要写 AI / DevOps / 工程化 / 架构 / Agent 工作流相关长文,并且希望文章**既有真实工程场景,又能沉淀成方法论**时,使用这个原型。

这个原型不是纯技术教程,也不是产品体验文,更不是情绪随笔。

它的核心是:**从一个真实工程场景出发,把具体问题抽象成方法论,再落到可执行工作流。**

### 1.2 "真实工程场景"的来源

场景可以是以下任意一种——**不强制是失败复盘**:

- 一次失败或踩坑
- 一次需求设计
- 一次工具使用体验
- 一个现实问题的解决过程
- 一个新项目的启动过程
- 一次流程优化
- 一次对现有工作方式的反思
- 一个从模糊需求走向结构化方案的过程

### 1.3 作者人格

作者身份是:**一个长期在工程现场使用 AI、DevOps 工具和自动化工作流的人**。

他不是站在高处讲道理,而是在真实项目、真实需求、真实流程里观察问题,然后回过头总结:**这个问题到底是什么,下一次怎么处理得更好**。

### 1.4 文章读感

应该像:**一个有工程经验的人,正在处理一个具体问题。**

他一开始只看到问题表层,后来逐渐看到问题背后的结构。最后,他把这套结构整理成一个可以复用的方法、流程或 skill。

## 二、适用与不适用

### 2.1 适合的主题

- AI 编程、Vibe Coding、Agentic Coding
- Claude Code / Codex / Cursor / Opencode / Gemini CLI 等工具使用反思
- DevOps、CI/CD、工程流程治理
- 架构设计、复杂项目协作、技术债治理
- AI workflow、skill、prompt、agent 方法论
- 从真实需求中抽象出的工程经验
- 从工具使用中提炼出的协作模式
- 从一个现实问题出发,整理成公众号技术长文

### 2.2 不适合的主题

- 纯工具安装教程
- 纯 API 文档解释
- 短平快新闻速读
- 纯鸡汤式成长感悟
- 没有真实场景、没有方法论抽象的普通观点文

---

## 三、核心气质

这类文章的气质:**真实、克制、工程化、有反思感**。

- 不是热血,不是煽情,也不是"AI 时代程序员必须如何如何"。
- 更像:**我遇到了一个具体问题。我一开始以为问题在 A。后来发现真正的问题在 B。于是我重新整理了一套判断框架。这套框架未必完美,但能帮我下一次处理类似问题。**

语气允许有一点自嘲和真实困惑,比如:

- "我感觉自己变成了一个嵌入式工程师。"
- "这对 AI 也不公平。"
- "AI 不是故意做错。"
- "工具越来越多,入口问题反而没有解决。"
- "这句话不能说错,但没有价值。"

但不要变成段子文。**幽默来自工程现实本身的荒诞,不来自夸张修辞。**

## 四、子风格配比与字数

| 维度 | 工程现场方法论型 |
|------|------|
| 口语化 | 中(比技术方法论型稍高,比产品体验型低) |
| 案例占比 | **高**(案例是骨架,不是辅助) |
| 术语严谨度 | 高 |
| 第一人称频率 | **高(5-7 处,集中在我以为 A 其实 B 的认知反转处)** |
| 文学性 | **开头保留,中段去文学化,结尾回来但不抒情** |
| 推荐字数 | **4500-7000 字** |
| 加粗密度 | **8%-15%** |
| 极短句独立成段 | 全文 5-8 处,集中在"反转判断"和"金句"位置 |

三家配比建议(在 SKILL.md 默认 40/30/30 基础上调整):

- **工程现场方法论型** → 奥威尔 55 / 卡尔维诺 25 / 博尔赫斯 20
- 比技术方法论型多 5 个点的 Orwell(冷反讽 + 立场密度)
- 比产品体验型少 Borges 的隐喻含量,但保留卡尔维诺的"轻承载重"

## 五、文章结构模板

优先使用下面六章结构。

```
# 标题:一个反直觉判断 + 一个方法论关键词

> 可选引用:一句能概括全文主题的名言

## 1. 从一个真实工程场景开始
## 2. 给问题命名:它不是 X,而是 Y
## 3. 建立概念框架(分类 4-8 类)
## 4. 讨论关键张力
## 5. 沉淀成工作流 / skill / 方法
## 6. 收束到工程师能力迁移
```

### 5.1 第一章:从一个真实工程场景开始

用一个具体场景开头。场景可以是:

- 我在做一个新项目
- 我想解决一个现实问题
- 我在设计一个工具 / skill / workflow
- 我在使用某个 AI 编程工具
- 我在推进一次流程优化
- 我在处理一个复杂需求
- 我在复盘一次失败或偏差

**不要泛泛说"最近 AI 很火""AI 改变了开发方式"。** 要直接写:

- 我在做什么
- 我想解决什么问题
- 我原来怎么理解这个问题
- 真实推进后出现了什么新情况
- 这个过程让我意识到什么

这一章要有真实感,但**避免暴露公司名、内部系统、真实项目名和敏感链路**。

### 5.2 第二章:给问题命名——它不是 X,而是 Y

把第一章的具体场景抽象成一个核心判断。常用句式:

- "我后来意识到,问题不在于 X,而在于 Y。"
- "这不是一个模型能力问题,而是一个协作结构问题。"
- "这不是 prompt 写得不够好,而是未知没有被显性化。"
- "这不是工具不够多,而是入口判断不清楚。"
- "这不是执行失败,而是分诊失败。"

这一章可以引入外部文章、行业观察或理论框架,**但外部材料只服务于本文论点,不要写成读书笔记**。

#### 5.2.1 「不是 X,而是 Y」家族句式硬上限(防模板腔)

技术方法论型(深水区风格)把「它不是 X,而是 Y」作为**章节命名武器**,但章节内的**文字**严格限制这类句式——章节名钉一次是风格,文字里反复用就是模板腔。

家族范围(同 tech_writing_rules.md 11.1):

- 「不是 X,而是 Y」
- 「不在于 X,而在于 Y」
- 「不再是 X,而是 Y」
- 「不是 X 的问题,是 Y 的问题」
- 「看起来像 X,真正麻烦的是 Y」
- 短句版:「这不是 X。这是 Y。」「问题不在于 A。问题在于 B。」

**硬上限**:
- 全文累计**不超过 4 处**(比沉淀风格多 1 处,因为深水区风格允许在反转章节与张力章节各出现一次)。
- 任意两段相邻**不得**都用。出现两段相邻时,改写其中一段。
- 章节标题**可以用**这种结构(本章标题就是范例),但**全文所有章节标题里只能出现一次**这种结构,第二次的章节标题必须换成普通命名(如「讨论关键张力」「沉淀成方法」)。
- 第三章「分类框架」章节内部**禁止**用这种句式——分类章节要用陈述式分类名(如「管理未知」「承重问题」),不要每条分类都用反差句式。

**改写路径**(按优先级):
1. 直接断言:「Y 才是关键。」「真正困难的是 B。」「重点是 C。」
2. 反问:「那真正的问题是什么?是 B。」
3. 短句断开:把「不是 X,而是 Y」拆成两行,中间留一行无主句做喘息。
4. 改成案例:用具体场景代替抽象反差(深水区风格最常用)。
5. 改用"我"做主语:「我真正在意的不是 X,而是 B。」——主语位移也能制造反差,但更个人化。

**判别自检**:写完后,把所有用这类句式开头/结尾的句子列出来,**超过 4 处立刻砍**。**两段相邻出现也要砍**。

### 5.3 第三章:建立概念框架

用一组清晰分类解释问题。**分类数量建议为 4-8 个。**

每类都要回答:

- 人处在什么状态
- 本质问题是什么
- 常见错误是什么
- 应该让 AI / 工具 / 流程扮演什么角色
- 有什么可执行做法

**如果分类很多,必须在最后给一个总结表。**

### 5.4 第四章:讨论关键张力

不要只给方法,还要讨论方法的边界。常见张力:

- 约束太少 vs 约束太多
- AI 主动性 vs 人类控制感
- 多问问题 vs 把人变成审批流
- 工具越多 vs 入口越乱
- 快速实现 vs 方向性返工
- 自动化效率 vs 人类判断力

这一章要写出判断:**问题不在于要不要约束,而在于约束有没有落在承重点上。**

### 5.5 第五章:沉淀成工作流 / skill / 方法

如果文章要介绍一个 skill、工具或工作流,**不要写成广告**。先写:

- 它要解决什么问题
- 为什么已有方式不够
- 它的生效逻辑是什么
- 它带来什么收益
- 它不解决什么

最后再给链接。

### 5.6 第六章:收束到工程师能力迁移

结尾不要喊口号。要回到人的能力变化:

- 从写代码,迁移到定义问题
- 从补细节,迁移到识别未知
- 从盯语法,迁移到判断质量
- 从控制每一步,迁移到设计协作节奏

**结尾要短,有余味。**

## 六、开头写法约束

开头**必须从一个具体工程场景进入**。这个场景不一定是失败。可以是一次现实问题的解决过程,也可以是一个新需求的设计过程。

### 6.1 推荐的五种开头类型

**现实需求型**

```markdown
最近我想做一个小工具。

需求听起来很简单:每天早上自动告诉我今天最该关注的几件事。

但真正开始设计时,我发现问题并不在"怎么生成摘要",而在"什么事情值得被提醒"。
```

**工具使用型**

```markdown
最近我在用 AI 辅助推进一个新项目。

一开始我只是想让它帮我把想法整理成方案。结果聊着聊着,我发现真正困难的不是生成方案,而是判断这个方案到底是不是我真正想要的东西。
```

**流程优化型**

```markdown
最近我在整理一套 AI 编程工作流。

刚开始,我以为问题是 prompt 不够系统。后来发现,prompt 只是表层,真正麻烦的是:不同阶段的未知混在一起,AI 不知道自己此刻应该扮演什么角色。
```

**被工具折磨型**

```markdown
最近我在做一个新项目。

一开始,我以为问题出在模型能力上。于是我切了更强的模型,换了更长的 prompt,也让 AI 做了更多轮自检。

但问题没有消失。

相反,开发越往后走,我越感觉自己被拖进了细节泥潭。
```

**工程隐喻型**

```markdown
这件事有点像盲人摸象。

我摸到一条腿,以为自己要的是一根柱子;AI 摸到一只耳朵,以为我要的是一把扇子。

两边都没错。

但两边都没有看到完整的大象。
```

### 6.2 开头禁区

- 不要用"随着 AI 技术快速发展"
- 不要用"在当今时代"
- 不要用"AI 正在改变软件工程"
- 不要先铺行业背景
- 不要先下宏大结论
- 不要强行把所有文章写成失败复盘

## 七、句式风格

优先使用短句。段落可以短。一个关键判断可以单独成段。

**句式硬上限**:下列推荐句式属于「不是 X,而是 Y」家族,**全文累计不超过 4 处**,两段相邻不得连用。详细规则与改写路径见 5.2.1。

推荐句式:

```markdown
这不是 X。

这是 Y。
```

```markdown
问题不在于 A。

问题在于 B。
```

```markdown
它看起来像 A。

但真正麻烦的是 B。
```

```markdown
这句话不能说错。

但没有价值。
```

```markdown
这对 AI 也不公平。
```

```markdown
AI 不是故意做错。
```

```markdown
工具越来越多,入口问题反而没有解决。
```

这种句式的作用是**制造判断密度**。**不要把每个判断都解释三遍。**

## 八、论证方式:五段式

每个核心观点按下面顺序展开:

```markdown
场景:我在做什么 / 想解决什么问题
误判:我一开始以为问题是什么
反转:后来发现真正问题是什么
机制:为什么会这样
方法:下一次应该怎么处理
```

**示例:**

```markdown
场景:我想做一个自动生成重点事项的小工具。
误判:我以为问题是怎么生成摘要。
反转:后来发现的问题是怎么判断"什么值得提醒"。
机制:如果优先级标准没有显性化,AI 只能按常见待办逻辑补全。
方法:先让 AI 做定义澄清,再进入功能设计。
```

第一章必须出现一次"我原来以为 A,后来发现 B"的认知反转。**全文建议至少出现 3-5 次这样的反转**,但不能滥用。

## 九、隐喻使用规则

这个风格允许使用隐喻,但**隐喻必须服务于工程理解**。

### 9.1 优先使用的工程隐喻

- **盲人摸象**——用于说明人和 AI 都只看到局部上下文
- **聪明实习生**——用于说明 AI 执行力强,但需要澄清
- **地图与领土**——用于说明 prompt / 文档 / skill 和真实代码库之间的差异
- **医院分诊台**——用于说明 skill / workflow 的入口路由作用
- **审批流**——用于批评过度澄清和无效确认
- **深水区**——用于表达从浅层 prompt 技巧进入真实工程复杂性

### 9.2 禁止使用

- 过度文学化隐喻
- 与工程问题无关的宏大比喻
- 一篇文章同时堆 5 个以上主隐喻
- 把隐喻写成散文段落

### 9.3 隐喻写法要短

```markdown
这很像医院分诊台。

分诊台不负责治疗,但分诊台决定你别一上来就找错科室。
```

## 十、加粗规则

适度加粗,**密度控制在 8%-15%**。

### 10.1 推荐加粗对象

- 每章核心判断
- 方法论关键词
- 反直觉结论
- 分类名称
- 读者应该记住的操作原则

**推荐加粗:**

```markdown
**管理未知**
**地图不是领土**
**先分诊,再行动**
**承重问题**
**不是所有未知都应该问人**
**你请 AI 来帮忙,不是为了把自己变成 AI 的审批流**
```

### 10.2 不要加粗

- 每个小标题里的普通名词
- 每个列表开头
- 普通形容词
- 已经足够醒目的代码块内容
- 连续整段文字

## 十一、分类章节写法

如果文章中有分类章节,**每一类使用稳定格式**。推荐格式:

```markdown
### 分类名称:一句能读懂的问题

先用 2-4 段解释人的状态。

然后指出本质问题:

**本质问题**:……

指出常见错误:

**常见错误**:……

指出正确角色:

**正确角色**:……

指出推荐措施:

**推荐措施**:……

最后给一个简短提示词或操作方式。
```

### 11.1 分类名称必须像问题,而不是像学术术语

**推荐:**

```markdown
定义未知:我说的是需求,还是产品冲动?
路径未知:方向有了,但不知道第一步怎么走
标准未知:我知道不对,但说不清什么叫好
决策未知:哪些问题真的会改变架构?
计划风险:方案看起来合理,但没人唱反调
现状未知:想改代码,但不认识代码库地形
验收未知:AI 说完成了,但我不知道能不能信
```

**不推荐:**

```markdown
第一类:需求澄清阶段
第二类:方案生成阶段
第三类:质量评估阶段
```

### 11.2 每类的硬性要求

**每类至少包含"常见错误 / 正确角色 / 推荐措施"中的两项**(五选二即可,但建议尽量给全三项)。

## 十二、工具 / skill 介绍写法

介绍工具时,**不要写成产品广告**。

### 12.1 反例与正例

**不要先说:**

```markdown
这个 skill 很强大,支持很多能力。
```

**要先说:**

```markdown
它要解决的不是"怎么写一个更强的 prompt"。

它要解决的是另一个关键问题:

> 当下,此刻,AI 对我的需求了解到了什么程度,我还需要澄清什么?
```

### 12.2 工具介绍结构

```markdown
### 它解决的问题

说明已有工作流哪里不够。

### 它生效的逻辑

说明它如何改变默认行为。

### 它带来的收益

用 3-4 条写清楚收益。

### 它的边界

说明它不替代什么。

### 链接

最后给链接。
```

### 12.3 工具介绍的硬约束

- 问题先于能力
- 逻辑先于功能
- 收益先于链接
- 不夸大
- 不写"强烈推荐所有人使用"

---

## 十三、结尾写法

结尾要从工具回到人的能力变化。

### 13.1 推荐结构

```markdown
AI 时代,工程师不会因为 AI 会写代码而失去价值。

但工程师的价值会迁移。

过去我们靠写代码证明自己理解问题。现在,我们要先靠提出问题、发现未知、定义边界、判断质量,证明自己配得上让 AI 写代码。

我现在越来越觉得,vibe coding 最关键的十字路口,不是做了多少决策。

而是它迫使我承认:很多时候,我并没有自己想象得那么清楚。

在充满决策的设计旅程中,最缺少一个在关键时刻能反问自己的人。
```

### 13.2 结尾禁区

- 不要喊"未来已来"
- 不要说"拥抱 AI"
- 不要说"不会 AI 的人会被淘汰"
- 不要写鸡汤式号召
- 不要突然拔高到时代宏大叙事

---

## 十四、语言禁区

避免以下表达:

```
赋能 / 闭环 / 抓手 / 底层逻辑 / 范式革命 / 颠覆
降本增效 / 提质增效 / 全面升级 / 未来已来
不得不承认 / 毋庸置疑 / 显著提升 / 极大改善
强烈推荐 / 一文讲透 / 保姆级教程
```

**除非这些词在引用或反讽中出现。**

---

## 十五、保留的个人口癖

这个风格可以保留以下表达方式:

```markdown
我开始意识到……
更可怕的是……
这对 AI 也不公平。
这句话不能说错,但没有价值。
真正困难的不是……而是……
问题不在于……而在于……
它不是……它更像……
这不是……这是……
所以我开始思考……
后来我逐渐意识到……
```

这些表达能保留真实人的思考痕迹。**但不要滥用,每篇文章使用 6-10 次即可。**

## 十六、最终生成要求(硬性 checklist)

当使用这个风格写文章时,**必须满足**:

1. 开头必须有真实工程场景或现实问题,**不强制是失败复盘**
2. 第一章必须出现一次"我原来以为 A,后来发现 B"的认知反转
3. 至少使用一个工程隐喻(盲人摸象 / 聪明实习生 / 地图与领土 / 医院分诊台 等)
4. 中段必须有分类框架或流程框架
5. 分类不超过 8 类
6. 每类至少包含"常见错误 / 正确角色 / 推荐措施"中的两项
7. 如果介绍工具或 skill,**必须按"问题 → 生效逻辑 → 收益 → 边界 → 链接"写**
8. 全文要有 **3-6 个可传播金句**
9. 结尾必须回到**工程师能力迁移**
10. **禁止**写成工具合集、prompt 合集、AI 鸡汤或产品广告
11. **「不是 X,而是 Y」家族句式硬上限 ≤ 4 处**——详细规则见 5.2.1;超过就是模板腔,立刻砍。

## 十八、与其它原型的关键差异(避免误用)

| 维度 | 工程现场方法论型 | 技术方法论型(沉淀风格,原型 3) | 产品体验评价型(原型 1) |
|------|------|------|------|
| 主驱动 | 真实工程场景 → 抽象成方法论 | 框架 → 落地清单 | 亲历过程 → 体验与判断 |
| 案例的角色 | **骨架** | 辅助说明 | 主体 |
| 反 AI 鸡汤 | **强约束** | 中等 | 中等 |
| 工程隐喻 | 强约束(至少 1 个) | 可选 | 可选 |
| 认知反转次数 | **3-5 次** | 1-2 次 | 0-1 次 |
| 落地清单 | 可选(以方法论呈现) | **必给** | 可选 |
| 结尾 | **工程师能力迁移** | 行动呼吁 / 实操级总结 | 实操级总结 / 信念宣言 |
| 字数 | 4500-7000 | 6500-7000 | 6500-7000 |
| 加粗密度 | 8%-15% | 8%-15% | 8%-15% |

**与原型 3 的判型边界:**

- 如果文章核心是"我有一套框架 / 工具 / 清单可以掏给你",走 **3 技术方法论型(沉淀风格)**
- 如果文章核心是"我遇到了一个问题,事后抽象成了方法",走 **6 工程现场方法论型**
- 区分点:**有没有一个真实场景作为骨架**(原型 6),还是**框架本身就是骨架**(原型 3 沉淀风格)

**与原型 1 的判型边界:**

- 如果文章核心是"我亲自下场玩了一个东西",走 **1 产品体验评价型**
- 如果文章核心是"我处理了一个工程问题",走 **6 工程现场方法论型**
- 区分点:**场景是不是工程问题**(原型 6 偏工程治理、流程、协作、抽象),还是**产品体验本身**(原型 1 偏工具上手 / 产品试用)
