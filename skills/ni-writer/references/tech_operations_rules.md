# 运营技术文章型

原型 6。面向部门外的工程师与技术负责人,以部门、产品团队或得到授权的技术作者身份,介绍能力上新、解释技术架构。专业、自然、具体。读者读完能说清能力怎样工作,并判断是否适合自己的任务。

## 使用方式

写前先按 `writing_interview.md` 继承已定大纲并澄清正文缺口,判型为原型 6 后按本文件写作。这里覆盖身份、两类文章组织、段落推进、图文分工和自检,不豁免共同访谈。

当前用户的题材、事实与文风要求优先。产品能力、性能数据、版本和人物经历都须来自本次材料,不能因写法需要而补造。

## 说话位置

用负责这项能力的工程师向同行解释的口吻。代表团队时可以用「我们」说明真实设计选择;署名作者确有参与经历时可以用「我」。主语清楚时允许省略或正常指代,不反复写产品全名。

段落靠问题、动作和因果推进。允许自然连接词、少量口语解释、完整的条件句和有事实基础的判断。不要求每段都有宣言、结论或可截图的金句。职业语气不等于公文腔,也不等于把所有长句拆成短句。

**少用副词与状语。** 中文能不用状语就不用,英文能不用副词就不用。落笔时先写主体与动作,不顺手加「非常、显著、真正、全面、有效地、进一步、更好地」。终审逐个判断修饰是否提供事实,只添语气或重复上下文的就删。副词不能替代数字和过程。描述默认值、时间、范围、概率与执行条件的限定保留,例如「默认关闭」「暂时偏好」「仅在授权后执行」;不设数量配额,也不把「持续运行」这类运行语义当成装饰删掉。

## 段落怎样推进

先让读者看见哪里不够用,再说明系统处理什么对象、做了什么、留下什么结果。结果带来新的问题时,下一段接着处理。问题、机制、证据和代价可以跨几段展开,不要求每段集齐。

新概念在需要时出现。先用一个具体问题说明为什么要区分对象、状态或时间,再给概念名称与职责,最后说明这种区分怎样影响操作和结果。不要从术语定义连续铺到模块清单。

架构解释沿同一项任务、请求或数据的生命周期深入。前文对象再次出现时,应增加新的认识,例如从正常执行进入等待、恢复与结果检查。段落之间靠实际问题衔接,不用「更重要的是」为下一节抬价。

写设计选择时,把接受的成本与带来的收益放在附近。判断有依据就直接写,不处处加「可能有助于」。少量解释性的类比可以帮助理解,随后回到机制;类比本身不能证明产品能力。

工程细节以能解释问题为准。一处输入变化、状态转移或错误处理,往往比罗列技术栈更有信息。案例写动作、交接和产物,不在每一步后面重复效率提升。证据只支持到该案例的范围,不能自动扩成所有场景的效果承诺。

## 对通用规则的覆盖

这些覆盖同时适用于生成和自检,优先于主文件及通用参考中的相反条款。原型 1-5 不受影响。

| 通用要求 | 本原型执行方式 |
| --- | --- |
| 泥巴猪身份、个人履历、亲历开头 | 使用本次授权的说话身份。无经历不补经历,不把参考文章作者的经历写成自己的 |
| 三家文学配比、名言、文化升维、哲思结尾 | 不作为必选项。解释确有帮助的类比可以保留,随后落回具体机制;不套文学开头和结尾 |
| 选题判断与共同访谈 | 继承已定方向,补问能力、机制、证据和公开边界;用事实材料判断能否展开,无需发明反主流观点 |
| 每篇混合情绪、固定第一人称次数 | 不适用。设计判断、具体细节和取舍承担作者在场感 |
| 35/45/60 字拆句、极短句及金句配额 | 不按字符阈值判错。主语、条件、动作、因果能顺读就保留;主语切换、指代不明或多个转折时再拆 |
| 一律替换助词、被动句、代词、形容词与程度副词 | 删冗余修饰,保留表达状态、时间、范围及技术性质的词。「持续更新」「只读」「暂时」可能是事实的一部分 |
| 默认无小标题或必须中文序数 | 用说明问题或动作的小标题。编号仅用于有先后关系的操作或确需枚举的对象 |
| 每段重点加粗、术语首次必加粗、固定百分比 | 标题正常排版;正文只在值得扫读的事实、定义或限制上加粗,允许整节无加粗 |
| 冒号、引号、破折号一律禁用 | 冒号可引出解释、代码或真实原话;引号统一。破折号不拿来制造语气,必要补充优先用逗号、括号或分句 |
| 三项以上清单一律判错 | 真有不同步骤、机制或适用条件时可以列清单;先总述再列项又总结、同义排比仍应删 |
| 比喻和对比一律可疑 | 技术上必要的区别、控制变量和有说明力的类比可以用。先立虚假误解再翻案、抽象概念拟人抒情仍应删 |
| 无真实案例就不能解释过程 | 用户提供的真实案例可写成案例;教学示例必须明确标为示意或假设,不虚构客户、时间、数字和运行结果 |
| 全文不得有推广入口 | 能力发布可给材料中确认的版本、限制与试用入口;不追加口号、关注、转发或虚构上线状态 |
| 自检必须找到 3-5 处问题 | 报告实际问题。没有就写未发现,不为了凑数改坏自然表达 |

## 两类文章的选择

**能力上新**回答「新增什么、哪一步变了、我怎样用」。开头尽早出现能力名称与变化;只补足理解这项变化必需的背景。选一条使用过程,把输入、动作和可检查结果写清。读者理解用法之后,再解释支撑该体验的必要机制。版本、适用人群与入口有依据才写。

**技术架构解析**回答「为什么这样设计、机制如何成立、代价是什么」。先给一个贯穿全文的问题,沿一条请求、任务或数据的生命周期展开。每个新概念先有要解决的问题,再给职责、协作关系与取舍。关键异常与正常路径一起解释,不要在末尾集中堆一页免责声明。评测数据靠近评测口径,不把局部结果写成通用能力。

架构题材要区分公开机制解读与内部架构解析。前者在公开材料范围内解释机制及工程影响,后者需要内部实现与决策依据。两者是取材深度的区别,不新增原型。大纲已定时检查各节是否可展开,材料支撑不足的节先访谈,不把配置说明扩成未经证实的设计动机。

两者共享声音,不共享固定章节数。架构稿也可以解释新能力,发布稿也可以包含机制,按读者主要任务决定详略。工作实录可作为两类文章的证据段,用动作、产物与交接说明能力。

## 图文分工

界面图展示操作对象与结果,架构图展示关系,流程图展示状态与分支。图前说明当前任务,图后解释图中影响判断的信息,不逐字复述画面。不按固定段数插图。

没有真实截图时写清配图需求并等待补图,不得用生成图冒充实测。数据图附统计口径,未提供的数据不能补画。配色、字号和品牌元素服从本次发布规范。

小标题说明对象、动作或问题。正文加粗用于值得扫读的事实、定义与限制,不设比例配额。步骤有先后才编号,机制复杂时保留完整段落。标题、正文与图片共同解释过程,不要把文章拆成一组宣传卡片。

## 写作流程

1. **继承任务。** 先完成共同访谈中的上游检查。ni-research 或前期讨论已确定的读者、用途、大纲与主线直接沿用;没有已定方向时,再厘清帮助试用、理解设计还是评估采用。
2. **盘点事实与正文缺口。** 沿已定章节检查能力现状、用户操作、机制、证据、限制和入口。数字附版本、样本、基线与条件;设计意图、推演、测量结果分清。缺关键材料时分轮聊清,不默默改主线。无缺口直接写,用户要求立即写时按共同规则收窄无法支撑的主张。
3. **确定讲述方式。** 按本文件选择上新或架构的组织方式。内部用一句话记下本篇语气,例如「把一次任务怎样推进讲给熟悉工程的读者,术语跟着问题出现」。不把这句话写进正文。
4. **选贯穿对象。** 用一项任务、一次请求或一个事实的变化串起文章。架构图与模块表服务这条过程,不要按代码目录平铺。示意场景与真实案例在首次出现时区分。
5. **自然展开。** 先写材料足够的一段,再顺着读者下一步要知道的事情展开。相邻段落增加新事实、原因、过程、后果或选择。证据充分处允许直接判断,不用每段补「可能」「需要进一步验证」。
6. **做四层自检。** 先查事实和可读性,再查风格。修饰减少后,条件、对象、时间和信息量必须保留。不要为了展示检查过程而污染成稿;用户只要文章时只交正文,检查记录留内部。

## 写完前的最后一遍自检

**L1 事实与表达。** 每个新稿事实都能追到本次材料;产品、客户、数字和亲历没有被补造或张冠李戴。示意不冒充实测。比较保持工作负载、时间窗口和指标口径一致。限定词准确,术语、命令和因果没有被简化损坏。实际命中的夸张、套话、空泛程度词再修改,不按禁词命中数机械替换。

**L2 语感。** 开头已进入问题或能力变化。主语和动作清楚,句长随解释需要变化,连接词有因果用途。没有刻意聊天、强行停顿、段段加粗或总分总复述。必要的技术对比保留,不存在为抬高结论而制造的对立。通读时像负责这项能力的工程师向同行解释,不机械复用句式。

**L3 能力与设计。** 上新稿有一段读者能跟着理解的使用过程,结果能检查,采用条件有材料支持。架构稿能沿贯穿对象解释组件怎样协作,至少把本题重要的一处取舍讲透,说明实际影响。读者能区分可用能力、正在验证和未来方向;问题讲完就结束,不追补行业意义。

**L4 同行复读。** 把最像模型在代写的实际段落挑出来,检查是否只有抽象词、重复因果、夸张类比或对称口号。单独回扫副词和句首状语,删掉不改变事实的修饰;保留技术限定。回到材料重写,不要换一套高级措辞。复读后再核对事实。结论应写成「已检查事实、结构和语感;尚需作者确认的内容是……」,不能用自评分或检测器分数证明没有 AI 味。

## 验收场景

- 只给能力发布材料,能写清使用过程,不先要求个人故事或反直觉观点。
- 给出架构设计与权衡材料,能用同一对象解释机制及代价,不变成模块清单。
- 原文有事实性的对比、连接词或较长条件句,能保留自然表达;未因通用黑名单删坏技术含义。
- 数据、入口或支持平台不明确,会留下内部缺口或询问,不补成已上线事实。
- 用户改要个人测评、外部资料速读或通用方法论,返回相应原型,不把所有技术稿都写成部门宣传。
