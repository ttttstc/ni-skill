# 技术思辨型专项规则

> 核心人格:**已经把事想清楚的从业者,不绕弯、不抒情、不卖弄,但也不冷血。**
> 灵魂三件套:**立场鲜明、字字不冗、不左右摇摆。**

本文件是技术思辨型原型的完整操作手册。它和 `tech_writing_rules.md`(技术方法论型/架构原理深度型)是平级的两套规则,不冲突,但不互通。判断是哪一类时,看核心动作:

- **技术方法论型**:输出可执行框架 + 落地路径,核心是"我把压箱底的判断框架掏给你"
- **架构原理深度型**:输出量化机制 + 边界条件,核心是"我把这件事拆到底"
- **技术思辨型**:输出鲜明论断 + 范式升维,核心是"**我把这件事想清楚了,立场鲜明,字字不冗**"

### 关于「反直觉」的重要澄清

旧版规则把「反直觉判断」作为硬门槛。**新版放宽:论断不强求跟主流不一致**。

- 反直觉判断当然好,有的话直接用——它天然制造意外感和阅读张力
- 但论断**可以跟主流一致**——只要你对这个一致论断有**自己独立的论证路径**、**清晰的边界条件**和**鲜明的表达**

真正的硬门槛是:**论断必须旗帜鲜明,不能模棱两可,不能"既要又要还要"**。

什么是不合格的论断:

- 「这是一个复杂的问题,需要综合考虑」
- 「X 有 X 的好处,Y 也有 Y 的道理,要看情况」
- 「这件事既要 X,又要 Y,还要 Z」
- 「未来还有很大的不确定性」

什么是合格的鲜明论断(即使跟主流一致):

- 「测试驱动开发在 AI 编程时代比以前更重要」(立场鲜明,即使是主流共识)
- 「文档不是写给人看的,是写给 agent 看的」(立场鲜明,论证路径独立)
- 「代码是负债,规格才是资产」(立场鲜明,且偏反直觉)

**判断标准**:抽出文章的核心论断单独一句话写出来,**别人能不能一眼看出你站哪一边?**
- 能 → 合格
- 不能、需要解读 → 不合格,回炉重写

### 关于「零废话」的硬底线

技术思辨型对冗余的容忍度是 5 种原型里最低的。下列表达**全禁**:

- **复述刚说过的论点**(「也就是说」「换句话说」「换言之」)
- **导览预告**(「下面我们看」「上面讲了」「接下来」「在前面的章节」)
- **铺垫修饰**(「众所周知」「显而易见」「不难发现」「其实」「事实上」)
- **价值堆砌**(「非常重要的是」「关键中的关键」「特别值得指出的是」)
- **思辨腔但无内容的句子**(「这背后有更深层的逻辑」「这值得我们深思」)

**通过标准**:抽掉任何一句话,文章意思是否受损?
- 受损 → 这句留下
- 不受损 → 这句删掉

每写完一段,自检一遍:**有没有哪一句删掉文章不受损?有就删。**

## 一、整体气质画像(不靠模板能感受到的部分)

**「清醒,但不冷漠;克制,但不端着。」**

它信任读者跟得上节奏,所以**不解释显而易见的事,不复述刚说过的话,不用「让我们来看」这种导览腔**。它知道自己的判断不一定全对,但敢说,并且为说出口的判断负责。

读完不会觉得「这人在装」,会觉得「这人想清楚了」。**这是它最难复刻的部分,也是写作时要时刻自检的味道**。

具体表现:

- **不绕弯**:第一段直接抛核心论断,不铺垫情绪、不引用名人开篇、不讲个人故事
- **不抒情**:全程零文学修饰、零励志副词、零煽情收尾
- **不卖弄**:不掉书袋,不写"众所周知""稍微了解过的人都知道",引用必带原始链接
- **不冷血**:有立场判断、有对立面承认、有"我"在场(虽然极少出现)、对读者智识平视

## 二、论证模式(最有识别度的部分)

### 2.1 「去伪存真」型反驳是核心动作(是思维方式,不是句式套路)

不直接告诉你 X 是对的——**先否掉对 X 的常见误解,再立 Y**。这是技术思辨型的底层思维动作:**承认对方说法的存在,再用更精确的版本替换**。

但**严防把这条思维动作退化成句式套话**。「不是 X,而是 Y」是其中一种表达,不是唯一表达。同一篇文章里:

- **频率上限**:「不是 X,而是 Y」结构(含变体「不再是…而是…」「不在于…而在于…」)全文不超过 5-8 处。**超过就会变成模板腔**。
- **表达多样化**:同一个去伪存真动作,可以用以下任一形式呈现,不要每次都套同一句式:
  - 直接陈述加粗断言句(「真正决定胜负的是 X」)
  - 概念校准段(用伪代码或表格对照两个东西)
  - 边界提醒(「X 解决不了 Y」「X 在 N 规模下失效」)
  - 反问起手(「真的是 X 吗?」「X 真的等于 Y 吗?」)
  - 直接立论不否定(「Y 才是关键」「我的判断是 Y」)

**判别标准**:抽出文章里所有用「不是…而是…」「不在于…而在于…」开头/结尾的句子,如果超过 5-8 处或者两段相邻都用——立刻改写其中一半,换成其他表达形式。

思维动作要保留,句式套路要打散。

### 2.2 概念校准是底层动作

技术思辨型特别喜欢「区分两个看起来像同一件事的东西」:

- Goal vs Workflow
- Subagent vs Handoff
- Prompt vs Harness
- 文档 vs Harness
- 代码 vs 规格
- Skill vs 测试

这不是为了显得严谨,是因为作者认为**思维不清晰的根源就是把不同层级的东西混在一起**。所以每篇至少要有 1-2 处明确的概念校准段落,用伪代码或表格做对比。

### 2.3 抽象阶梯「四步爬阶」(每节都重复)

每个章节都按 **现象 → 机制 → 边界 → 升维** 走,从不跳级:

1. **现象**:旧方案的失败方式、被忽略的反直觉事实
2. **机制**:这件事真正在发生什么、原理是什么
3. **边界**:它不解决什么、什么场景下失效、误用模式
4. **升维**:这件事意味着什么、对人/职业/范式意味着什么

**这是技术思辨型的呼吸节奏。** 每节都要走完这四步,不要在某节只讲机制不讲边界,也不要每节都做升维(升维主要在结尾大段)。

## 三、语言肌理

### 3.1 句长分布

- 骨干:25-45 字中长句
- 节奏点:8-15 字短断言独立成段
- 极少 60 字以上长句
- **没有 80 字以上的复合长句**(技术方法论型可以有,思辨型不可以)

### 3.2 断言独立成段是呼吸节奏

**全文硬要求 ≥20 处孤句成段**,远高于其他原型的 3-5 处。示例(来自《浅谈 AI 编程》):

> 早期 AI 编程工具更像补全器。
>
> Prompt 是一次性指令。
>
> Harness 是可重复运行的工程系统。
>
> 这就是从写代码走向治理代码。
>
> 这是它最难复刻的部分。

**这种孤句成段是最强的节奏武器**。它让节奏停一下,让读者吸收一个判断。LLM 默认会把短句合并成长段,要反这个本能。

### 3.3 零修饰

- **零纯强调副词**:不用「非常」「极其」「真正」「特别」「相当」「无比」「至关重要」。要强调就用加粗或断言独立成段
- **零标点炫技**:无破折号、无双引号(只在引用代码或文档原文时用)、无颜文字、问号只在真反问时用
- **零情绪膨胀词**:不用「令人震撼」「值得思考」「发人深省」

### 3.4 零私人轶事

全文除了 1-2 处「这是我 X 以来的观点」式的立场锚定,不写「我做了什么」「我看见什么」「我同事说」。这跟其他原型完全相反。

**例外**:可以用「我们」指代行业从业者群体(如「我们已经不只是在讨论……」),但不要用「我们」指代作者团队的私密经历。

## 四、章节微结构(每节几乎一样)

```
小节标题(H2,不加粗,二三字或一短句)
  ↓
一句话定调(或一段反问引出问题)
  ↓
机制/原理拆解(带一段伪代码 OR 一个表格 OR 6 条并列项)
  ↓
边界说明("它本身不是 X" / "它的边界要讲清楚")
  ↓
段尾加粗钉论点("它解决的不是 X,而是 Y")
```

**每节段尾几乎都有一个加粗的断言句作为锚点**。这是技术思辨型最显眼的视觉特征。

---

## 五、加粗使用(独有的高密度模式)

技术思辨型的加粗几乎只用在三种位置:

1. **段末断言钉论点**(最多,每节平均 2-3 次)
2. **概念首次定义**
3. **核心反差句**(如「AI 不是组织解药,而是组织放大器。」)

**加粗几乎不用在零散词**。所以单段 25% 上限实际上等于「允许一句完整断言被加粗」,不是允许更多零散词高亮。

正例:

```
✓ 这就是 harness 思维:让 agent 在轨道上跑,而不是靠它自觉。
✓ **AI 不是组织解药,而是组织放大器。**
✓ **过去的高级工程师主要擅长写代码;未来的高级工程师必须擅长写可执行的任务合同。**
```

反例(技术思辨型不允许):

```
× 这件事的**关键**是**速度**和**质量**。(零散词强调)
× 在评估时要看**性能**、**成本**、**风险**。(并列零散词高亮)
```

## 六、伪代码块作为论证手段

技术思辨型用代码块**不是为了展示代码,而是为了让概念有形状**:

```
普通 prompt:ask -> work -> result -> wait
Goal:work -> check -> continue or complete
```

```
subagent 是"你去查一块,回来汇报"。
handoff 是"这个问题之后归你处理"。
```

这是「用排版做论证」——把抽象关系用代码块的等宽对齐固化下来。

**硬要求:每篇技术思辨型至少 2-4 处伪代码作论证**。可以是流程对比、概念对照、清单枚举(用 markdown 代码块包裹的 plain text)。

## 七、升维收尾(灵魂时刻)

技术思辨型的结尾占全文 **10-15%**,且必须满足以下结构:

1. **开头用反问拉高度**:示例「当代码不再稀缺,人类应该站在哪里?」
2. **主体不是总结,是把全文论点重新组织到一个更大的命题里**——人的位置、职业未来、范式迁移、行业结构变化
3. **最后一句是格言式断言**(冷的、留白的、不抒情的)

示例(《浅谈 AI 编程》结尾末句):

> 这不是编程的终结,而是编程从手工业进入 AI 工业化生产之后,人类重新寻找控制点的开始。

升维段的硬约束:

- **禁止抒情、禁止励志、禁止「让我们一起拥抱未来」式收尾**
- **必须落到人/范式/职业层面**,不要只停留在工具层
- **不要写成总结**,不要逐条复述前面的论点——而是把它们重新组织到一个更大的判断里
- 最后一句必须是**单独成段的格言式断言**,15-50 字,不带感叹号

---

## 八、句式参考(节制使用,不是模板套用)

以下是技术思辨型常见的几类句式形态。**它们是参考,不是模板**——同类句式全文用 1-2 次就够,**累计「不是…而是…」家族句式不超过 5-8 处**,超过就是模板腔。

写作时优先用直接陈述,只在论点最需要张力的关键节点动用反差句式。

1. **去伪存真家族**(慎用,全文限 5-8 处合计):
   - 「真正的 X 是 Y」「Y 才是关键」(直接立论,首选)
   - 「不是 X,而是 Y」「不在于 X,在于 Y」(反差句式,节制用)
2. **过去-未来型**:「过去 X,未来 Y」(全文 1-2 次)
3. **定义升维型**:「这就是 X 的真正含义」「这就是 X 思维」(全文 1 次)
4. **断言隔离型**:「X 和 Y 处在不同层级」「X 是一回事,Y 是另一回事」(全文 1-2 次)
5. **反问起手型**:「当 X 时,Y 应该在哪里?」「真的是 X 吗?」(全文 1-3 次)
6. **格言收束型**:「X 不会让 Y 自动变好。」(全文最多 1 次,留给结尾或核心节点)
7. **边界提醒型**:「它的边界要讲清楚」「但 X 也不能被神化」(全文 1-2 次)

**自检**:写完后扫一遍,如果上述任何一种句式在同一篇里出现了 4+ 次,或者两段相邻都用了相似句式,立刻把其中一半改写为直接陈述句。**句式不该被读者察觉**——读者只该察觉到你的判断,而不该察觉到你的套路。

## 九、专项禁区(技术思辨型独有)

### 9.1 导览句全禁

- 「上面我们讨论了……」
- 「接下来让我们看……」
- 「综合来看……」
- 「在前面的章节中……」
- 「下一节将……」
- 「让我先解释一下……」

读者跟得上节奏,不需要被牵着手走。**LLM 写这种导览句是默认动作,要反这个本能**。

### 9.2 复述句严控

刚说过的论点不要在下一段再总结一遍。如果非要钉一次,直接用加粗断言句,**不用「也就是说」「换言之」开头**。

### 9.3 励志收尾全禁

- 「未来已来」
- 「让我们共同见证」
- 「这是最好的时代」
- 「拥抱变化,拥抱未来」
- 「相信未来,相信 AI」

任何带情绪膨胀的收尾句都不能用。技术思辨型的力量来自**冷的判断**,不是热的口号。

### 9.4 「众所周知」「不言而喻」全禁

技术思辨型不预设读者认知。要么不写,要么直接说出来。「众所周知」是回避论证的偷懒。

### 9.5 「值得思考」「发人深省」「引人深思」全禁

这些都是把判断权推给读者的废话。技术思辨型自己做判断,不让读者代劳。

## 十、引用规范(硬要求)

技术思辨型**必须带 [n] 引用列表**(放在正文结束之前)。每个外部观点、官方文档、产品文档、第三方研究都要标 `[n]`。

格式参考:

```
正文中:
Anthropic 在 context engineering[5] 文章里明确指出,context 是有限资源。

文末 References:
[5] **context engineering:** _https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents_
```

引用数量参考:5000-8000 字文章,引用 8-15 条。

**只引一手资料**:官方博客、官方文档、论文、调查报告。不引社交媒体二手解读,不引 KOL 的转述。

## 十一、示范段落对照

### 示范 1:开头三件套

❌ AI 平庸开头:

> 在当今 AI 飞速发展的时代,Agent 已经成为最热门的话题之一。本文将带大家深入了解 Agent 的本质,探讨它如何改变软件工程的未来。

✓ 技术思辨型开头:

> 过去两年,大家总喜欢问"模型能不能写代码"、"能不能替代程序员"、"是不是以后不用学编程了"。
>
> 这些问题当然重要,但它们都停留在表层。
>
> 真正的变化不是 AI 会写多少行代码,而是**代码生产的边际成本正在快速趋近于零**。

落点:第一段抛常见误解,第二段一句话否掉,第三段直接抛核心论断并加粗。

### 示范 2:概念校准段

❌ AI 平庸校准:

> Subagent 和 Handoff 都是 Agent 协作的方式,它们有一些区别,我们来详细看看。

✓ 技术思辨型校准:

> 这和 subagent 不同:
>
> ```
> subagent 是"你去查一块,回来汇报"。
> handoff 是"这个问题之后归你处理"。
> ```

落点:零导览句,直接用伪代码块让概念有形状,两句话讲完。

### 示范 3:段尾断言钉论点

❌ AI 平庸段尾:

> 综上所述,我们可以看到,AI 时代的 code review 正在发生变化,人类应该把更多精力放在风险审查上。

✓ 技术思辨型段尾:

> 这就是从写代码走向治理代码。

落点:零导览词,一句格言式断言,独立成段,加粗。

### 示范 4:升维收尾末句

❌ AI 平庸末句:

> 让我们共同期待 AI 编程的美好未来,拥抱变化,迎接挑战!

✓ 技术思辨型末句(直接断言式,不用「不是 X 而是 Y」):

> 编程在变形。人类要在新的位置上重新找回控制权。

❌ 同等位置的模板腔末句(刻意套「不是…而是…」):

> 这不是编程的终结,而是人类与机器关系的重塑。

落点:升维末句**优先用直接断言**,把判断本身砸下来;**只在论点最需要张力的关键节点才动用「不是 X 而是 Y」**。一篇文章里这种反差末句最多 1 处,不要每节都用。

## 十二、可选工具箱:量化推演与边界条件分析(合并自原架构原理深度型)

技术思辨型合并了原「架构原理深度型」的能力。如果题材本身有规模/性能/成本可量化,可以选择性启用这套工具箱。**启用与否不影响气质判断——气质始终是冷、剥离文学的论证向。**

### 12.1 数量级推演四步

当文章涉及「这个方案在什么规模下成立」时,做一次显式推演:

1. **基础量级**:写出基础指标的数量级(比如 1 万 QPS、100GB 数据、1000 个 agent)
2. **关键操作的代价**:每次操作的延迟/字节/成本
3. **总规模**:基础量级 × 代价 = 总开销
4. **边界**:在什么规模下这套方案失效

示例(假设的写法):

```
1 万 QPS × 单请求 50ms LLM 延迟 = 需要 500 个并发请求处理能力
500 并发 × 8B 模型 50GB 显存 ÷ A100 80GB = 至少 313 张 A100
临界点:QPS > 5 万 时,这套架构成本不再合理,必须降级到 4B 模型或缓存层
```

### 12.2 边界条件分析

每个核心论断,显式写出三类边界:

- **失效边界**:在什么条件下这个论断不成立
- **退化路径**:超出边界时降级方案是什么
- **极端反例**:有没有一个明显反例(承认它,不回避)

### 12.3 机制硬拆(原架构原理深度型继承)

不只是「概念校准」(原 7 的强项),还要做「机制硬拆」(原 6 的强项):

- 把一个抽象机制拆到操作步骤层面("调用什么 API、传什么参数、产生什么副作用")
- 用伪代码 / 时序图 / 状态机表达机制
- 解释清楚每个分支为什么这么设计

### 12.4 启用判断

题材具备以下任一特征时,启用量化推演工具箱:

- 涉及性能、并发、延迟、成本、容量
- 涉及"这套方案能 scale 到哪"
- 涉及"什么规模下应该用 A、什么规模下应该用 B"
- 涉及边界条件、退化方案、降级路径

不具备这些特征的纯概念辨析文(比如「代码是负债,规格是资产」),不启用,保持纯思辨。

**注意**:启用量化推演不改变气质要求——第一人称仍然 1-2 处,文学修饰仍然全程剥离,升维段仍然必须,断言独立成段仍然 ≥20 处。

## 十三、写完前的最后一遍自检(技术思辨型专属)

通读全文,逐项打勾:

- [ ] 核心论断是否**旗帜鲜明、不左右摇摆**?(可以和主流一致,但必须立场清晰、一眼可辨)
- [ ] 抽掉任何一句话,文章意思是否受损?(零废话硬底线——不受损就该删)
- [ ] 每节是否走完了「现象→机制→边界→升维」四步爬阶?
- [ ] 「不是 X,而是 Y」家族句式(含「不在于…在于…」「不再是…而是…」)是否 ≤ 5-8 次?是否两段相邻都用了同一句式?(超过就是模板腔,立刻改写一半为直接陈述)
- [ ] 至少有 1-2 处明确的概念校准段落?
- [ ] 断言独立成段是否 ≥20 处?
- [ ] 每节段尾是否有加粗断言锚点?
- [ ] 伪代码作论证是否 ≥2 处?
- [ ] 升维段是否占全文 10-15%?是否落到人/范式/职业?
- [ ] 最后一句是否是格言式断言、独立成段、无感叹号?
- [ ] 是否带 [n] 引用列表,引用 8-15 条?
- [ ] 是否清干净了导览句、复述句、励志收尾?
- [ ] 第一人称是否 ≤2 处,且只用于立场锚定?
- [ ] 文学修饰是否全程剥离(无名言起手、无文学性收尾)?
- [ ] 通读时是否给人「这人想清楚了」的感觉,而不是「这人在装」?

**最后一条是最重要的味道判断,过不了就回炉。**
