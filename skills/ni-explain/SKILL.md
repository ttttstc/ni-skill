# ni-explain — 讲清楚

> 一句话：**受控语言是手段，不是目标。真目标是读者一次读懂、只有一种理解。**

受控中文（ASD-STE100 精神）只解决**句子级唯一性**——保证不被误读。但「把方案讲给业务方听懂」还需要另外两层：**结构**（结论先行、已知→未知）和**格式**（一段文字讲不清，就换一张图）。三层一起用，才叫讲清楚。

本 skill 治的是**表达**，不治内容。内容本身有没有判断、有没有价值，那是 `ni-tech-report` 的事。分工见下节，边界先立死。

---

## 一、与 ni-tech-report 的边界（硬约束，先读）

`ni-tech-report` 的四层价值——立意（为什么现在 / 三股力量 / 大想法）、姿态（强框架 / 消除需求感）、证据（战绩 / 科研故事）、收束（判断收束）——**全是结构、修辞、判断**。受控语言的杀器（禁比喻成语、单句限长、一句一事）**正好会把这些压平**。

因此：**ni-explain 对「汇报」文体分层适用，只借句子、不碰判断。**

| 规则层 | 技术方案 / 文档 | 汇报 |
|---|---|---|
| 句子清晰层（去包装动词、明确主体、术语一致、标点） | ✅ 全量 | ✅ **只做这层** |
| 单句长度上限 | ✅ 描述 ≤50 字、步骤 ≤40 字 | ⚠️ **框架句豁免**（强框架句可超） |
| 单义连接词 | ✅ | ✅ |
| 9.x 反比喻 / 反成语 | ✅ | ❌ **禁止套用**（会杀掉「三股力量」「大想法」这类框架装置） |
| 结构重排（结论先行 / 换开头） | ✅ 可做 | ❌ **不重排**（保留「为什么现在」开头） |
| 强框架 / 判断收束 / 科研故事 / 大想法 | —（非汇报无此概念） | ❌ **绝对不动** |

**接力方向：**

- **ni-tech-report → ni-explain**：内容已攒好，ni-explain **只打磨句子，交回时结构零改动**。交付报告明写一句「未改动结构与判断」。
- **反向不成立**：ni-explain **不做转交、不指路**。内容层的判断/框架不归它管——它不改写、不评估，也不让用户去别处。它只做句子层，做完就交付。

> ni-tech-report 管「判断立不立得住」，ni-explain 管「这句话读不读得懂」。清晰 ≠ 削平说服。

## 二、四种模式

先分诊，再进模式。

| 模式 | 输入 | 产出 |
|---|---|---|
| **写** write | 材料 / 提纲 | 按规则写出的清晰文本 |
| **改写** rewrite | 现成文本 | 清晰版（**保事实，只改表达**） |
| **审查** review | 现成文本 | 问题清单（哪里会被误读），**不改** |
| **讲解** explain | 一个概念 / 方案 | 选对格式（文字/图/表/HTML/视频脚本）+ 套讲解法，从零讲清楚 |

先判文体：**技术方案 / 汇报 / 文档**。文体决定规则怎么调（尤其汇报走上面的禁区）。

## 三、三层清晰度

### 第 1 层 · 句子级（受控中文，强制）

**这是生成时就必须遵守的硬约束，不是事后检查项。**

#### 3.1 动词受控表（严禁万能动词，必须还原为物理动作）

正文里**不许出现模糊动词**。看到左边的词，改写成右边**可执行、可复现**的具体动作：

| 禁用（模糊，无具体物理过程） | 强制替换（明确物理动作） |
|---|---|
| 进行（如：进行校验） | 校验、解析、比对 |
| 实现（如：实现高可用） | 部署冗余节点、自动切换主从 |
| 通过（如：通过 RPC 获取） | 发起 RPC 请求、读取、拉取 |
| 优化（如：优化查询性能） | 建立索引、限制返回条数、压缩负载 |
| 赋能 / 支撑 / 协同 | 提供接口、存储数据、调用下游 |
| 自动触发（无主句） | [主体服务] 发送事件、定时任务扫描 |

「处理 / 操作 / 支持 / 调整」同理——只说了「做了点事」，要落到具体动作。例外：动作在下一句马上给出时，可先用总称（如「支持三种格式：PNG、JPEG、HEIC」）。

#### 3.2 句法与结构约束（强制）

- **主体显式化**：每个陈述句**必须包含明确的执行主体**（如「API 网关」「消息队列 Worker」），**严禁被动句与无主句**。主体换了就写出来，不能默认省略。
- **单句长度上限**：描述性陈述句 **≤ 50 字**；步骤操作指令 **≤ 40 字**。（汇报的框架句豁免，见第一节。）
- **定语剥离原则**：单句**最多一级修饰语**。超过两重定语时，拆成**前置定义句**或**并列短句**。
  - 反例：`这是一个基于 Raft 共识协议的具备跨机房容灾能力的高可用分布式元数据存储引擎。`
  - 正例：`这是一个元数据存储引擎。引擎使用 Raft 协议达成数据一致。系统支持跨机房容灾部署。`
- **单义连接词**：只允许表**因果 / 时序**的单义连接词——「因此」「如果……则……」「随后」「此时」。**禁用**模棱两可的过渡词——「与此同时」「在此基础上」。

#### 3.3 其余句子规则（一词一义 / 无含糊词 / 代词明确）

- **一个概念只用一个词**：同一事物、同一动作，全文同一个词，不为「读起来有变化」而换说法。
- **不用含糊词**：适当、有关的、一定程度上、较为、基本上、若干、显著、大幅、明显——应写成**数字、名称或条件**。（「性能有显著提升」→「p99 延迟从 120 毫秒降到 45 毫秒」）
- **代词只指一个东西**：「它」「这」「该」「其」只能指上一句里**唯一可能**的那个名词；有两个可能时，写出名字。
- **一句只讲一件事**：第二件事出现时用句号断开；逗号连起来的分句不超过三个。
- **不用四字格 / 成语 / 比喻代替事实**（汇报的框架装置除外，见第一节）。不写「开箱即用」「无缝」「一劳永逸」「赋能」「闭环」——写出具体做了什么、快了多少。

> 完整规则、每条的理由与例子见 `references/rules-zh.md`（九章：词 / 名词短语 / 动词 / 句子 / 步骤 / 说明 / 警告 / 标点长度 / 写作习惯）。

### 第 2 层 · 结构级

- **结论先行**：每段第一句写结论，后面才是原因、数据、例外。读者常常只读每段第一句。
- **一段一主题，不超过 6 句**：第二个主题开始时另起一段。
- **已知 → 未知**：先接读者已经懂的，再引新的；不要一上来甩陌生概念。
- **分清已做和计划**：已做写日期或「已完成」；计划写「将」或放「下一步」小节。

### 第 3 层 · 格式级（Karpathy 格式阶梯）

**当一段文字讲不清时，换载体——这是「讲清楚」最被忽略的一层。**

按「读者一次读懂的难度」从高到低选格式：

| 格式 | 什么时候用 |
|---|---|
| 一段文字 | 线性、无分支、无结构的说明 |
| 列表 / 表格 | 并列项、对照项、参数、选项 |
| 图（架构图 / 流程 / 时序） | **关系、流向、先后**——文字描述拓扑很费力时 |
| HTML 交互页 | 需要读者自己探索、切换、试参数时 |
| 视频脚本（含分镜） | 讲给完全不看文字的人、或概念本身有动态过程时 |

判据：**如果读者要靠脑内重建一张图才能懂，就直接给他图。**

## 四、主流程

```
① 分诊（判文体 + 选模式） → ② 写/改写/讲解（套三层） → ③ 跑 check.py → ④ 自查交付
```

1. **分诊**：一句话问清——这是**技术方案 / 汇报 / 文档**？要**写 / 改写 / 审查 / 讲解**？
2. **执行**：按文体套三层规则。汇报走第一节禁区。
3. **机械检查**（写 / 改写后必跑）：

   ```bash
   python ${SKILL_DIR}/scripts/check.py <你的文件>      # 只检查中文（本 skill 面向中文写作）
   ```

   脚本报出「**该看的地方**」，不是判决。两级读法：
   - **`确定`**：机械可判、几乎不误报（万能动词 `进行`/`加以`、含糊词 `显著`/`大幅`、半角标点、缺空格）——看到就改。
   - **`存疑`**：靠上下文、常见误报（「操作 / 支持」可能是领域术语、「建议」可能是名词、长句有时该长、`的` 密集可能本就该拆）——先判断，是误报就跳过。

   压不动长句时，用 `references/explain-patterns.md` 第四节的「压长句五手法」。
4. **交付**：按 `references/output-template.md` 给出改动清单 + 给作者的话。

## 五、硬规则

- **先立护栏**：动手前读 `references/rules-zh.md` 第 0 节——**同一对象同一名称、条件例外贴对应动作、分清建议/要求/可能、已经清楚就不改**。这四条优先级**高于任何句子规则**。
- **不为简短删原因和边界**：压缩时该留的「为什么」和「到什么程度」一个字不少；本来就没问题的句子原样保留。
- **保事实，只改表达**：改写不篡改事实、数字、结论、条件。缺数据就照原样保留，在交付说明里列给作者，**不编数字**。
- **汇报禁区优先于一切句子规则**：判为汇报时，第一节的禁区覆盖第三节。宁可句子长一点，不许压平判断。
- **不越权、不转交**：内容层的判断/框架不归本 skill 管；它不改判断、不指路，只做表达。
- **不含糊化**：不把确切的说法改成笼统的说法来「显得流畅」。

## 六、验收

交付前自查：

- **主体齐全**：每个陈述句都能说出执行主体，无被动句、无无主句。
- **动词落地**：正文无「进行 / 实现 / 通过 / 优化 / 赋能 / 支撑」这类万能动词。
- **长度达标**：描述句 ≤50 字、步骤 ≤40 字（汇报框架句已豁免并标注）。
- **`check.py` 无硬命中**（或每条遗留都有理由）。
- **护栏达标**：同一对象同名；指代不清处写了对象名；条件 / 例外未被从对应动作旁挪走；建议 / 要求 / 可能未混用；**没有为了变短而改掉本已清楚的句子**，也没有删掉理解所需的原因和边界。
- **汇报场景额外查**：强框架、判断收束、科研故事、大想法——**一处未被削弱**；交付说明写了「未改动结构与判断」。

## 七、降级

| 场景 | 降级路径 |
|------|---------|
| 用户要的其实是说服型文案（软文 / 演讲稿 / 品牌故事） | 明说：受控语言会压平修辞和说服力，问是否仍要按 STE 写；要写就写，但标注「已损失说服节奏」。 |
| 汇报内容本身缺判断 | 停手，说明判断/框架不属本 skill 职责；只做句子层，不替它补判断、不转交。 |
| 改写时原作事实不清 | 不补事实，标出「这里需要你提供真实数据/结论」，由用户填。 |
| 源文本已是小说 / 诗 / 营销长文 | 把规则只用于其中的**技术部分**，其余保持原样。 |

降级时显式标注，让用户知道这是降级结果。
