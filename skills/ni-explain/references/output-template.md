# 交付格式

用**请求所用的语言**写交付。用能回答问题的最小形式。四种模式各一套。

---

## 写 / 改写

交付文档本体（只在用户指定了那个文件、且有版本控制时原地改；否则写一个**同目录、名字清楚**的旁路文件）。然后简报：

```markdown
## 改动
- 适用规则：3.1 ×5、2.1 ×2、1.4 ×3、8.3 通篇   <!-- 按规则计数，不做逐句 diff -->
- check.py：<硬> 硬命中、<软> 软命中；<每条遗留软命中为何保留>

## 给作者
- 缺数据的说法：<说法>（<位置>）——保持原样；请补数字和条件。
- 文中 [待补]：<仅列读者缺了就做不了事的事实，及其位置>
- <规则修不了的内容层问题，如有>
```

没有「给作者」内容时，省略该节。

**汇报场景额外加一句**：`本稿只改句子，未改动结构与判断。`

---

## 审查

硬命中排在前面。**原样引用原句**，给一段可直接粘贴的改写。

```markdown
| 位置 | 规则 | 原文 | 建议 |
|---|---|---|---|
| 第 12 行 | 3.1 硬 | 对输入进行校验 | 校验输入 |
| 第 30 行 | 1.4 硬 | 性能有显著提升 | p99 从 120 毫秒降到 45 毫秒（[待补：测量条件]） |
| 第 45 行 | 3.2 硬 | 请求会被转发到后端 | 网关把请求转发到后端 |
```

结尾一行：硬命中数、软命中数，以及文档是否遵循了项目术语表（找不到术语表就明说）。

**若发现内容层问题**（汇报没有判断框架、文档自相矛盾）：单独一段点出即可；**不转交、不指路**——内容层不属本 skill 职责。

---

## 讲解

从零讲清一个概念 / 方案时，先**选格式**（见 `explain-patterns.md` 第二节格式阶梯），再按下面结构：

```markdown
## 这是什么
<一句话：它属于哪一类，像读者已经懂的什么>

## 一个例子
<一个能跑通的具体例子>

## 一般规律
<从例子归纳出的定义/规律>

## 边界
<它不解决什么、什么时候别用>

## <按需要> 图 / 表 / 代码 / 分镜
<格式阶梯里选中的载体>
```

交付时说明**为什么选这个格式**：「关系是拓扑的，所以配了架构图，而不是三段文字。」

---

## 通用

- 改写**不篡改事实、数字、结论、条件**；缺数据照原样保留，在「给作者」里列，**不编数字**。
- 引用、代码、命令、专有名词、用户原话**保持不动**；结构、标题、链接保留。
- 占位符 `[待补：……]` 只在读者缺了它做不了事时用，**从不放猜测值**。
