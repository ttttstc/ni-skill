# 讲清楚的模式库：结构 · 格式 · 讲解法 · 文体

> 句子级规则（`rules-zh.md`）保证「不被误读」。这份文件管另外两层：**结构**（怎么排）、**格式**（用什么装），以及**从零讲一个概念**时的讲解法。最后给出三种文体怎么微调规则。

---

## 一、结构层：让读者走得顺

四条骨架，按优先级排。

**1. 结论先行。**
每段第一句就是结论，后面才是原因、数据、例外。理由：读者常常只读每段第一句；汇报、邮件、方案尤其如此。
- 弱：「因为 A、B、C，所以我们决定用方案二。」
- 强：「**我们用方案二。** 原因是 A、B、C。」

**2. 一段一个判断，不超过 6 句。**
第二件事出现时另起一段。段首那句结论只能概括一个主题；硬塞两个，结论就塌了。

**3. 已知 → 未知。**
先接读者已经懂的，再引新的。不熟悉的概念第一次出现时，先用一句话把它挂到读者已知的东西上，再展开。
- 弱：「本方案采用 CRDT 做多端同步。」
- 强：「多端各自改同一份数据会冲突（读者已知）。本方案用 CRDT 解决：每个端各自记录改动，合并时不冲突。」

**4. 自顶向下，先地图后街道。**
先说整体有哪几块、它们怎么连，再进任何一块的细节。读者有了地图，细节才有地方放。
- 反模式：一头扎进某个模块的参数，读者不知道它在整体里的位置。

**收尾**：结尾把前面的判断收束成一句明确的话，**不要停在「以上，供参考」**（汇报的收束另见 ni-tech-report）。

## 二、格式阶梯：文字讲不清就换载体

这是「讲清楚」最常被忽略的一层。**同一件事，换个载体，读者读懂的难度天差地别。**

按「读者一次读懂的难度」从高到低排：

| 载体 | 适合什么 | 什么时候该降级到它 |
|---|---|---|
| 一段文字 | 线性、无分支、无结构的说明 | — |
| 列表 / 表格 | 并列项、对照项、参数、选项 | 出现三项以上并列，或要对照两个东西 |
| 图（架构 / 流程 / 时序 / 状态） | **关系、流向、先后、拓扑** | 读者要靠脑内重建一张图才能懂 → **直接给他图** |
| HTML 交互页 | 读者需要自己探索、切换、试参数 | 要展示「不同输入下的不同结果」，或内容分层可折叠 |
| 视频脚本（含分镜） | 讲给完全不看文字的人，或概念本身有动态过程 | 目标受众不会读长文，或过程有先后动效 |

**判据一句话**：**如果读者要在大脑里运行一遍才能懂，就换个能直接看的载体。**

常见误用：把一张架构图写成三段文字（读者读完更糊涂）；把并列参数塞进长句（读者要数逗号）。**关系用图，并列用表，步骤用列表，单线说明才用段落。**

## 三、概念讲解法：从「没听过」到「懂了」

讲一个陌生概念，比改写一段文字更激进——你要在读者脑里从零搭模型。四步：

**1. 先定位：这是「什么东西」的哪一类？**
开口先给坐标——它属于读者已知的哪个大类，和哪个熟悉的东西同族。
- 例：「消息队列，你可以先理解成一个**只会往里塞、按顺序往外取的传送带**。」
- 目的：让新概念挂到旧概念上，而不是悬空。

**2. 用一个具体例子开路，再上抽象定义。**
先给一个能跑通的例子，再回头说一般规律。人从例子归纳比从定义演绎快得多。
- 反模式：先背定义、再举例——读者读定义时没有锚点。

**3. 类比要标「像到哪里」。**
类比是脚手架：帮读者建立起初印象，但一定**紧跟一句把类比按住**——它在哪里不成立。
- 例：「像传送带——但队列有个传送带没有的性质：取走一条，后面自动前移，所以你不用管位置。」
- 记住了：**类比后面不跟事实修正 = 埋雷。**

**4. 给边界，不只给定义。**
说清它**不解决什么**、什么时候**不该用**。只讲「能做什么」的讲解，读者一用就踩坑。

**讲完的自检**：合上你的讲解，让读者复述——他能否说清「这是什么、什么时候用、什么时候别用」？说不出，回哪步补哪步。

## 四、把长句压下来：五个手法

规则说「描述句 ≤50 字、步骤 ≤40 字」，但没教你**怎么压**。密句压不动，多半是没夹对地方。五个手法，从易到难：

1. **砍包装**：`对 X 进行 Y` → `Y X`。`对日志进行压缩` → `压缩日志`；`实现了对 H3 的支持` → `支持 H3`。一句能砍掉四到六字。
2. **换主语就断句**：一句里出现第二个主语（动作者换了人、换了部件），立刻断成两句。`网关把请求转发到后端，后端查完缓存再回源` → `网关把请求转发到后端。后端查完缓存，再回源。`
3. **从句外置**：把「因为……所以……」「如果……就……」的从句提成独立句，或降成前置条件句。`由于迁移脚本可能失败所以升级前要先备份然后停服务` → `升级前先备份。迁移脚本可能失败。`
4. **甩修饰**：名词前修饰超过一层，拆成前置定义句。`基于 Raft 的跨机房高可用元数据引擎` → `这是个元数据引擎。它用 Raft 达成一致，支持跨机房容灾。`（rules 2.1）
5. **并列出表**：三项以上并列、或各项自带说明，改成列表 / 表格——列表项不受单句长度限制。

**判断句该不该断**：读一遍，问「这句里有没有两个动作、两个主语、或一个『因为』」。有 → 断。都没有却还长（例如逐项列举）→ 那是列表的活，不是断句。

## 五、三种文体的规则微调

同一套句子规则，三种文体侧重点不同。

### 技术方案 / 设计文档
- **句子规则**：全量适用（这是受控中文的舒适区）。
- **结构**：约束 → 取舍 → 决策。先说约束条件（不能违反什么），再说候选方案与取舍（为什么选它不选别的），最后给决策。
- **格式**：架构/流程用图，方案对比用表。重点：**把「为什么这么选」写清**，而不只是「选了什么」。

### 业务 / 技术汇报 ⚠️
- **句子规则**：**只适用** 3.1 动词受控、3.2 主体显式化、1.1–1.4 用词、8.x 标点。
- **豁免**：9.4 反比喻成语（框架装置要用）、单句长度上限（框架句可超）、结构重排（不重排）。
- **禁区**：立意 / 姿态 / 证据 / 收束四层**一个字不动**——那是 ni-tech-report 的财产。见 SKILL.md 第一节。
- **一句话**：ni-explain 在汇报上**只借句子、不碰判断**。

### 技术文档（README / 手册 / 运维）
- **句子规则**：全量适用。
- **结构**：步骤 + 参考。操作走编号步骤（见 rules 第 5 章），参考信息（参数、错误码）走表格。
- **格式**：操作步骤用列表，参数用表，拓扑用图，危险操作用警告块（第 7 章）。
