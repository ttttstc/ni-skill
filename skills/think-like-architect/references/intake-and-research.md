# 信息充分性与项目调研

## 目的

只获取足以支持首层架构决策的证据。不要把调研变成代码库全景考古，也不要下钻实现方案。

## 充分性检查

| 维度 | 最低充分证据 | 阻塞信号 |
|---|---|---|
| 目标与价值 | 明确用户、问题、预期业务结果 | 只能复述功能列表 |
| 成功标准 | 至少一个业务结果和关键验收信号 | “做完上线”就是全部标准 |
| 范围 | 系统边界、主要参与者、非目标 | 新旧系统责任不清 |
| 当前状态 | 现有能力、主要约束、关键上下游 | 把存量系统当绿地设计 |
| 驱动力 | 能排出 3–5 个优先项 | 所有质量属性都同等重要 |
| 数据与安全 | 数据所有者、敏感级别、信任边界 | 不知道谁能读写关键数据 |
| 交付现实 | 团队、时间、预算、运维能力 | 方案可能超出组织承载能力 |
| 验收 | 能说明架构判断如何被验证 | 只能凭主观评价验收 |

缺失内容只有可能改变首层边界或高价值决策时才阻塞。否则记录为待详细设计确认。

## 已授权项目内的最小检查顺序

按证据价值检查，不做无边界遍历：

1. README、架构文档、ADR、设计说明和项目约束文件；
2. 顶层目录、构建清单、服务或模块入口；
3. 部署、基础设施和运行配置；
4. 数据存储、消息、外部 API 和身份认证配置；
5. 与当前需求直接相关的模块、测试和调用边界。

每次扩大检查范围前，回答：它将关闭哪个首层 Unknown？无法回答就停止扩大。

## 调研触发判断

满足任一条件且答案不在已授权项目中时，提出调研：

- 关键业务规模、增长、延迟或恢复目标未知；
- 数据法规、分类、驻留或访问规则未知；
- 外部平台能力、限制、SLA 或长期契约未知；
- 当前生产瓶颈、故障模式或容量证据缺失；
- build/buy 决策缺少市场或供应商事实；
- 跨团队所有权和交付能力无法从项目确定。

不要为了确认具体框架、库版本、接口字段或表结构而启动首层调研。

## 调研提案模板

```markdown
## 首层架构调研提案

- 待关闭决策：{哪个首层决策缺少证据}
- 当前缺口：{已知什么、缺什么}
- 拟获取信息：{具体事实或指标}
- 来源与访问范围：{项目外文档、外部官网、指标、日志、访谈等}
- 明确不做：{实现细节、无关模块、生产变更等}
- 预期产出：{调研完成后能确定或排除什么}
- 权限/风险：{外部访问、敏感数据、账号、成本；无则写“无”}

是否授权我按以上范围开始调研？
```

输出后停止。用户没有明确同意时，不启动新来源访问。

## 访谈问题选择

优先级从高到低：

1. 会改变业务或系统边界；
2. 会改变数据、安全或合规策略；
3. 会改变最重要质量属性及其优先级；
4. 会改变团队所有权或交付路径；
5. 会改变验收标准。

每轮最多问 3 个。每个问题附一句“该答案将影响什么决策”。不要询问可以延迟的问题。

## 调研结果回流

调研完成后只回填：

- 新确认事实及来源；
- 被推翻的假设；
- 已关闭和仍阻塞的 Unknown；
- 因证据变化而改变的驱动力或候选决策。

仍有阻塞 Unknown 时继续门禁，不直接输出正式方案。
