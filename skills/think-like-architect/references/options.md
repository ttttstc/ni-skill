# 结构性方案分歧

## 何时生成多个选项

只在以下条件同时成立时生成 2–3 个选项：

- 事项已经被判定为高价值首层决策；
- 存在两个以上现实可行方向；
- 不同方向会产生实质性架构代价。

只有一个方向满足硬约束时，说明排除理由并直接选择，不制造陪跑方案。

## 生成不同取舍立场

按实际驱动力选择，不强行凑齐：

- 最小复杂度：最少运行单元、最少跨边界协调、最快获得价值；
- 关键质量属性优先：为最重要的可靠性、性能、安全或隔离目标承担复杂度；
- 演进与可选性优先：在高不确定且未来改变昂贵处保留替换或拆分路径；
- 购买/复用优先：把非差异化能力交给成熟产品或平台；
- 自建核心能力：只为真正差异化且外部方案无法满足的部分承担建设成本。

## 结构差异门禁

两个选项至少在以下一项上不同，否则合并为一个：

- 业务或系统边界；
- 部署和故障隔离边界；
- 数据所有权或一致性模型；
- 同步、异步或批处理关系；
- build/buy；
- 团队所有权和交互方式；
- 迁移与回滚路径。

更换编程语言、云厂商、中间件品牌或框架通常不构成架构选项，除非它直接改变驱动力、契约、成本或可逆性。

## 统一比较格式

```markdown
| 选项 | 如何满足驱动力 | 主要收益 | 主要代价 | 最差的一面 | 失败条件 | 可逆性 |
|---|---|---|---|---|---|---|
| A | ... | ... | ... | ... | ... | 高/中/低 |
| B | ... | ... | ... | ... | ... | 高/中/低 |
```

比较时使用同一组驱动力，不为偏爱的方案临时增加评价标准。

## 选择规则

1. 先淘汰违反硬约束的选项；
2. 再比较对 P0 驱动力的满足程度；
3. 选择团队能够持续运行的最小复杂度；
4. 高不确定且难逆时，优先降低不可逆性；
5. 写清接受的代价和复审触发条件。

不要输出“各有优劣，视情况而定”。必须给出当前约束下的选择，或明确说明缺少哪项证据导致暂缓。
