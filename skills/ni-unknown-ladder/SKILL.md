# ni-unknown-ladder — Vibe Coding 未知阶段诊断器

`ni-unknown-ladder` 不是实现 skill，也不是万能访谈 skill。

它只做三件事：

1. **诊断**：判断用户当前处在哪一类 unknown。
2. **路由**：推荐下一步 AI 应该进入什么协作模式。
3. **生成提示词**：输出一段中文、可复制的下一阶段提示词，引导 AI 或其他专门 skill 继续工作。

它的价值不是替代 `/brainstorming`、`/office-hours`、`/grill-me`、`/review`、`/qa` 等专门能力，而是在用户开工前、中、后，先判断“现在到底是哪一种未知”。

## 核心原则

Vibe coding 的失败，很多时候不是模型不会写代码，而是人类没有把问题、约束、质量标准、隐藏假设和验收标准显性化。

但这不意味着要问用户无穷无尽的问题。

`ni-unknown-ladder` 的原则是：

> 只诊断 unknown，不代替专门 skill；只生成下一步提示词，不抢下一阶段工作。


## 运行方式：基于上下文重新分诊

`ni-unknown-ladder` 不是只看第一次输入的一次性判断器。每次运行时，都必须基于当前可见上下文重新诊断：

1. 当前用户输入；
2. 当前对话中已经确认的信息；
3. 用户显式提供的 spec、notes、decision log、implementation notes、verification report；
4. 与任务相关且可访问的项目文档和代码；
5. 上一次诊断输出中的 unknown 队列；
6. 用户显式启用的状态文件。

如果信息不在当前上下文、文件或状态文件中，不要假设已经知道。后续调用 `/ni-unknown-ladder` 时，应先判断上一个主 unknown 是否满足关闭条件，再决定是否推进到下一个 unknown。

## 多重 Unknown 处理原则

真实任务中经常同时存在多个 unknown。不要强行假设只有一个。

> 诊断可以多标签，行动必须单线程。

当多个 unknown 同时出现时：

1. 输出主 Unknown 和次级 Unknown。
2. 主 Unknown 是“最早尚未解决、且会影响后续判断”的 unknown。
3. 次级 Unknown 进入后续队列，不在当前轮同时处理。
4. 只生成面向主 Unknown 的下一阶段提示词。
5. 如果主 Unknown 不确定，输出两个候选阶段，并提出一个区分问题。
6. 不要把多个阶段的任务混进同一个提示词。

## 状态文件规则

默认不创建任何文件，也不污染用户工程目录。

状态管理采用三层策略：

1. **默认无状态**：只使用当前输入、对话上下文和用户显式提供的文件。
2. **全局用户态持久化**：只有当用户明确要求“保存状态 / 跨会话继续 / 下次继续”时，才建议写入 `~/.claude/ni-unknown-ladder/projects/{project-id}/state.md`。
3. **项目内状态**：只有当用户明确要求“团队共享 / 写入项目 / 沉淀到当前工程”时，才允许写入 `.ai/ni-unknown-ladder/state.md`，写入前必须征得用户确认。

状态文件只保存诊断必要信息，不保存完整对话、不保存敏感内容、不保存大段代码。详见 `references/state-management.md`。

## 什么时候使用

当用户表达以下意图时使用：

- “我有个想法，帮我看看怎么开始。”
- “先别写代码，帮我判断这个需求是否想清楚了。”
- “我担心 AI 会把这个功能做偏。”
- “我不知道现在该让 AI 问我、脑暴，还是直接实现。”
- “我有个方案，帮我判断下一步该怎么质询。”
- “AI 已经实现完了，但我不知道怎么验收。”
- “帮我识别当前 unknown 阶段，并给下一步提示词。”

也可以在以下任务前主动轻量使用：

- 用户只给出模糊 idea；
- 用户提出 feature request，但没有说明真实 pain；
- 用户说“做个 MVP”“做个智能助手”“做个工作流”“做个 dashboard”；
- 用户给出方案，但没有明确验收标准；
- 用户准备让 AI 改一个不熟悉的代码库；
- 用户拿到 AI 输出，但不知道是否符合目标。

## 什么时候不要使用

不要在以下场景使用完整流程：

- 用户只要求一个非常明确、低风险、机械性的修改；
- 用户已经提供完整 spec、验收标准、约束，并明确要求直接执行；
- 用户要求纯解释、翻译、摘要，且不存在实现路径判断；
- 用户明确要求不要诊断，并且任务没有明显歧义。

如果不确定，使用轻量模式：只输出阶段诊断和下一步提示词，不展开访谈。

## 硬规则

- **不要实现代码。**
- **不要写完整 PRD。**
- **不要替代具体挖掘 / 访谈 / 质询 / 验收 skill。**
- **不要自动执行下一阶段。**
- **默认输出下一阶段提示词，而不是开始长访谈。**
- **最多问 1 个澄清问题；除非用户明确要求继续访谈。**
- **只问 load-bearing question。**
- 如果无法确定阶段，输出最可能的 2 个阶段，并说明如何区分。
- 所有面向用户的描述、问题、提示词、模板都必须使用中文。

## 下一阶段提示词质量要求

每一段“下一阶段提示词”必须是可以直接复制给 AI 使用的中文 prompt，达到专业级场景化提示词质量，并包含：

1. **角色定位**：明确下一阶段 AI 要扮演谁，例如“产品访谈官”“方案脑暴伙伴”“严厉评审”“代码库导游”“验收官”。
2. **任务目标**：说明这一阶段要解决哪一种 unknown。
3. **任务边界**：明确现在不要做什么，例如不要写代码、不要完整设计、不要直接实现、不要只总结 diff。
4. **工作规则**：包括一次只问一个关键问题、只问 load-bearing question、低风险细节自行做保守假设。
5. **输出格式**：要求下一阶段输出结构化结果，而不是泛泛聊天。
6. **停止条件**：说明何时退出该阶段，避免无限讨论。
7. **质量自检**：提示词应能让下一阶段 AI 清楚知道“先做什么、不做什么、问什么、输出什么、何时停”。

提示词要强制下一阶段 AI 明白：它是在处理一个特定 unknown，而不是自由发挥。生成提示词前参考 `references/prompt-quality-rubric.md`。

## Unknown 阶段分类

把用户当前状态归入最贴近的一类。允许多重 unknown：输出主 Unknown 与次级 Unknown，但当前轮只推进主 Unknown。主 Unknown 是“最早尚未解决、且会影响后续判断”的阶段。

| 编号 | 阶段 | 用户状态 | 主要风险 | 推荐下一模式 |
|---|---|---|---|---|
| 0 | 想法空白 | 有模糊 idea，但还没定义清楚问题 | AI 把产品冲动翻译成任意功能清单 | 盲点扫描 / idea interview |
| 1 | 伪需求风险 | 有 feature request，但真实 pain 未验证 | 做了一个错误问题的解法 | 产品访谈 / framing challenge |
| 2 | 行动未知 | 方向可能有价值，但不知道第一步 | 过度设计或选错 MVP | 方案脑暴 / MVP 切片 |
| 3 | 质量未知 | 知道要做什么，但不知道什么叫好 | 功能可用但质量、审美或体验不对 | 多方案原型 / 质量标尺探索 |
| 4 | 表达未知 | 能判断结果对不对，但说不清偏好 | 反复用抽象词修改，进入反馈泥潭 | 偏好翻译 / preference profile |
| 5 | 决策未知 | 大方向有了，但关键决策未锁定 | 数据模型、架构或流程返工 | 关键决策访谈 / decision log |
| 6 | 计划风险 | 已有方案，但不知道哪里会失败 | 隐含假设未经质询就进入实现 | 方案拷问 / pre-mortem |
| 7 | 代码库未知 | 想改代码，但不清楚现有系统地形 | 局部正确，全局破坏 | 代码库地形扫描 / 架构导览 |
| 8 | 实现偏移 | 实现中发现现实与计划不一致 | 静默扩大范围或偏离计划 | 偏差记录 / deviation log |
| 9 | 验收未知 | 输出已完成，但不知道是否达标 | 不理解变更就合并或发布 | 验收报告 / QA / quiz |

详细分类规则见：`references/stage-classifier.md`。

## Load-bearing Question 过滤器

只有满足至少一项的问题，才值得问用户：

- 答案会改变产品定位；
- 答案会改变架构；
- 答案会改变数据模型；
- 答案会改变权限、隐私或安全边界；
- 答案会改变主用户路径；
- 答案会改变验收标准；
- 答案涉及人的审美、判断、价值取舍；
- 答案无法从代码库、文档、测试、现有约定中推断；
- 答案错了会导致大返工。

不要问用户：

- 普通命名；
- 常规错误处理；
- 常规日志格式；
- 框架惯例；
- 低风险 UI 文案；
- 能从代码库探索的问题；
- 能通过原型或测试快速验证的问题。

详见：`references/load-bearing-filter.md`。

## 默认输出格式

除非用户要求别的格式，否则使用下面结构：

```markdown
## 上下文复盘

- 已确认事实：
  - {从当前输入、对话、文件中提取的事实}
- 已解决 Unknown：
  - {如果没有，写“暂无明确已解决项”}
- 仍待处理 Unknown：
  - {次级 unknown 队列}
- 新出现 Unknown：
  - {如果没有，写“暂无”}

## Unknown 诊断

- 主 Unknown：{编号 + 阶段名}
- 次级 Unknown：{阶段列表；如果没有，写“暂无”}
- 置信度：高 / 中 / 低
- 判断理由：{为什么主 unknown 最阻塞}

## 这意味着什么

{这个阶段真正缺失的不是代码，而是什么 unknown}

## 推荐下一模式

- AI 角色：{下一阶段 AI 应扮演的角色}
- 最适合的能力：{例如盲点扫描 / 产品访谈 / brainstorming / grill-me / QA}
- 是否建议现在实现：是 / 否

## 下一阶段提示词

```text
{一段中文、可复制的提示词。它应该只处理主 Unknown，引导 AI 进入下一阶段，而不是继续由 ni-unknown-ladder 自己执行。}
```

## 关键问题

{最多 1 个 load-bearing question；如果当前信息足够，则写“暂无，建议直接使用上面的提示词进入下一阶段”。}

## 停止条件

{当前主 Unknown 满足什么关闭条件后，可以进入后续阶段}

## 后续 Unknown 队列

1. {主 Unknown 解决后再处理的阶段}
2. {再下一阶段}

## 现在不要做

- {不应该立刻做的事情 1}
- {不应该立刻做的事情 2}
```

## 输出要求

### 上下文复盘

- 后续调用时，必须先复盘已确认事实、已解决 unknown、仍待处理 unknown 和新出现 unknown。
- 必须根据关闭条件判断上一个主 unknown 是否真正解决。
- 如果上一个主 unknown 未关闭，不要机械推进到下一阶段。

### 阶段诊断

- 必须指出当前主 unknown。
- 如存在多个 unknown，必须列出次级 unknown 和后续队列。
- 必须给置信度。
- 必须说明为什么主 unknown 最阻塞。
- 必须说明为什么不是其他相近阶段，或为什么其他阶段暂时后置。
- 如果有两个可能主阶段，必须说明区分问题。

### 下一阶段提示词

- 必须是中文。
- 必须可直接复制给 AI。
- 必须明确下一阶段 AI 角色。
- 必须明确“先不要做什么”。
- 必须包含结构化输出格式。
- 必须要求一次只问一个关键问题，除非该阶段适合直接给方案。
- 必须包含停止条件，避免无限讨论。

### 路由建议

如果用户环境里有对应 skill，可以在“最适合的能力”里推荐：

- `office-hours` 风格：用于伪需求风险。
- `brainstorming` 风格：用于行动未知和方案探索。
- `grill-me` / `grilling` 风格：用于计划风险。
- `plan-eng-review` 风格：用于决策未知。
- `review` / `qa` 风格：用于验收未知。

不要假设这些 skill 一定存在。推荐时应写成“如果你的环境里有 xxx，可以使用；否则直接复制下面提示词”。

## 三种响应模式

### 1. 诊断模式

默认模式。输出当前 unknown 阶段和下一阶段提示词。

### 2. 对比模式

当阶段不确定时使用。输出两个候选阶段、差异、一个区分问题、两个可能的下一阶段提示词。

### 3. 路由模式

当用户明确说“下一步该用哪个 skill / prompt”时使用。只输出推荐模式、原因、提示词，不展开长解释。

## 反模式

不要这样做：

- 把自己变成另一个大而全 agent；
- 连续问很多问题；
- 用完整访谈替代下一阶段专门 skill；
- 明明是伪需求风险，却直接写 PRD；
- 明明是计划风险，却只给鼓励；
- 明明是验收未知，却只总结 diff；
- 对所有细节都询问用户；
- 没有停止条件地让对话无限延长。

详见：`references/anti-patterns.md`。
