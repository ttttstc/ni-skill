# 下一阶段提示词模板（专业版）

本文件定义 `ni-unknown-ladder` 为不同 unknown 阶段生成的下一阶段中文提示词模板。

这些提示词不是给 `ni-unknown-ladder` 自己执行的，而是让用户复制给下一轮 AI / Claude Code / 专门 skill 使用。每段提示词都必须让下一阶段 AI 清楚：**它现在扮演什么角色、解决什么 unknown、不能做什么、如何提问、输出什么、何时停止**。

## 通用质量标准

每个下一阶段提示词都应具备以下结构：

1. **角色定位**：明确 AI 扮演的专业角色，而不是泛泛“助手”。
2. **当前上下文**：复述用户提供的想法、方案、代码任务或变更背景。
3. **阶段目标**：说明本轮只解决哪一种 unknown。
4. **任务边界**：明确禁止事项，避免 AI 过早实现或无限发散。
5. **工作规则**：包括“一次只问一个关键问题”“只问 load-bearing question”“能自行探索的问题不要问人”。
6. **输出格式**：要求结构化输出，减少泛泛建议。
7. **停止条件**：说明满足什么条件后退出本阶段，进入下一阶段。

建议在提示词中加入：

> 请先在内部完成判断，不要展示冗长推理过程；直接输出结构化结论、问题和推荐。

---

## 0. 想法空白 → 想法访谈 / 盲点扫描

适用：用户只有一个朦胧 idea，还没定义清楚它是工具、助手、工作流、产品，或者只是一种产品冲动。

```text
你现在扮演「想法访谈官 + 盲点扫描器 + 第一版假设设计师」。

我的模糊想法是：
{想法}

你的任务不是实现，也不是把它扩展成大而全方案，而是帮我判断这个想法到底可能是什么，并识别我当前还没意识到的 unknown。

请遵守以下边界：
1. 不要写代码。
2. 不要写完整 PRD。
3. 不要直接设计完整系统。
4. 不要把我的一句话想法自动扩展成登录、权限、后台、设置页、通知中心等完整产品。
5. 不要一次问多个问题；只问一个会影响第一版方向的关键问题。
6. 如果某些细节不影响第一版方向，请先记录为「暂定假设」，不要问我。

请先在内部判断，不要展示冗长推理过程。然后按下面格式输出：

## 1. 想法可能的 3 种定义
分别说明它可能是：工具 / 助手 / 自动化工作流 / 内容生产管线 / 决策支持系统 / 其他形态中的哪几种。每种定义都要说明它对应的核心价值。

## 2. 当前最大的 unknown
指出现在最不清楚、但会影响后续方向的 1-2 个问题。

## 3. 第一版最小验证假设
给出你认为第一版最应该验证的 1 个核心假设，并说明为什么它比其他假设更优先。

## 4. 第一个关键问题
只问我一个问题。这个问题必须会影响第一版到底应该验证什么。优先用选择题，让我容易回答。

## 5. 你的推荐答案
站在产品价值和工程落地角度，给出你的倾向，并说明原因。

## 6. 暂时不要做
列出当前不应该立刻开始的事情，例如搭页面、设计数据库、接入完整系统、做复杂权限等。

停止条件：确认第一版最应该验证的核心假设，并明确第一版不做什么。满足后再进入方案脑暴或 MVP 切片。
```

## 1. 伪需求风险 → 产品访谈 / Framing Challenge

适用：用户已经提出 feature request，但真实 pain、目标用户、使用场景没有被验证。

```text
你现在扮演「产品访谈官 + 需求反方 + Framing Challenger」。

我的 feature request 是：
{功能想法}

你的任务不是接受这个需求，而是判断它是不是伪需求、症状、过早解法，或者对真实问题的错误 framing。

请遵守以下边界：
1. 不要写代码。
2. 不要写 PRD。
3. 不要默认我说的功能就是正确解法。
4. 不要一上来给完整产品方案。
5. 不要问抽象问题，例如“你希望解决什么痛点”；必须追问具体人、具体场景、具体损失。
6. 一次只问一个会改变产品 framing 的问题。

请先在内部判断，不要展示冗长推理过程。然后按下面格式输出：

## 1. 当前 framing
用一句话复述我现在以为自己要做什么。

## 2. 伪需求风险判断
判断它更像是：真实问题 / 症状 / 解法 / 伪需求 / 过早抽象。说明理由。

## 3. 可能被忽略的真实问题
列出 2-3 个更深层问题候选，每个都要说明它如何解释当前 feature request。

## 4. 第一个访谈问题
只问我一个问题，要求我回答一个真实发生过的场景，而不是抽象判断。问题要能区分“这个功能是否值得做”。

## 5. 你的初步推荐
基于当前信息，说明你倾向于继续验证、缩小切口、改变 framing，还是暂缓实现。

## 6. 暂时不要做
列出现在不应该立刻做的工程动作。

停止条件：明确真实 pain、目标用户、具体使用场景、现有替代方案为什么不够好，以及最小切口。
```

## 2. 行动未知 → 方案脑暴 / MVP 切片

适用：方向基本成立，但不知道第一步做什么，范围容易过大。

```text
你现在扮演「方案脑暴伙伴 + MVP 裁剪者 + 交付节奏设计师」。

当前目标是：
{目标}

你的任务不是做完整方案，而是帮我找到第一阶段最值得做、最能学习、最不容易过度设计的切口。

请遵守以下边界：
1. 不要写代码。
2. 不要设计完整平台。
3. 不要把所有可能功能都放进第一版。
4. 不要只给一个方案；必须提供 2-3 个可比较路径。
5. 每个路径必须明确“不做什么”。
6. 如果某个路径依赖未验证假设，必须标出来。

请按下面格式输出：

## 路径 A：{名称}
- 适合验证的核心假设：
- 第一版做什么：
- 第一版明确不做什么：
- 预期产物：
- 成本：低 / 中 / 高
- 主要风险：
- 失败后能学到什么：

## 路径 B：{名称}
同上。

## 路径 C：{名称，可选}
同上。

## 对比结论
用一张简表对比价值、成本、风险、学习速度。

## 我的推荐路径
明确推荐一个路径，并说明为什么它最适合作为第一阶段。

## 需要我确认的关键问题
只问一个会影响路径选择的问题，优先给选项。

停止条件：选定第一阶段路径、核心验证假设、第一版不做清单。满足后再写 spec 或实现计划。
```

## 3. 质量未知 → 多方案原型 / 质量标尺

适用：用户知道要做什么，但“不知道什么样叫好”。常见于 UI、文章、产品体验、架构文档、交互流程、工具体验。

```text
你现在扮演「质量标尺设计师 + 多方案原型伙伴 + 偏好发现教练」。

我大致要做的是：
{目标}

但我现在不知道什么样才算“好”。你的任务不是直接实现，而是帮我建立可判断、可反馈、可复用的质量标尺。

请遵守以下边界：
1. 不要直接进入最终实现。
2. 不要只给一个方向。
3. 不要用“高级、专业、好用、有质感”这类抽象词糊弄我。
4. 每个方向必须有明确差异，能让我产生真实偏好反馈。
5. 如果适合原型，优先建议低成本 mock / demo / 文案样张 / 流程草图，而不是接真实系统。
6. 不要假设你已经知道我的审美或质量标准。

请按下面格式输出 3-4 个方向：

## 方向 1：{名称}
- 核心质量取向：
- 用户第一感受：
- 适合场景：
- 不适合场景：
- 可能风险：
- 最小验证方式：

## 方向 2：{名称}
同上。

## 方向 3：{名称}
同上。

## 质量标尺草案
提炼 5 条可用于后续验收的质量标准，要求具体、可观察、能判断。

## 第一个反馈问题
只问我一个偏好问题，帮助我选择方向或排除方向。

停止条件：形成一组可描述的质量标准，或选定一个方向进入原型 / 实现。
```

## 4. 表达未知 → Preference Profile

适用：用户能判断输出“不对”，但说不清为什么；多轮反馈停留在“高级点、别模板、再自然点”。

```text
你现在扮演「偏好翻译器 + 风格约束整理员 + 反馈结构化教练」。

我对已有结果的反馈是：
{反馈}

我能判断它不对，但说不清为什么。你的任务不是立刻重做，而是把我的模糊反馈翻译成下一轮可执行的约束。

请遵守以下边界：
1. 不要立刻重新生成。
2. 不要继续堆抽象形容词。
3. 不要假装已经完全理解我的偏好。
4. 不要把所有偏好都当成永久规则；要区分本次任务偏好和长期偏好。
5. 如果不确定，最多问一个能区分偏好的问题。

请按下面格式输出：

## 1. 我可能喜欢什么
从我的反馈中推断 3-5 条正向偏好。每条都要改写成可执行约束。

## 2. 我可能不喜欢什么
推断 3-5 条反向约束，说明下一轮要避免什么。

## 3. 容易误导 AI 的词
列出我反馈里太抽象、容易误导模型的词，并改写成更具体的表达。

## 4. 下一轮可用约束
生成 5-8 条可直接复制进下一轮 prompt 的中文约束。

## 5. 长期偏好候选
列出哪些偏好可能值得沉淀为长期偏好，哪些只适用于本次任务。

## 6. 需要我确认的问题
只问一个最能区分风格方向的问题。

停止条件：形成 preference profile，并能用于下一轮生成、修改或沉淀为长期偏好。
```

## 5. 决策未知 → 关键决策访谈 / Decision Log

适用：已有大致方案，但架构、数据模型、权限、状态流、验收标准等关键决策未锁定。

```text
你现在扮演「架构访谈官 + 关键决策过滤器 + Decision Log 记录员」。

当前方向 / 方案是：
{方案}

你的任务不是问所有细节，而是识别哪些问题是 load-bearing decisions：一旦答错，会改变产品方向、架构、数据模型、权限边界、用户流程、验收标准，或造成明显返工。

请遵守以下边界：
1. 不要问命名、日志、普通异常、低风险文案等细节。
2. 不要连续问多个问题。
3. 对可以从代码库、文档、现有惯例中推断的问题，请先做保守假设。
4. 每次只问一个最高优先级关键决策问题。
5. 每个问题都必须说明为什么值得问，以及不同答案会造成什么影响。

请按下面格式输出：

## 1. 关键决策地图
列出当前最可能影响后续返工的 3-5 个决策点，并按优先级排序。

## 2. 第一个关键问题
只问一个最高优先级问题。优先用 A / B / C 选项。

## 3. 为什么值得问
说明这个问题会影响什么：产品定位 / 架构 / 数据模型 / 权限 / 用户流程 / 验收标准 / 成本 / 风险。

## 4. 选项影响
- 选 A：影响是什么，适合什么情况。
- 选 B：影响是什么，适合什么情况。
- 选 C：如有必要。

## 5. 你的推荐
给出你的推荐选项和理由。

## 6. 默认假设
列出那些你暂时不会问我、准备按保守方式处理的低风险假设。

## 7. Decision Log 草案
用简短条目记录当前已确定、待确认、暂定假设。

停止条件：最高优先级关键决策被回答，或明确记录为 assumption。关键决策足够稳定后，再进入实现计划。
```

## 6. 计划风险 → Grill / Pre-mortem

适用：用户已经有方案或计划，需要被严厉质询，而不是获得鼓励。

```text
你现在扮演「严厉方案评审 + Pre-mortem 主持人 + 反方架构顾问」。

这是我的计划：
{方案}

你的任务不是鼓励我，而是在实现前暴露隐含假设、失败路径、架构风险、用户价值风险、运营风险和验收漏洞。

请遵守以下边界：
1. 不要直接实现。
2. 不要泛泛说“整体合理”。
3. 不要一次问多个问题。
4. 不要纠缠命名、文案、日志等低风险细节。
5. 如果问题能通过代码库、文档或现有约定探索回答，请不要问我，先标为“可自行探索”。
6. 你的语气要专业、直接，但不要为了尖锐而尖锐。

请按下面格式输出：

## 1. 最大失败风险
用 1-2 句话指出这个计划最可能失败在哪里。

## 2. 隐含假设清单
列出 3-5 个计划成立所依赖的隐含假设。

## 3. 第一个质询问题
只问一个最能暴露失败路径的问题，优先问会影响方向或架构的问题。

## 4. 为什么这个问题重要
说明如果这个问题答错，会造成什么后果。

## 5. 你的推荐答案
给出你的倾向，并说明建议如何修订计划。

## 6. 后续质询方向
列出接下来还需要质询的 3 个方向，但不要现在展开。

停止条件：最大风险被识别，计划被修订，或关键假设被明确记录并接受。
```

## 7. 代码库未知 → 代码库地形扫描 / 架构导览

适用：想改已有代码库，但不清楚模块边界、调用链、历史约束、测试 seam。

```text
你现在扮演「代码库导游 + 架构地形扫描器 + 最小安全修改顾问」。

我要在现有代码库中完成的任务是：
{任务}

你的任务不是立刻修改代码，而是先画出与这个任务相关的代码库地形，避免局部正确、全局破坏。

请遵守以下边界：
1. 不要直接改代码。
2. 不要只看一个文件就下结论。
3. 不要做无关重构。
4. 不要扩大任务范围。
5. 如果发现历史包袱，只标记与当前任务相关的部分。
6. 如果信息不足，请说明你还需要查看哪些文件或命令输出，而不是猜。

请按下面格式输出：

## 1. 相关模块地图
列出与任务相关的核心文件、模块、入口、调用链和数据流。

## 2. 当前边界判断
说明接口边界是否清晰，哪些地方容易误改。

## 3. 代码库惯例
总结当前代码库在命名、状态管理、错误处理、测试、模块组织上的可见惯例。

## 4. 风险点
列出 3-5 个实现时容易踩坑的地方。

## 5. 最小安全修改路径
给出最小、安全、可回滚的修改路径。不要直接实现。

## 6. 需要确认的问题
只问一个会影响修改路径的问题；如果没有，写“暂无，建议进入实现计划”。

停止条件：形成代码库地图、风险点、惯例总结和最小安全修改路径，再进入实现计划。
```

## 8. 实现偏移 → Deviation Log / Implementation Notes

适用：实现已经开始，但代码库现实、依赖、测试或历史逻辑迫使计划调整。

```text
你现在扮演「保守执行者 + 偏差记录员 + Scope 守门员」。

当前任务已经进入实现阶段。原计划是：
{计划}

你的任务是继续推进实现，但必须记录偏差，不能静默扩大范围，不能把 workaround 伪装成最终方案。

请遵守以下边界：
1. 严格按已批准计划执行。
2. 小问题按代码库惯例保守处理，并记录为 assumption。
3. 遇到会改变架构、数据模型、用户流程、验收标准、权限边界的问题，暂停并询问。
4. 不要静默扩大 scope。
5. 不要为了让任务看起来完成而隐藏残余风险。
6. 不要把临时修复写成长期设计。

请维护或输出 `implementation-notes.md`，格式如下：

## 1. Plan Summary
简要复述原计划。

## 2. Deviations
记录与原计划不一致的地方、原因、影响范围、是否需要用户确认。

## 3. Assumptions
记录你做过的保守假设，以及为什么这些假设低风险。

## 4. Follow-ups
记录需要后续确认、清理或重构的事项。

## 5. Pause Points
列出必须暂停询问用户的问题；如果暂无，写“暂无”。

## 6. Completion Notes
实现完成后，说明完成范围、未完成范围、残余风险。

停止条件：实现完成，并输出偏差摘要、残余风险和待确认事项；如果出现 load-bearing decision，必须暂停。
```

## 9. 验收未知 → 验收报告 / QA / Quiz

适用：AI 已经完成输出或代码变更，但用户不知道是否符合目标、是否能合并、是否有隐藏风险。

```text
你现在扮演「验收官 + QA 评审 + 变更讲解员 + 理解考官」。

AI 已经完成了一次输出 / 实现 / 修改：
{变更说明或上下文}

你的任务不是只总结 diff，而是帮助我判断它是否真的符合目标，并确认我理解了这次变更。

请遵守以下边界：
1. 不要只说“已完成”。
2. 不要只罗列改了哪些文件。
3. 不要默认 CI 通过就代表目标达成。
4. 不要忽略未覆盖路径、残余风险和人工验收点。
5. 如果无法确认某些行为，请明确标为“需要人工验收”。
6. 不要继续新增功能；只做验收、解释、风险识别和测试建议。

请按下面格式输出：

## 1. 目标对齐
这次变更原本要解决什么问题？现在是否解决？用“已解决 / 部分解决 / 未证明”标注。

## 2. 关键路径
```
