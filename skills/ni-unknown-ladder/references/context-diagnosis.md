# 基于上下文的重新诊断

`ni-unknown-ladder` 不是一次性判断器。每次运行时，都要基于当前可见上下文重新分诊。

## 诊断来源优先级

按以下顺序读取和综合信息：

1. **当前用户输入**：最新意图、最新限制、最新问题。
2. **当前对话上下文**：用户已经回答过的问题、已经确认的结论、已经否定的方向。
3. **用户显式提供的文件**：spec、research、notes、decision log、implementation notes、verification report 等。
4. **当前工程中可访问的文档和代码**：只在用户任务与代码库相关时使用。
5. **上一轮 `ni-unknown-ladder` 输出中的 unknown 队列**：如果仍在上下文中可见，则用于判断是否推进。
6. **可选状态文件**：仅当用户明确要求保存 / 读取状态时使用。

如果某个信息不在当前上下文、文件或状态文件中，不要假设已经知道。

## 每次运行前必须做的轻量复盘

在正式诊断前，先内部完成以下检查，并在输出中简要呈现：

- 当前已确认事实是什么？
- 上一个主 unknown 是否已经满足关闭条件？
- 哪些 unknown 已经解决？
- 哪些 unknown 仍然存在？
- 是否出现新的 unknown？
- 当前最阻塞的是哪一个？

## 输出中的上下文复盘

当用户是第二次或后续调用时，默认输出中加入：

```markdown
## 上下文复盘

- 已确认事实：
  - ...
- 已解决 Unknown：
  - ...
- 仍待处理 Unknown：
  - ...
- 新出现 Unknown：
  - ...
```

如果这是第一次调用，或上下文不足，可以省略“已解决 Unknown”，但必须说明当前判断基于哪些输入。

## 关键原则

- 后续诊断不是重新开始，而是基于当前上下文重新分诊。
- 如果用户已经通过上一阶段补齐信息，要承认该 unknown 已解决，不要反复卡在同一阶段。
- 如果用户只是说“继续吧”，但没有满足关闭条件，不要机械推进。
