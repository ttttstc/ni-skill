# 技术书风格契约（机制拆解型）

> 对标《GitHub Actions 运行机制蓝皮书》，全部从成书与其写作标准（TEMPLATE v3）提炼。本契约定义"技术书"书种的风格 DNA；在技术书种内，与共同底盘冲突时以本契约为准。

## 一句话气质
一个把事情彻底想清楚的实践者，在系统地讲清一个领域"后台到底怎么运转、为什么这么设计、边界在哪"——冷静、精确、零废话，读完能照着复刻一套等价系统。

## 定位契约
- **与官方文档分工**：不复述"字段叫什么、能取什么值"，讲「怎么运转 / 每条分支走向哪 / 为什么如此 / 放弃了什么」。
- **深度标尺**：让读者"不只是会配置，而是清楚——若要自己实现一套等价系统，该如何动手"。正文称「实现机制解析」，不用"复刻 / 逆向"等字眼。
- **一本书锚一条主线**：找出贯穿全书的结构主线（蓝皮书是"服务端编排 + Runner 执行"分离），再立 1-2 条关键分界当全书钩子；后文每遇反直觉行为，都能回主线找归处。

## 文风契约（硬规则）
- **人称"用户"，不出现"我"**：技术书去第一人称——这是技术书与公众号文章最大的分野（文章要"活人在场"，技术书要中性客观）。读者可称"读者"；指代配置者统一用"用户"。
- **不打比方**：删一切装饰性比喻（钥匙 / 保险箱 / 温床 / 踩踏 / 毒害 / 分水岭 / 命门…）；只保留已成行业标准的术语（缓存投毒、握手、心跳、信任锚、沙盒）。要生动靠"具体的真实细节 + 精确的因果"，不靠类比。
- **因果链叙述**：解释设计用「因为 X，所以 Y，代价是 Z」，把"放弃了什么"写出来。
- **每个机制三段展开**：实现现象 → 运行机制 → 设计原因。
- **重点句加粗**：每节约 1 句"最该记住的话"加粗（关键定义 / 反直觉结论 / 硬规则）；不满屏加粗（密度 ≤ 每节 1-2 处）。
- **章首强钩子**：用「本章核心问题」一句话钉死本章要解决的根本问题，加粗；禁"本章介绍…"。

## 优先级（技术书种内）
**严谨 > 可读性 > 文学性**（与公众号文章相反——文章是可读 > 专业）。但"严谨优先"不等于晦涩：通读时不得出现"需要折返才能读懂"的段落；去比喻后用因果链与具体例子顶上，不能滑成干巴巴的条目堆叠。

## 准确性铁律（详见 accuracy-rules.md）
零猜测；可溯源（官方文档 / 可观测行为 / 源码，三者皆无只描述边界并标"官方未公开"）；锚定时点（如"本书行为以 2026 年 6 月的 X 为准"）；易漂移数值指向官方、不写死；禁"基本上 / 通常来说 / 合理推断 / 置信度"等含糊词与标注腔。

## 结构契约（详见 structure-templates.md）
卷 → 篇 → 章三级；章内**八段式**；复杂机制单设「实现机制解析」节，区分**可观测行为 / 实现取舍**，以"这一层要维护的状态"收束。三条查询入口并存：按定义（官方语法条目顺序）/ 按场景（行为速查总表）/ 按问题（高频疑问）。

## 图（详见 figure-rules.md）
图表是承载复杂度的主体，文字只点睛。**时间先后 / 两方对比 / 多条件分支 / 层级结构**四类内容必配图或表，纯文字描述这四类视为不达标。图内只机制词、无导航词（不写篇号节号），每图至多一处强调色，配"读图指引"。
