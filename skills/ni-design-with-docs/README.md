# ni-design-with-docs

中文 | [English](./README.en.md)

> 先给调研输入，通过访谈与用户对齐，再从第一性原理生成产品与总体架构方案，并经过独立架构和安全评审。

`ni-design-with-docs` V1 适合新的产品或平台需求。它不分析现有代码，也不直接把模糊需求扩写成长报告，而是先关闭会改变产品行为、系统边界、影响范围、总体责任、质量、安全和验收的关键分支。

## 快速开始

Codex：

```text
$ni-design-with-docs 我需要为平台支持某项新能力。目标是……；已知业务和平台约束如下……
```

Claude Code：

```text
/ni-design-with-docs 我需要为平台支持某项新能力。目标是……；已知业务和平台约束如下……
```

第一次有效响应应给出当前理解、调研输入和第一轮 3–5 个决策问题，不得直接开始架构设计。

## 核心保证

- 设计前必须完成访谈并给出对齐摘要；只有用户确认后才能开始设计。
- 用户可以回复“本轮全部按推荐”，也可以授权后续分支全部采用推荐项；决策本身不会被省略。
- 调研过程、访谈记录、术语教程、评审记录和 Skill 策略留在工作底稿。
- 正式报告用普通开发能直接理解的中文，包含可直接定位的产品方案和系统规格，并只写用户结果、系统边界与影响范围、关键决定、主要流程、质量、安全、失败处理、上线和验收。
- 系统边界由访谈确认后由设计者归纳，不要求用户提供架构图，也不扫描代码补全内部现状。
- 方案选择能完整解决问题、责任最少、关系最简单的总体设计。
- 报告固定为六章。总体设计按“结论、产品方案、系统边界和责任、系统规格、流程/数据/状态、关键决定和协作约束”从大到小展开。
- 主要流程使用 UML 时序图或活动图，核心状态使用 UML 状态图，跨边界数据使用数据流图；多个模块共同承担责任时使用模块架构关系图；L0/L1 不是必填项。关键决定、责任和协作约束必须有文字结论，不能只放在图里。
- 正式报告默认保留 1–2 张表，最多 3 张；质量、安全、失败和验收内容使用“发生什么—系统怎么处理—怎样判断通过”等直接分块，避免宽表和抽象标签。
- 全文中文优先，不创造无必要的新模块和新术语。
- 独立评审只抓主要矛盾；如果评审不通过，先列出问题、最小修复和推荐选择，等用户确认修复范围后再改稿和复审。
- 正式发布前必须通过独立架构评审和独立安全评审。

## 工作流

```text
任务与证据准备
  → 调研输入与分轮访谈
  → 对齐摘要
  → 推荐决策清单与用户确认
  → 最小充分设计
  → 正式草稿
  → 独立架构评审 + 独立安全评审
  → 正式方案
```

“本轮全部按推荐”只关闭当前问题。用户也可以授权“后续全部按推荐”，减少来回问答；Skill 仍要遍历决策树，为每项记录选择、依据和影响。

用户要求“跳过访谈，按推荐设计”时，Skill 会进入推荐项快速路径，而不是跳过决策。能查明的事实由 Agent 调查；不能可靠推荐的用户目标、内部权限、商业或合规决定仍要询问。全部选择最后进入对齐摘要，用户确认后才开始设计。

## 调研与报告边界

访谈前的调研只回答会改变范围、协作约束、安全、质量或验收的问题。优先使用用户资料、官方标准、官方产品文档和官方参考实现。

正式报告不设置默认的调研过程、访谈记录或百科式概念章节。关键外部来源只出现在它实际支撑的事实或决策附近。

“非目标”只写用户确认的业务或产品范围。Skill 自身不处理的实现层级不能被写成项目非目标。

## 安全审视

每个方案都要判断安全适用性。存在身份、权限、敏感数据、秘密、外部输入、信任边界、高价值操作或资源风险时，需要：

- 识别资产、参与者、入口、数据流和信任边界；
- 分析主要威胁与滥用路径；
- 把控制措施落实到产品、责任、协作约束或运行路径；
- 明确残余风险和责任人；
- 给出可执行的安全验收；
- 通过独立安全评审。

安全影响不显著时，只需给出具体依据，由安全评审者核对，不机械生成安全清单。

## 正式交付

正式 Markdown 使用六章结构，章节内部按问题裁剪：

- 2–3 个短句组成的整体方案结论、目标和业务范围；
- 完整的产品方案，包括用户、问题、入口、操作、状态、反馈和支持边界；
- 系统边界、影响范围与责任；
- 系统必须遵守的规则、权限、数据、状态、失败行为和总体硬限制；
- 关键产品与架构决策；
- 必要的责任、运行、数据和协作约束；
- UML 时序/活动图、UML 状态图、数据流图和模块架构关系图（按问题适用）；
- 用“发生什么—系统怎么处理—怎样判断通过”分块表达的质量要求；
- 安全问题、可能后果、解决办法和验证；
- 失败处理和问题定位；
- 上线、兼容和回退；
- 验收、风险和研发下一步。

模板不是为了完整而完整的清单。没有实际内容的子节可以合并或省略，但六个一级章节及其从结论到细节的顺序保持稳定。

## 质量门禁

- G0：用户对齐
- G1：产品方案闭合
- G2：系统边界与影响范围
- G3：架构决策与责任
- G4：运行、数据与协作约束
- G5：安全与信任边界
- G6：质量、故障与运维
- G7：演进与可逆性
- G8：验收与追溯
- G9：可读性与可维护性

架构评审负责 G0–G4、G6–G9，安全评审负责 G5。两项都通过后才允许发布。
