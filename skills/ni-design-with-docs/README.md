# ni-design-with-docs

中文 | [English](./README.en.md)

> 用资料、访谈、公开证据和独立评审，把模糊的产品或云服务需求收敛为可研发评审的 Markdown 架构基线。

`ni-design-with-docs` 面向产品负责人、平台架构师和技术负责人。它先建立事实与概念底座，再逐步关闭范围、现状、契约和约束中的关键未知项；最终交付经过 G0–G10 硬门禁验收的产品架构基线，而不是直接生成一篇看似完整的长文。

## 快速开始

先确保 `ni-design-with-docs` 已安装到当前 Agent 的 skills 目录。完整安装方式见 [ni-skill 根 README](../../README.md)。

Codex：

```text
$ni-design-with-docs 我需要为平台支持某项新能力。目标是……；当前已支持……；相关产品、架构和接口资料如下……
```

Claude Code：

```text
/ni-design-with-docs 我需要为平台支持某项新能力。目标是……；当前已支持……；相关产品、架构和接口资料如下……
```

第一次响应应建立事实底座、对齐真正影响方案的核心概念，并提出第一批 3–5 个架构问题；信息收敛后才生成正式基线。

## 适用范围

| 适合 | 不适合 |
|---|---|
| 新建产品、平台或云服务能力 | 直接写代码或完整 PRD |
| 对存量能力做结构性增强 | 设计数据库表、类、方法或内部 DTO |
| 兼容第三方协议、生态或产品行为 | 默认逆向分析整个代码仓 |
| 从多份产品、架构或接口资料收敛顶层设计 | 只想快速比较两个局部技术选项 |
| 明确产品形态、L0/L1、主要契约、全局约束与验收 | 用空泛“最佳实践”替代内部事实和业务决定 |

## 交付内容

最终 Markdown 按当前问题裁剪，但关键设计不得缺失：

| 设计面 | 结果 |
|---|---|
| 问题与范围 | 背景、目标、非目标、用户和成功结果 |
| 事实与证据 | 已确认事实、假设、未知项、公开来源和能力差距 |
| 产品与架构 | 产品形态、L0/L1、一级模块职责和必要视图 |
| 契约与约束 | 主要接口、权限、数据、兼容、可靠性、性能容量和演进边界 |
| 验证 | 测试场景、可观察验收标准、风险、未决事项和详细设计边界 |
| 独立评审 | G0–G10 逐项结论；全部通过后才发布正式版本 |

## 工作流

1. 理解任务与资料，建立事实底座。
2. 对齐核心概念，分阶段批量访谈。
3. 定向分析文档，形成现状与能力差距。
4. 调研公开资料，收敛关键架构决策。
5. 设计产品形态、L0/L1、必要视图、主要接口和全局约束。
6. 反推测试与验收，生成 Markdown 草稿。
7. 启动独立评审，修订至通过后发布正式基线。

每轮通常只问 3–5 个同层问题，复杂场景最多 7 个。用户已经提供的信息不会重复询问；不会改变边界、契约、约束或验收的问题留给详细设计。

## 资料与证据规则

- 用户提供产品、架构、接口或设计文档时，只分析与当前能力直接相关的部分。
- 不默认扫描整个代码仓；用户明确要求时才把代码分析纳入范围。
- 公开调研优先使用官方标准、官方产品文档、官方参考实现和设计记录。
- 行业做法只作为证据，不自动升级成用户硬约束。
- 无法确认的现状和指标明确标记为假设、未知项或待确认，不编造数字。
- 关键来源应靠近它支撑的设计判断，说明证据如何影响选择。

## 评审与降级

调研阶段优先把 2–4 个互不重复的问题交给独立子代理并行取证。如果运行时没有调研子代理，主代理可以按问题顺序取证，但必须显式标注降级，并继续执行来源核对、版本确认和冲突识别。

正式交付前的独立评审不可降级为自评。运行时无法启动独立评审子代理时，结果必须是 `BLOCKED`，不能伪装成已经通过 G0–G10。
