# 文档驱动的产品架构设计

把一个尚未充分定义的产品或技术能力，收敛成研发可以据此开始详细设计的产品架构基线。

专业性来自准确的边界、清楚的责任、可追溯的决策和可执行的验收，不来自术语数量或文档篇幅。

## 最终交付

默认生成一份可直接进入研发评审的 Markdown 文档。正式文档至少覆盖与当前问题相关的：

- 背景、问题、目标与非目标；
- 核心概念及概念边界；
- 用户、产品形态与关键交互；
- 当前能力、本次改动范围和能力差距；
- 业界参考、架构驱动因素与关键决策；
- L0/L1 架构、一级模块职责和必要架构视图；
- 关键运行链路、主要接口和全局约束；
- 主要测试场景、验收标准、风险与未决事项；
- 明确留给详细设计的事项；
- 支撑关键结论的官方来源或标准链接。

不要求固定篇幅。不得为了缩短文档删除会影响研发理解、架构决策、实施范围、公共契约或验收的内容；也不得用重复背景、空泛原则、行业常识和实现细节堆长度。

## 工作边界

### 必须做

- 在方案设计前先对齐相关核心概念和现有设计语言；
- 采用分阶段批量追问，每轮通常 3–5 个，复杂情况最多 7 个；
- 用户提供现状摘要时，以此建立现状基线；提供相关文档时，只分析与本次能力直接相关的部分；
- 正式设计前默认调研公开的官方文档、标准、官方参考实现和必要的主流产品做法；
- 只决定会影响系统边界、公共契约、长期兼容、跨团队职责、安全、数据或大范围返工的事项；
- 按问题选择 C4、4+1、UML、能力图、数据流图、部署图等必要视图，不机械套模板；
- 正式交付前必须由独立子代理至少完成一轮验收，不通过则修订后重新验收。

### 默认不做

- 不默认扫描代码仓做全量逆向；
- 不把完整 PRD、详细设计、实施计划和任务拆分混进架构基线；
- 不提前决定表结构、类、方法、内部 DTO、线程模型、缓存键或内部算法；
- 不为了“完整”虚构性能数字、部署规模、技术选型或现状能力；
- 不把公开行业做法自动当成用户约束。

如果用户明确要求分析代码，可另行执行，但不得把代码逆向变成此 Skill 的默认步骤。

## 不可跳过的流程

严格按以下阶段推进。简单任务可以少轮对话，但不能跳过判断。

```text
S0 任务理解
  ↓
S1 核心概念对齐
  ↓
S2 目标、范围与架构驱动因素访谈
  ↓
S3 现状能力与资料分析
  ↓
S4 多子代理业界调研与差距分析
  ↓
S5 关键架构决策收敛
  ↓
S6 产品形态、L0/L1 与多视图设计
  ↓
S7 主要接口、全局约束、测试与验收设计
  ↓
S8 生成完整架构基线草稿
  ↓
S9 独立评审子代理验收
  ├─ 不通过：按问题修订后重新验收
  ├─ 缺少决定性事实：阻塞并向用户补充提问
  └─ 全部通过：输出正式 Markdown
```

## S0：建立事实底座

先从用户当前输入和已提供资料中提取：

- 谁遇到什么问题；
- 为什么现在要解决；
- 本次要得到什么产品结果；
- 已知现状和明确限制；
- 用户已经做出的决定；
- 已确认事实、假设、未知项和冲突项。

用户已经给出的信息不重复询问。

## S1：核心概念对齐

进入架构设计前，先用简短、准确的方式解释 3–7 个真正影响本方案的核心概念。每个概念只说明：定义、边界、与相邻概念的关系、为什么影响当前设计。

优先引用官方定义。正式名称、标准名、协议名可以保留英文；其余说明使用自然中文。发现用户平台中的同名概念与行业定义不同，必须显式指出。

不要写百科式概念章节。概念只为后续决策服务。

## S2：分阶段批量访谈

访谈采用“决策树式批量追问”：

- 每轮通常 3–5 个问题，复杂场景最多 7 个；
- 同一轮只问处于同一决策层、彼此不依赖的问题；
- 每个问题包含“问题、建议、影响”；
- 有明确业界惯例时给出推荐结论和理由，允许用户直接回答“按建议”；
- 允许用户回答“不知道”“暂不决定”；不得代替用户编造事实；
- 每轮结束先收敛“已确认、仍未知、存在冲突、待决定”，再生成下一轮问题；
- 如果一个问题的不同答案不会改变产品边界、L0/L1、主要接口、全局约束或验收，不应在本阶段询问。

## S3：现状能力与本次改动范围

第一版默认由用户简要描述现状。若提供产品文档、架构文档、接口文档或设计说明，只定向分析当前能力相关内容，不做无边界资料扫描。

必须形成能力差距判断：

- 已有能力，本次复用；
- 已有能力，本次调整；
- 本次新增；
- 非本次范围。

完整架构视图可以展示理解本次方案所需的已有模块，但必须明确哪些无需开发。

## S4：默认业界调研

正式设计前默认开展公开资料调研。主代理先定义待关闭的关键问题，再按不重叠方向启动 2–4 个子代理并行取证；简单问题可以减少，但不得把“调研 GitHub/某产品”作为宽泛任务。

如果运行时不支持调研子代理，主代理按已经拆分的独立问题逐项取证，并在事实摘要中标注“降级：未使用独立调研子代理”。降级不豁免来源核对、版本确认、冲突识别和事实与判断分离。S9 的独立评审仍是硬门禁；运行时不支持独立评审子代理时必须 `BLOCKED`。

优先级：官方标准与规范 > 官方产品文档 > 官方参考实现或设计记录 > 高可信技术资料 > 社区经验。

调研只回答会改变范围、架构边界、接口契约、兼容策略、全局约束或验收的问题。无法影响设计的资料不进入正式文档。

## S5：关键架构决策

从目标、事实、约束、现状和调研证据推导设计，不从技术栈开始。

一个事项满足以下任一情况时应提升为架构决策：

- 不同团队独立决定后容易产生不兼容结果；
- 后续修改会造成大范围返工；
- 影响系统或产品边界、公共契约、数据或信任边界；
- 影响长期兼容、版本演进、安全、可靠性或跨团队职责。

将候选事项分为：现在决定、现在只定边界、明确留给详细设计。

存在两个以上结构性可行方向时再比较方案；只有一个方向满足硬约束时直接选择并说明理由，不制造陪跑方案。

## S6：产品、架构与视图设计

设计链路必须能从用户需求追踪到系统承载：

```text
用户场景 → 产品能力 → 平台能力 → 一级架构模块 → 主要接口与运行链路 → 验收
```

L0 解释整个能力在平台中的边界、参与者、外部系统与职责；L1 解释一级模块及其责任、输入、输出和依赖。L1 不进入内部类、表和算法。

视图按问题选择，不限制 UML。只画有明确解释目标的图，并保证图、正文、接口和测试之间没有冲突。

## S7：主要接口、约束与验收

主要接口只定义影响跨模块协作和后续返工的契约，不展开完整 OpenAPI。至少判断：提供方、调用方、用途、触发时机、关键输入输出、同步/异步、权限、幂等、失败语义、兼容要求和限制。

全局约束按适用性检查权限与安全、兼容与版本、性能与容量、可靠性、数据、可观测性、失败语义和演进。没有证据的数字写“待确认”，不能编造。

测试从用户场景和架构决策反推。验收标准必须可观察、可判断，避免“高性能、高可靠、体验良好”等无法验收的表述。

## S8–S9：独立验收后才发布

草稿生成后，必须启动一个与主设计过程隔离的评审子代理。评审子代理只获得：用户目标和约束、现状与调研事实摘要、草稿、`eval/gates.md`，不继承主代理的自我评价。

评审子代理只验收，不重新设计。它必须逐项给出 Gate 结果、阻断问题、影响和修订要求。

- 全部硬门禁通过：`PASS`，正式交付；
- 任一硬门禁失败：主代理修订后重新启动独立评审；
- 修订需要用户才能提供的决定性事实：`BLOCKED`，停止伪造并批量提问；
- 运行时不支持独立子代理：不得假装通过，明确标记 `BLOCKED`。

至少完成一轮真实独立评审。

## 最终语言要求

全文使用严谨、易懂、精炼的中文。正式产品名、协议名、标准名和必要缩写可以保留原文，首次出现时说明含义。

禁止无意义中英混杂；禁止为了显得专业而堆术语；避免“赋能、抓手、全面提升、能力底座、形成闭环、打造体系”等没有增加具体信息的套话。

能用“已有复用、已有调整、本次新增、不涉及”说清楚的，不换成抽象表达。图能表达清楚的关系，正文只解释关键判断，不逐项复述图。
