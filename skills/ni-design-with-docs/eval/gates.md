# 产品与架构方案硬门禁

所有门禁都必须通过。架构评审负责 G0–G4、G6–G9；独立安全评审负责 G5，并核对相关安全验收。缺少只能由用户或内部事实提供的信息时使用 `BLOCKED`。独立评审采用风险优先原则，只报告会造成目标、边界、责任、安全、重大返工或验收失败的主要问题，不为完整而完整。

## G0 用户对齐

通过条件：

- 评审材料中有用户原始目标和约束；
- 有完整决策树、用户回答或推荐项授权、最终对齐摘要；
- 用户已经明确确认包含全部显式决策的对齐摘要；
- “本轮全部按推荐”没有被误当成自动开始设计；
- “后续全部按推荐”没有省略决策清单、事实调查或最终确认；
- 推荐阶段没有在系统边界未经确认时提前创造模块、分层或技术实现；
- 草稿没有把未确认的推荐、假设或行业做法写成用户决定；
- 访谈和推荐选择记录留在工作底稿，没有变成正式报告章节。

## G1 产品方案闭合

通过条件：

- 核心用户、问题和成功结果清楚；
- 目标直接描述具体需求和用户或系统结果，没有把文档用途或研发过程当成产品目标；
- 有可直接定位的产品方案，写清面向谁、解决什么、入口、主要操作、状态反馈和支持边界；
- 有独立可定位的系统规格，写清核心规则、权限和数据规则、状态结果、失败行为和总体硬限制；
- 系统规格是系统行为和约束的唯一真源，没有新增独立 Story、行为规格或 Gherkin 章节；
- 产品方案不重复系统规则，系统规格不重复用户操作；
- 入口、主要交互、状态、反馈、异常和恢复按需明确；
- 处理中、成功、失败、超时和取消能力按适用性给出用户可见结果；
- 产品行为能够追踪到系统责任和验收；
- 多角色、多状态或分支交互使用了合适的用户视图，或有充分理由不用图；
- 没有用技术接口或架构图替代用户方案。

## G2 系统边界与影响范围

通过条件：

- 系统边界来自用户资料和访谈确认，由设计者归纳，而不是要求用户自己画架构；
- 系统负责什么、责任在哪里结束已经说清；
- 与需求直接相关的用户、团队、外部系统和依赖已经识别；
- 新增责任、调整协作、保持不变和外部约束按需区分；
- 没有通过猜测、代码或仓库扫描补全未确认的内部现状；
- 只保留理解用户路径、总体协作、安全、质量和验收必需的对象。

## G3 架构决策与责任

通过条件：

- 方案从真实目标、不可变事实和约束推导；
- 关键责任、边界和所有权足以承载用户场景；
- 只保留会影响边界、长期协作约束、安全、质量、演进或大范围返工的决策；
- 每个决策都直接写清结论和理由；
- 决策正文是权威结论，没有只依赖结构图或流程图表达；
- 关键决定表没有“接受的代价、复审条件”等辅助字段；
- 没有制造陪跑方案、新名词、无责任抽象或多余模块；
- L0、L1 和其他视图按问题选择，没有机械补图；但主要流程、核心状态、跨边界数据和多模块责任关系已按对应问题提供必要视图。

## G4 运行、数据与协作约束

通过条件：

- 主成功路径可以端到端解释；
- 关键异常、状态变化和恢复路径闭合；
- 跨系统或跨团队的关键协作约束写清规则、涉及对象、生效阶段和违反后的系统结果；
- 权限、数据所有权、重复、顺序、并发、超时、失败和重试只在影响总体方案时明确；
- 存在并发、重复、乱序或异步结果合并时，用户结果、数据状态和恢复方式不含糊；
- 超时、取消或部分失败后的停止、恢复或继续方式按需明确；
- 协作约束没有复述普通责任和流程步骤，也没有展开接口路径、字段或错误码；图没有替代关键约束的文字结论；
- 影响总体设计的数据所有权、流转、一致性和保留边界清楚；
- 内容深度足以支撑后续详细设计，没有无关实现细节；
- 设计门禁不要求尚未完成的代码、测试结果或生产证据；内部事实和系统边界仍必须经过用户确认。
- 主要流程涉及两个以上责任方时有 UML 时序图或 UML 活动图；核心状态有 UML 状态图；跨模块或跨系统数据有数据流图；两个以上系统或模块共同承担责任时有模块架构关系图；不适用时说明理由；
- UML 图、数据流图和模块架构关系图各自只回答一个问题，且图、正文、协作约束、状态和验收没有冲突。

## G5 安全与信任边界

由独立安全评审者判定。

通过条件：

- 安全适用性有明确结论和依据；
- 相关资产、身份、入口、数据流和信任边界清楚；
- 主要滥用路径和威胁与本次改动相符；
- 身份认证、授权、输入限制、秘密、隔离、审计和资源控制按适用性落实；
- 控制措施能够定位到产品或架构设计，并有可执行验证；
- 新增控制在设计阶段写清责任、失败处理、验收和发布门槛即可，不要求提前提供实现证据；
- 正式报告直接写明安全问题、可能后果、解决办法和验证方式；
- 面向用户或其他系统的详情、错误、日志和导出遵守请求者权限，并最少暴露敏感信息；
- 安全事件回退能停止继续扩大风险，并按实际影响处理进行中操作、秘密或凭证，明确责任人并保留必要记录；
- 残余风险有责任人、接受结论或关闭方式；
- 不存在 `references/08-security-review.md` 所列硬阻断项；
- 安全影响不显著时，理由足以排除实质影响，而不是简单写“不涉及”。

## G6 质量、故障与运维

通过条件：

- 使用业界通用质量模型检查遗漏，但没有把分类清单直接复制进报告；
- 只选择会改变产品结果、系统边界、跨系统协作、安全、上线或验收的质量要求；
- 每项质量要求都写清发生什么、系统必须怎样响应和怎样判断通过；
- 没有编造性能、容量、可用率或恢复时间；会改变总体方案的数值已经确认，不会改变的数值留给详细设计或容量测试；
- 关键依赖失败后，用户结果和系统状态明确；
- 重试、降级、补偿、恢复和责任边界按需明确；
- 日志、指标、追踪、审计和告警足以支持验收与问题定位；
- 没有用“高性能、高可靠”等口号替代可观察结果。

## G7 演进与可逆性

通过条件：

- 兼容、版本、迁移、灰度和回滚已按适用性判断；
- 新旧行为共存和废弃边界按需明确；
- 不可逆步骤、回滚触发信号和恢复责任清楚；
- 暂停或回退由谁判断、批准和执行已经明确；
- 安全事件下，已经创建或正在执行的受影响操作有止损办法；
- 兼容方案没有破坏既有契约或降低安全要求；
- 没有演进影响时，方案没有机械生成空章节。

## G8 验收与追溯

通过条件：

- 每个核心产品能力、硬限制、关键异常、安全边界、兼容与回归要求和架构级质量要求按适用性至少有一个设计级主验收场景覆盖；
- 每个主验收场景都能追踪到前文的系统规格、质量、安全、兼容、上线要求或其他既有结论；
- 每个主验收场景至少包含覆盖要求、前置条件、关键操作和明确 PASS 条件；
- PASS 条件能够通过状态、数量、已确认阈值、一致性结果或其他确定性信号判断；
- 数值阈值有明确来源，没有为了形式完整编造性能、容量、可用率或恢复时间；
- 没有只用“正确、正常、合理、体验良好、基本兼容、高性能、高可用、符合预期”等不可直接判定的结果；
- 验收只验证前文结论，没有重新描述产品方案、系统规格或失败处理，也没有扩张成详细测试用例库；
- 测试数据组合、等价类、完整边界矩阵和自动化实现细节留给后续测试设计；
- 系统规格是行为要求的唯一真源，没有重复维护独立 Story 或行为规格章节；
- Given / When / Then 如有使用，只描述可观察场景，不描述内部实现路径；
- 复杂方案可以从稳定标题或编号追踪要求、决定和验收；简单方案没有为了追踪堆满编号。

## G9 可读性与可维护性

通过条件：

- 第一章是一个段落、2–3 个短句，能让熟悉背景的开发快速知道最终结果、核心做法、关键保护、主要影响和保持不变的关系；
- 摘要直接写最终结果，不以“本方案旨在、通过建设、形成能力”等空泛句式开头；
- 正式报告只有六个一级章节，并按“方案摘要、目标和范围、总体设计、质量安全异常、上线验收、风险与参考来源”排列；
- 总体设计按“结论、产品、边界和责任、规格、流程数据状态、决定和约束”从大到小展开；
- 每章、每节先给结论，再给支持信息；
- 正式报告没有访谈记录、调研过程、术语教程、Skill 策略或评审全文；
- “非目标”只包含用户确认的业务或产品范围；
- 增量需求只在差异影响研发理解或总体设计时说明当前/目标行为和设计影响；全新能力没有空差异小节；
- 系统边界、影响范围、决策、质量、视图、风险和来源都与本次需求直接相关；
- 中文自然、句子简洁，普通开发一次阅读即可理解主流程；
- 优先写“谁做什么、失败后怎么办”，没有连续堆叠“边界、语义、属性、可逆性、适用性”等抽象词；
- 正式报告默认保留 1–2 张表，最多 3 张；表格只用于短文本的横向比较、映射或状态汇总；
- 质量、安全和失败内容使用符合其问题的直接标签，不使用“适配策略”等抽象说法；验收使用“覆盖要求—前置条件—操作—通过条件”，单元格不放大段文字；
- 同一个问题只有一个主要归属，产品、质量、安全、失败和验收章节没有重复解释；
- 系统规格、行为规格和验收没有形成三套同义文本；SR/AC 编号没有妨碍阅读；
- Given / When / Then 只在比自然语言更清楚时使用，没有把报告写成 `.feature` 文件或内部调用脚本；
- 没有无意义中英混杂、AI 套话或无法解释的新名词；
- 图有明确类型、标题和要回答的问题，优先使用现有名称和中文标签；UML 图不是类图堆砌，数据流图不是调用步骤清单，模块关系图不是全系统目录；
- 标题、状态词和必要编号稳定，人和 Agent 都能定位信息；
- 删除重复和无关内容后，仍保留后续详细设计所需的责任、协作约束、质量、安全、风险和验收。

## 总体判定

只有架构评审和安全评审都为 `PASS`，总体结果才是 `PASS`。

- 任一评审为 `FAIL` 或 `BLOCKED` 时，先向用户列出评审结论、主要影响、最小修复、不修复后果和推荐选择；用户确认修复范围后，才允许改稿和复审；
- 评审不得把低收益边缘适配、可留给详细设计的实现细节或个人格式偏好列为阻断项；
- 用户未确认修复范围，或拒绝必要阻断修复时，不得标记为 `PASS` 或发布正式方案。

- 已有证据足以修复：`FAIL`，修订后重新启动对应独立评审；
- 需要用户或不可访问的内部事实：`BLOCKED`，停止并提出最少必要问题；
- 运行时无法提供独立评审上下文：`BLOCKED`，不得以主设计者自评代替。
