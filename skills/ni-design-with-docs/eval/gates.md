# 产品架构基线硬门禁

所有 Gate 均为硬门禁。任一 `FAIL` 不得发布正式基线；缺少只能由用户或内部事实提供的信息时标记 `BLOCKED`。

## G0 问题与范围

通过条件：

- 背景说明为什么需要建设；
- 用户问题、建设目标和成功结果清楚；
- 本次范围与非目标明确；
- 没有把解决手段误写成业务目标。

## G1 核心概念一致性

通过条件：

- 影响设计的核心概念已定义；
- 易混概念边界清楚；
- 采用的行业或参考产品定义有来源；
- 全文术语一致，没有同义词随意切换。

## G2 现状与改动范围

通过条件：

- 能说明当前已有相关能力；
- 明确区分已有复用、已有调整、本次新增和非本次范围；
- 没有把未经证实的现状写成事实；
- L0/L1、接口和测试范围与改动范围一致；
- 研发能够明确知道“本次到底做什么、不做什么”。

## G3 产品设计完整性

通过条件：

- 主要用户和核心使用场景明确；
- 产品能力和用户可见形态明确；
- 关键交互、状态和限制能够被用户理解；
- 产品设计能够追踪到后续平台和系统能力。

## G4 L0/L1 架构完整性

通过条件：

- L0 边界、外部参与者和依赖清楚；
- L1 一级模块足以承载核心场景；
- 每个模块责任、输入、输出和依赖清楚；
- 不存在关键职责重复兜底或无人负责；
- 没有无依据引入数据库、缓存、消息队列等实现组件。

## G5 架构视图一致性

通过条件：

- 每张图都有明确解释目标；
- 选择的视图适合当前问题，没有机械补齐 UML 或 4+1；
- 图、正文、主要接口、状态和能力差距没有冲突；
- 图中已有/调整/新增状态与正文一致。

## G6 关键运行链路

通过条件：

- 主成功路径可以端到端解释；
- 影响总体设计的关键异常路径已覆盖；
- 有生命周期的核心对象状态变化清楚；
- 能判断失败发生后由谁感知、谁处理。

## G7 主要接口与全局约束

通过条件：

- 跨模块主要契约有明确责任方和使用方；
- 关键输入输出、交互方式、权限、失败语义、幂等或兼容要求按需明确；
- 安全、数据、兼容、版本、可靠性、性能容量、可观测性等已按适用性判断；
- 没有编造无法支撑的量化指标。

## G8 测试与验收

通过条件：

- 核心用户场景和关键架构决策都有对应验证；
- 主路径、边界、关键异常、兼容和回归按需覆盖；
- 验收结果可观察、可判断；
- 不使用“高性能、高可靠、正确执行”等空泛标准代替结果。

## G9 证据与决策可追溯

通过条件：

- 重要业界事实优先使用官方或一手来源；
- 关键外部结论附近保留必要引用；
- 能看出事实如何影响设计选择；
- 行业做法没有被自动当成用户硬约束；
- 存在版本或来源分歧时已经明确说明。

## G10 文档质量与设计边界

通过条件：

- 中文表达严谨、易懂、精炼；
- 没有无意义中英混杂和明显 AI 套话；
- 没有大段重复、空泛背景或图文复述；
- 没有为了压缩而缺失关键设计；
- 没有提前进入表结构、类、方法、内部算法等详细实现；
- 风险、未决事项和详细设计边界明确。

## PASS 判定

评审者必须逐项检查 G0–G10。只有全部为 `PASS` 时总结果才是 `PASS`。

如果问题可以由主代理根据已有证据修复，结果为 `FAIL` 并给出修订要求；如果修复依赖用户或无法访问的内部事实，结果为 `BLOCKED`。
