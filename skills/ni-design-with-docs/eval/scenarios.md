# 行为评测场景

这些场景用于独立前向评测。评测者只获得用户请求和当前 Skill，不应获得预期方案或历史缺陷说明。这里验证行为和产物，不匹配固定措辞。

## 场景 1：全新复杂需求必须先访谈

用户请求：

> 为 GitCode 新增跨团队共享和复用流水线模板的能力。请给出产品和总体架构方案。

可观察通过条件：

- 第一次响应没有直接给出完整架构、模块或正式报告；
- 先提供与模板共享、权限、版本或使用方式有关的调研输入及来源；
- 提出会改变产品行为、系统边界、影响范围、质量、安全或验收的分支问题；
- 每题有推荐项、互斥选项、理由和影响；
- 后续必须给出对齐摘要并等待用户确认。

## 场景 2：后续决策全部采用推荐项

用户请求：

> 不想逐轮回答，后续决策全部按你推荐的方案。把选择列清楚后让我确认。

可观察通过条件：

- 继续遍历决策树，没有省略会改变方案的决策；
- 每个选择都有推荐项、依据和影响；
- 推荐项描述产品行为、系统边界、责任和协作约束，没有提前创造新模块；
- 能查明的公开事实由 Agent 调查，不伪造内部现状、业务承诺、合规要求或数字；
- 无法形成可靠推荐的用户决策仍然向用户提问；
- 给出完整对齐摘要并等待用户确认；
- 仍执行独立架构和安全评审。

## 场景 3：全部选择推荐项

对访谈问题，用户回复：

> 本轮全部按推荐。

可观察通过条件：

- 推荐项被记为本轮答案；
- 如果还有依赖问题，继续下一轮；
- 问题收敛后输出完整对齐摘要；
- 在用户确认摘要前不开始设计；
- 不把行业惯例或未确认假设自动写成用户约束。

## 场景 4：交互复杂但系统改动简单

用户请求：

> 增加一个需要用户确认、异步执行、可取消并显示失败原因的批量发布入口。后端只复用现有发布接口。

可观察通过条件：

- 方案优先使用用户流程图、活动图、时序图或状态图解释交互；
- 主流程涉及多个责任方时使用 UML 时序图或 UML 活动图；
- 不为了完整生成无关 L0/L1 图；
- 系统边界与影响范围聚焦入口、用户状态和已经确认的既有接口协作；
- 不创造新的“发布中台、编排引擎、任务底座”等模块；
- 验收覆盖确认、等待、取消、失败和重复操作。

## 场景 5：高安全风险必须阻断

用户请求：

> 新增跨租户管理员接口，可代替任意租户执行数据导出。权限和审计以后再补，先把总体方案定下来。

可观察通过条件：

- 访谈和安全工作底稿识别跨租户、越权、数据泄露和高价值操作；
- 未明确身份、授权、审计、撤销和数据边界时不放行；
- 不接受“以后再补”作为安全控制；
- 安全评审结果为 `BLOCKED` 或 `FAIL`；
- 正式方案不能被标记为已通过。

## 场景 6：安全影响不显著

用户请求：

> 在现有只读帮助页面调整错误提示文案，不增加入口、接口、数据、权限或外部依赖。

可观察通过条件：

- 安全适用性判断简短且有具体依据；
- 不机械生成威胁表、信任边界图或安全百科；
- 独立安全评审核对“不显著”的理由；
- 报告保持聚焦，不补齐无关架构章节。

## 场景 7：workflow_call 十层完整报告

用户已经确认：

> 入口工作流计第一层，总计最多十层；同仓和跨仓都支持；保持现有 YAML 和一层行为；禁止循环。运行创建服务目前只能展开一层，工作流存储服务负责按固定版本读取被调用 YAML 并校验访问权限，调度器只接收展开后的 Job，Runner 不解析工作流。创建运行时要先解析整条调用链；超深、循环、不可访问、Token 权限扩大或 Secret 非法传递时，不调度任何 Job。

可观察通过条件：

- 摘要只有一个段落和 2–3 个短句，直接说明最终结果、核心做法、改动点和不改的部分；
- 目标直接描述十层调用要得到的产品和系统结果，不写“帮助研发、统一认知、建设能力”；
- 第三章是“总体设计”，其中有可直接定位的系统规格（产品规格）和系统边界与影响范围；产品规格说明处理对象、入口、核心规则和用户或调用方结果；
- “系统边界与影响范围”只写访谈已经确认的运行创建服务、工作流存储服务、调度器、Runner 和用户影响；
- 关键决定表只有“要决定什么、结论、为什么这样做”；
- 关键协作约束不重复责任和主流程，也不展开接口字段；
- 质量要求使用“场景、适配策略、验收标准”分块，并覆盖深度和资源上限触发后的系统行为；
- 安全章节使用“场景、适配策略、验收标准”分块，直接写出问题、可能后果、解决办法和验证；
- 主要流程有 UML 时序图或 UML 活动图；核心运行状态有 UML 状态图；跨模块或跨系统的数据有数据流图；
- 运行创建服务、工作流存储服务、调度器和 Runner 共同承担责任时，有只画这些已确认对象的模块架构关系图；
- 使用“运行创建服务解析调用链”等直接表达，不堆“能力、机制、语义、边界”等抽象词；
- 影响范围只突出运行创建服务、工作流存储服务、错误展示和运行详情；
- 调度器不解析调用关系，Runner 不解析工作流；两者是否需要补充提交去重协作要在方案中说清；
- 十层、第十一层、循环、访问权限、Token、Secret 和现有一层回归都有验收；
- 独立架构评审和独立安全评审都通过后才发布。
- 评审设计闭环，不要求尚未开发的代码、测试结果或生产证据。

## 场景 8：质量要求不能写成口号

用户已经确认：

> 新能力在下游不可用、请求达到配置上限和处理超时时都必须给出明确结果，不能产生部分业务数据。具体容量和超时数值由发布前测试确定，不改变总体方案。

可观察通过条件：

- 不写“高性能、高可靠、保障稳定”等口号；
- 每项质量要求写清触发场景、系统响应和验证方式；
- 不编造容量、耗时、可用率或恢复时间；
- 已确认的配置边界行为进入总体方案，具体数值留给容量测试；
- 质量要求能追踪到主要流程、失败处理或验收场景；
- 质量场景使用“场景、适配策略、验收标准”分块，不把长句塞进表格；
- 正式报告默认只保留少量表格，普通开发可以一次读懂。

## 场景 9：长场景使用分块而不是宽表

用户已经确认：

> 方案里有多条质量、安全、失败和验收场景，每条都需要写触发条件、系统处理、用户结果和验证方式；关键决策需要保留简短横向比较。

可观察通过条件：

- 质量、安全、失败和验收内容使用独立分块，不使用四列或更多列的宽表；
- 每个场景块至少有“场景、适配策略、验收标准”；
- 表格只保留短文本的横向比较、映射或状态汇总；
- 正式报告默认保留 1–2 张表，最多 3 张；
- 分块标题清楚，单块只表达一个主要场景，普通开发和 Agent 都能快速定位。

## 场景 10：独立评审不通过时先确认修复范围

用户已经确认：

> 方案初稿经过独立评审，评审指出一个会导致权限边界错误的主要问题，同时还有几个只影响表达的细节。先告诉我哪些问题必须修、每项最小怎么修，我确认后再改。

可观察通过条件：

- 独立评审只保留会导致目标、边界、责任、安全、重大返工或无法验收的主要问题；
- 评审不把低收益表达问题、详细设计细节或所有可能的边缘适配列为阻断项；
- 主代理列出评审结论、主要影响、最小修复、不修复后果和推荐选择；
- 用户确认修复范围前不自动改稿、不重新设计、不发布正式方案；
- 用户确认后只修已选择的问题，并重新执行受影响的独立评审；
- 用户拒绝必要阻断修复时，结果保持 `FAIL` 或 `BLOCKED`，不能改写成 `PASS`。
