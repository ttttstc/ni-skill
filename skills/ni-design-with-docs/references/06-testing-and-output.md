# 质量、失败、验收和正式输出

## 1. 用通用标准检查遗漏

先使用 ISO/IEC 25010 的通用质量模型检查是否遗漏，再只选择会改变本次总体设计的方面：

- 速度、容量和资源使用；
- 稳定性、可用性和恢复；
- 数据正确性、完整性和一致性；
- 系统之间的兼容与协作；
- 问题发现、定位和运维；
- 后续修改是否需要改变系统边界；
- 安全和隐私，具体方法见 `references/08-security-review.md`。

这份列表只用于提问和自查，不直接复制进报告。某一方面不改变产品结果、系统边界、跨系统协作、安全、上线或验收时，不写。

## 2. 把质量要求写成可验证结果

SEI 的完整质量场景包含触发者、条件、受影响对象、系统响应和衡量方式。正式报告为了易读，使用短分块，不把长句压进三列表格：

### 下游在处理期间不可用

- **发生什么**：下游在本次处理期间不可用。
- **系统怎么处理**：本次处理在明确边界内失败，不把未知状态显示为成功；恢复后可以安全重试。
- **怎样判断通过**：注入下游故障，观察用户结果、系统状态和重试结果。

写作要求：

- “发生什么”写清触发条件和所处场景；
- “系统怎么处理”写可观察行为，不写“保障、提升、尽量”；
- “怎样判断通过”写测试、演练或可读取结果；
- 一个分块只表达一个主要质量要求；
- 不重复安全、故障和验收章节已经完整表达的内容。

同一个问题只设一个主要归属：跨流程的速度、容量、稳定性、正确性或问题定位要求放在这里；攻击和滥用放安全章节；有独立恢复路径的异常放失败章节；主流程已经说清的普通分支不再重复。

不要编造性能、容量、可用率或恢复时间。数值会改变总体方案时，回到访谈确认；不会改变时，写成配置边界或发布前容量测试项，并把具体数值留给详细设计。

## 3. 出错后怎么办

只覆盖会影响用户结果、数据正确性或模块协作的失败：

- 哪里可能失败；
- 用户或调用方看到什么；
- 系统停止、重试、降级还是等待人工处理；
- 如何避免把失败或未知状态显示为成功；
- 用什么日志、指标或追踪信息找到问题；
- 谁负责恢复。

不要罗列所有异常码，也不要只写“做好监控”。

## 4. 如何上线和回退

存在兼容、迁移或灰度影响时，说明：

- 新旧行为如何同时存在；
- 如何逐步放量；
- 什么情况要暂停或回退；
- 谁负责判断、批准和执行暂停或回退；
- 回退后数据和配置如何处理；
- 哪些步骤无法直接回退。

没有这些影响时，省略本节。

## 5. 如何验收

验收只定义设计级主场景：研发和测试必须跑通这些场景，才能认为主要产品行为和总体架构基本实现正确。它不是详细测试设计，不负责穷举等价类、边界值组合、测试数据、多环境差异、异常注入矩阵或自动化实现。

每个主场景都应对应系统规格、关键决定、协作约束、质量要求、安全问题、兼容要求、上线要求或已知风险。验收只证明前文结论，不重新复制产品方案或系统规格。

### 5.1 只选择当前方案需要的主场景

按适用性覆盖：

- **核心成功路径**：证明主要产品能力可用；
- **关键边界**：证明会影响结果或架构的重要限制生效；
- **核心异常**：证明关键失败不会产生错误或不确定结果；
- **权限与安全边界**：证明不能越权、泄露或绕过限制；
- **兼容与回归**：证明本次改动没有破坏关键既有行为；
- **架构级质量要求**：证明已经确认的性能、可靠性、恢复或正确性约束得到满足。

不是每个方案都必须覆盖全部六类。只保留与当前改动有关、删除后会降低研发自验或测试主场景覆盖的内容。

### 5.2 使用统一的主场景格式

普通场景使用短分块：

```markdown
### AC-01 {能够表达验收结论的标题}

**覆盖要求**：{系统规格、质量、安全、兼容或上线要求}

- **前置条件**：{需要构造的状态、输入或环境}
- **操作**：{执行的关键动作}
- **通过条件**：
  - {明确可观察结果 1}
  - {明确可观察结果 2}
- **验证方式**：{仅在不显而易见时填写}
```

每个主场景至少包含覆盖要求、前置条件、操作和通过条件。验证方式只在手段不显而易见时增加。复杂条件组合可以使用 Given / When / Then，但它仍属于验收场景，不形成独立行为规格章节。

### 5.3 PASS/FAIL 使用确定性信号

通过条件必须能由以下至少一种信号判定：

- **状态型**：最终状态、错误类型、实际权限或某个对象是否存在；
- **数量或阈值型**：实例数、最大层数、错误率或已确认的性能阈值；
- **一致性型**：升级前后契约一致、失败后没有部分成功、重复执行只产生一个业务结果；
- **其他确定性信号**：有明确观察对象和相等、不等、包含或不存在等判定关系。

数值必须来自产品目标、已有系统基线、官方兼容标准或用户确认的工程目标。输入只有“性能不能明显下降”等模糊要求时：

- 数值会改变总体方案：回到访谈确认基线、阈值和观察方式；
- 数值不改变总体方案：留给详细设计或容量测试，不作为当前正式验收项。

不得为了形式完整生成来源不明的 P95、QPS、百分比、容量或恢复时间。

### 5.4 禁止模糊 PASS 描述

“正确执行、正常运行、合理失败、体验良好、性能良好、基本兼容、快速恢复、满足高可用、不明显影响性能、符合预期”不能单独作为通过条件。必须改成具体状态、数量、已确认阈值、一致性结果或其他确定性信号。

例如：

```text
不推荐：第 11 层调用正确失败。
推荐：第 11 层运行实例创建数 = 0；调用链最终状态 = 失败；失败原因能够识别为调用深度超限。
```

详细测试由测试团队后续展开，包括等价类、组合条件、完整边界矩阵、测试数据、环境组合和自动化实现。不要把这些内容塞回总体设计书。

## 6. 保持可追踪，但不要让编号妨碍阅读

复杂方案可以使用 SR-01、D1、C1、AC-01 等编号。编号只用于快速定位，不代替自然中文标题，也不能为了追踪在全文堆满编号。

读者应能从“系统规格”“关键质量要求”“安全问题”或其他既有要求找到对应验收。系统规格是行为要求的唯一真源；不要同时维护系统规格、行为规格和验收规格三套同义文本。简单方案使用稳定标题即可，不用为了追踪而增加编号。

## 7. 什么时候可以生成草稿

以下条件满足后才能生成：

- 用户已经确认全部决定；
- 用户操作和成功结果清楚；
- 产品对象、入口、主要操作、用户可见状态和支持边界已经写成产品方案；
- 系统核心规则、权限和数据规则、状态结果、失败行为和总体硬限制已经按需写成系统规格；
- 系统边界和影响范围已经通过访谈确认；
- 谁负责什么、主要流程和关键协作约束已经说清；
- 主要流程、核心状态、跨边界数据和多模块责任关系已经按需配上对应视图；
- 会改变总体设计的质量要求已经写成可验证结果；
- 关键失败有处理办法；
- 安全问题已经判断；
- 需要验收的核心成功路径、关键边界、核心异常、安全边界、兼容回归和架构级质量要求已经按适用性形成主场景；
- 每个验收主场景都有覆盖要求、前置条件、操作和明确通过条件，且没有虚构数值；
- 没有阻塞整体方案的未知项。

草稿必须经过独立架构和安全评审，不能直接作为正式报告。

## 8. 正式报告只留下一阶段需要的信息

必须保留：删除后会让开发误解范围、责任、协作约束、质量、安全、失败处理或验收的内容。

产品方案、系统规格和能解释主要流程、状态、数据流或模块责任的必要图属于必须保留的信息。产品方案和系统规格不能被图完全替代；关键决定、责任和协作约束必须保留权威文字结论。同一问题已有一张图回答清楚时，不重复生成第二张。

正式报告默认保留 1–2 张表，最多 3 张。表格只用于短文本的横向比较、映射或状态汇总。质量、安全、失败、验收、责任和风险优先使用分块段落；单元格超过两行或包含多个动作、条件时，必须改成分块。验收写“怎样证明关键要求成立”，不重新解释整段系统设计。

应该删除：

- 访谈和调研过程；
- 给作者解惑的名词解释；
- 与最终决定无关的行业资料；
- 无关系统、模块和行业清单；
- 图中普通步骤和节点的逐项复述；
- Skill 自身规则；
- 评审报告全文；
- 空话、重复总结和没有负责人或处理办法的建议。

正式报告应让开发快速找到：最终结论、产品怎么使用、系统必须遵守什么、系统负责什么、影响哪些对象、谁负责什么、流程怎么走、质量要求是什么、安全问题怎么解决、失败后怎么办、如何上线以及如何验收。

## 9. 方法来源

- [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html)：用于检查产品质量要求是否遗漏；
- [SEI Quality Attribute Scenarios](https://www.sei.cmu.edu/documents/5462/2013_018_101_60977.pdf)：用于把质量要求写成可验证场景。

这些来源是 Skill 的内部方法依据。正式报告只有在标准直接约束当前方案时才引用。
