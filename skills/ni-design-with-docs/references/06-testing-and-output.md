# 测试、验收与正式输出

## 1. 从架构决策反推测试

测试章节不是“功能测试、性能测试、安全测试”的分类清单。每个主要测试场景至少能追溯到以下之一：

- 核心用户场景；
- 关键架构决策；
- 跨模块接口契约；
- 全局约束；
- 已知风险和兼容要求。

优先覆盖：

- 主成功路径；
- 关键边界条件；
- 关键异常和失败恢复；
- 权限和越权；
- 幂等、重复请求或重入；
- 兼容与版本；
- 会改变结构的性能和容量目标；
- 已有能力不被本次改动破坏的回归场景。

## 2. 验收格式

使用容易执行的中文结构：

```markdown
### 场景：{名称}
- 前置：{环境和必要条件}
- 操作：{用户或系统行为}
- 预期：{可观察、可判断的结果}
- 对应设计：{能力、接口、决策或约束}
```

不要写“性能良好”“正确执行”“满足高可用”之类无法判断的结果。确实缺少量化目标时，明确标记待确认，并判断是否阻塞当前架构。

## 3. 正式文档生成时机

只有在以下条件都满足后才生成待评审草稿：

- 概念、范围、现状和关键决策已收敛；
- 主要架构视图和接口已经闭合；
- 关键未知项不会阻塞顶层设计；
- 所有引用能够追溯到真实来源。

草稿生成后立即进入独立评审，不先把草稿冒充正式版本交付。

## 4. 信息密度规则

没有固定页数或字数上限。

必须保留：删除后会导致研发产生不同理解、遗漏关键约束、错误判断实施范围、改变公共契约或无法验收的内容。

应该删除或合并：

- 重复背景；
- 图中已经清楚表达且正文逐项复述的内容；
- 与本次决策无关的行业常识；
- 空泛原则和口号；
- 没有进入本次范围的实现细节；
- 多处重复出现的同一结论。

最终文档应该让研发可以快速定位：为什么做、这次做什么、哪些已有、总体怎么设计、关键约束是什么、如何验收。
