# 简单、清楚的中文方案

## 1. 用普通开发的语言写

读者第一次阅读就应该知道：

- 最终要做到什么；
- 系统负责什么，影响哪些对象；
- 谁负责什么；
- 主流程怎么走；
- 失败后怎么办；
- 安全上有什么问题，怎么解决；
- 怎么判断开发完成。

如果读者必须先理解作者创造的新词，才能看懂方案，就继续简化。

## 2. 多用动作，少用抽象名词

目标要写具体需求带来的用户或系统结果。不要写“帮助研发理解”“统一团队认知”“建设某某能力”或“为后续开发提供基础”，这些是文档用途，不是产品目标。

优先写：

- “运行创建服务解析调用链”；
- “校验失败后不创建任务”；
- “调度器继续接收展开后的任务”。

少写：

- “构建调用链解析能力”；
- “形成统一校验机制”；
- “实现调度侧能力承载”。

常见替换：

| 抽象说法 | 直接说法 |
|---|---|
| 责任边界 | 谁负责什么 |
| 关键语义 | 传什么、返回什么 |
| 失败语义 | 失败时返回什么，能否重试 |
| 质量属性 | 发生什么、系统必须怎样响应、怎样判断通过 |
| 可观测性 | 如何发现和定位问题 |
| 可逆性 | 能否回退，怎么回退 |
| 适用性 | 是否与本次改动有关 |
| 残余风险 | 还有什么问题没有解决 |

必要的正式产品名、协议名、接口名和代码标识符可以保留原文。首次出现不常见缩写时，用一句中文解释。

## 3. 句子要短

- 一个句子只说一个主要判断；
- 一个句子出现两个以上逗号时，优先拆开；
- 因果、条件和例外不要挤在同一句；
- 每段只讲一个主题；
- 表格单元格使用短语或短句，不放整段文字；
- 能用主语加动作写清楚，就不用被动句。

不要把正文切成没有主语的碎片。短句仍要说明“谁做什么”。

## 4. 摘要只保留结论

第一章使用一个段落、2–3 个短句：

1. “最终要做到什么”；
2. “哪个现有部分在什么时候做哪些关键动作，检查失败后怎么办”；
3. “系统主要影响哪些部分，哪些关系保持不变”。

不要以“本方案旨在、通过建设、围绕目标、形成能力”等句式开头。不要在摘要里写背景、调研、方案比较、口号和新术语。熟悉背景的开发只读摘要，就应知道方案结论。

## 5. 标题直接回答读者问题

优先使用：

- 目标和范围；
- 产品规格；
- 用户怎么使用；
- 系统边界与影响范围；
- 总体设计；
- 系统必须达到的质量要求；
- 安全问题和解决办法；
- 出错怎么办；
- 如何上线和回退；
- 如何验收。

少用“全局约束、关键语义、质量属性、演进与可逆性”等标题。

## 6. 不创造新名词

沿用用户和现有系统的名称。同一事物全文只用一个称呼。

新增名称前检查：

1. 它是否对应真实新增的产品概念、系统责任或对外接口；
2. 现有名称是否已经够用；
3. 能否用一句具体中文解释；
4. 删除这个名称后是否更容易理解。

没有独立责任时，不创造“中心、引擎、平台、底座、桥接层、编排层”等名字。

## 7. 删除空话

以下词没有具体对象和动作时直接删除：

- 赋能；
- 抓手；
- 全面提升；
- 打造体系；
- 能力底座；
- 形成闭环；
- 端到端能力；
- 灵活可扩展；
- 高内聚低耦合；
- 业界领先；
- 统一承载；
- 无缝衔接。

例如不要写：

> 新增统一编排底座，赋能工作流生态形成端到端闭环。

改成：

> 运行创建服务解析每一层工作流。校验通过后，再把任务交给调度器。

## 8. 交付前冷读

脱离设计过程检查：

- 摘要是否用 2–3 个短句说清最终方案；
- 产品规格是否能独立说明产品规则，并没有被用户流程或架构图替代；
- 系统边界与影响范围是否来自已确认访谈，而不是设计者猜测；
- 普通开发能否一次读懂主流程；
- 是否出现没有解释的新词；
- 是否大量使用“边界、语义、能力、机制、体系”等抽象词；
- 是否有一句话塞入多个判断；
- 表格是否有不用也不影响开发的列；
- 安全章节是否直接写出“问题—后果—办法—验证”；
- 质量要求是否写成“发生什么—系统响应—如何验证”；
- 是否有一整节删掉后不影响开发；
- 是否把调研、术语教程或 Skill 规则放进报告；
- 图是否只出现陌生模块名，没有说明业务动作。
- 主要流程是否使用合适的 UML 图，核心状态、数据流和模块责任关系是否各有对应表达；

发现问题时，先删内容、改标题和拆句，再做文字润色。
