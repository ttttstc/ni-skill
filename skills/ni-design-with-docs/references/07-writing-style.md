# 简单、清楚的中文方案

## 1. 用普通开发的语言写

读者第一次阅读就应该知道：

- 最终要做到什么；
- 系统负责什么，影响哪些对象；
- 谁负责什么；
- 主流程怎么走；
- 失败后怎么办；
- 安全上有什么问题，怎么解决；
- 怎么判断开发完成。

如果读者必须先理解作者创造的新词，才能看懂方案，就继续简化。

## 2. 用金字塔原理组织内容

每章、每节都先写一句结论，再补 2–4 组支持信息。结论要直接回答标题提出的问题，不要先铺背景、过程和术语。

正式报告按从大到小展开：

```text
方案摘要 → 目标和范围（按需含当前/目标差异） → 总体设计结论 → 产品方案 → 系统边界与责任 → 流程、数据和状态 → 系统规格 → 决定与约束 → 质量、安全和异常 → 上线与验收 → 风险和来源
```

同一层的内容放在一起。用户怎么完成任务放产品方案；各部分怎样协作放主要流程；系统必须遵守什么放系统规格。不要在三个章节重复同一件事。

## 3. 多用动作，少用抽象名词

目标要写具体需求带来的用户或系统结果。不要写“帮助研发理解”“统一团队认知”“建设某某能力”或“为后续开发提供基础”，这些是文档用途，不是产品目标。

优先写：

- “运行创建服务解析调用链”；
- “校验失败后不创建任务”；
- “调度器继续接收展开后的任务”。

少写：

- “构建调用链解析能力”；
- “形成统一校验机制”；
- “实现调度侧能力承载”。

常见替换：

| 抽象说法 | 直接说法 |
|---|---|
| 责任边界 | 谁负责什么 |
| 关键语义 | 传什么、返回什么 |
| 失败语义 | 失败时返回什么，能否重试 |
| 质量属性 | 发生什么、系统必须怎样响应、怎样判断通过 |
| 可观测性 | 如何发现和定位问题 |
| 可逆性 | 能否回退，怎么回退 |
| 适用性 | 是否与本次改动有关 |
| 残余风险 | 还有什么问题没有解决 |

必要的正式产品名、协议名、接口名和代码标识符可以保留原文。首次出现不常见缩写时，用一句中文解释。

## 4. 句子要短

- 一个句子只说一个主要判断；
- 一个句子出现两个以上逗号时，优先拆开；
- 因果、条件和例外不要挤在同一句；
- 每段只讲一个主题；
- 表格单元格使用短语或短句，不放整段文字；
- 能用主语加动作写清楚，就不用被动句。 

不要把正文切成没有主语的碎片。短句仍要说明“谁做什么”。

## 5. 分块段落优先

正式报告默认保留 1–2 张表，最多 3 张。表格只适合短文本的横向比较、映射或状态汇总。

质量、安全、失败和验收内容优先使用分块段落。标签直接回答问题，不使用“适配策略”等抽象说法：

```markdown
### {一句话标题}

- **发生什么**：{触发条件和可能后果}
- **系统怎么处理**：{系统怎样响应，用户或调用方看到什么}
- **怎样判断通过**：{怎么观察和判断}
```

产品规则、协作约束和风险也可以使用分块，但标签要准确，例如“产品规则”“违反后”“下一步”。如果一个表格单元格需要超过两行，或同时包含多个动作、条件和例外，就改成分块。不要为了减少表格而把需要横向比较的短信息拆散成重复段落。

### 5.1 规格与验收只写一套事实

- 系统规格是系统行为和约束的唯一真源，不同时维护“系统规格 + 行为规格 + 验收规格”三套同义文本；
- Current/Target 差异只说明“从什么变成什么”和设计影响，不提前复述完整方案；
- 验收写要证明什么、怎样判定 PASS/FAIL，不重新解释整段系统规格；
- 简单方案不为了追踪堆满 SR/AC 编号，稳定的自然中文标题已经足够；
- Given / When / Then 只在比自然语言更清楚时使用，不把整篇报告写成 `.feature` 文件，也不描述内部模块调用。

## 6. 摘要只保留结论

第一章使用一个段落、2–3 个短句：

1. “最终要做到什么”；
2. “哪个现有部分在什么时候做哪些关键动作，检查失败后怎么办”；
3. “系统主要影响哪些部分，哪些关系保持不变”。

不要以“本方案旨在、通过建设、围绕目标、形成能力”等句式开头。不要在摘要里写背景、调研、方案比较、口号和新术语。熟悉背景的开发只读摘要，就应知道方案结论。

### 6.1 正式报告内容边界

正式报告可以写背景，但背景只保留当前事实、直接影响和本次变化。已经在系统边界与责任中说明的定义不在背景重复。

正式报告禁止以下内容：

- 作者推导、被否决方案、思维链和“我们选择”的过程；
- “已确认”“经过讨论”“根据前文”等访谈或对齐状态；
- “本章只说明”“下文作为唯一真源”“不是完整测试用例”等报告策略；
- “帮助研发理解”“方便读者定位”“研发无法判断”等面向读者的价值说明。

“研发”只有在承担实际责任时才出现。不要把它当作报告读者、受益者或结果判断主体。每个句子只表达一个主要判断，条件、动作和结果分开写。

## 7. 标题直接回答读者问题

正式报告只保留六个一级标题：

- 方案摘要；
- 目标和范围；
- 总体设计；
- 质量、安全和异常处理；
- 上线与验收；
- 风险与参考来源。

“总体设计”内部按总体设计结论、产品方案、系统边界/影响范围/责任、主要流程/数据/状态、系统规格、关键决定/协作约束排列。标题应让读者不用猜就知道这一节回答什么。

少用“全局约束、关键语义、质量属性、演进与可逆性”等标题。

## 8. 不创造新名词

沿用用户和现有系统的名称。同一事物全文只用一个称呼。

新增名称前检查：

1. 它是否对应真实新增的产品概念、系统责任或对外接口；
2. 现有名称是否已经够用；
3. 能否用一句具体中文解释；
4. 删除这个名称后是否更容易理解。

没有独立责任时，不创造“中心、引擎、平台、底座、桥接层、编排层”等名字。

## 9. 删除空话

以下词没有具体对象和动作时直接删除：

- 赋能；
- 抓手；
- 全面提升；
- 打造体系；
- 能力底座；
- 形成闭环；
- 端到端能力；
- 灵活可扩展；
- 高内聚低耦合；
- 业界领先；
- 统一承载；
- 无缝衔接。

例如不要写：

> 新增统一编排底座，赋能工作流生态形成端到端闭环。

改成：

> 运行创建服务解析每一层工作流。校验通过后，再把任务交给调度器。

## 10. 交付前冷读

脱离设计过程检查：

- 摘要是否用 2–3 个短句说清最终方案；
- 是否只有六个一级章节，并按结论到细节的顺序展开；
- 每章、每节第一句话是否直接给出结论；
- 增量需求是否只在有意义时说明当前/目标差异，全新能力是否没有空差异小节；
- 产品方案是否完整说明用户、问题、入口、操作、状态、反馈和支持边界；
- 系统规格是否作为唯一行为真源独立说明系统规则，并没有重复用户操作或被流程图替代；
- 系统边界与影响范围是否来自已确认访谈，而不是设计者猜测；
- 普通开发能否一次读懂主流程；
- 是否出现没有解释的新词；
- 是否大量使用“边界、语义、能力、机制、体系”等抽象词；
- 是否有一句话塞入多个判断；
- 正式报告是否默认不超过 3 张表，表格是否只保留短信息；
- 长内容是否已经改成“发生什么—系统怎么处理—怎样判断通过”等具体分块；
- 安全章节是否直接写出“问题—后果—办法—验证”；
- 质量要求是否写成“发生什么—系统响应—如何验证”；
- 同一个问题是否只在一个章节完整说明，是否没有独立行为规格层，验收是否只验证而不重述方案；
- 每个验收主场景是否包含覆盖要求、前置条件、操作和明确通过条件，且没有模糊 PASS 或来源不明的数值；
- SR/AC 编号和 Given / When / Then 是否只在确有助益时出现，没有增加阅读噪声；
- 关键决定、责任和协作约束是否有明确文字结论，没有只放在图里；
- 是否有一整节删掉后不影响开发；
- 是否把调研、术语教程或 Skill 规则放进报告；
- 图是否只出现陌生模块名，没有说明业务动作；
- 主要流程是否使用合适的 UML 图，核心状态、数据流和模块责任关系是否各有对应表达；

发现问题时，先删内容、改标题和拆句，再做文字润色。
