# 工作流、状态与门禁

## 1. 两类产物

整个过程维护两类内容，不能混用。

### 工作底稿

只服务于分析和评审，可以包含：

- 用户原始输入和访谈记录；
- 已确认事实、外部证据、假设、未知项和冲突项；
- 临时术语解释；
- 调研材料、备选方向和被否决原因；
- 安全分析；
- 架构和安全评审输出。

### 正式报告

只服务于产品、架构、研发和后续 Agent 执行。它只保留已对齐的范围、系统边界与影响范围、最终决策、协作约束、质量、安全、风险和验收。

正式报告固定为六个一级章节。第三章“总体设计”按总体设计结论、产品方案、系统边界和责任、系统规格、主要流程/数据/状态、关键决定和协作约束展开；后续章节合并质量/安全/异常、上线/验收、风险/来源。每章、每节先说结论，再补细节。

不要把“做过很多分析”误当成正式报告需要展示的内容。

## 2. 状态定义

| 状态 | 可以做 | 不可以做 | 退出条件 |
|---|---|---|---|
| P0 任务与证据准备 | 整理输入、定向取证、识别未知项 | 给出方案结构或技术结论 | 知道要解决谁的什么问题 |
| P1 研究输入与访谈 | 提供证据、提出分支问题、收敛答案 | 开始自主设计 | 决策树前沿为空，所有相关分支已有选择 |
| P2 待用户确认 | 输出对齐摘要、等待修改或确认 | 自行判断“默认通过” | 用户明确确认 |
| P3 最小充分设计 | 推导产品与总体架构方案 | 扩大范围、填充模板、下钻实现 | 核心场景、系统边界、责任、质量、安全和验收闭合 |
| P4 正式草稿 | 按交付价值裁剪文档 | 把草稿冒充正式版 | 草稿可进入独立评审 |
| P5 独立评审 | 独立上下文找主要问题 | 主设计者自评或逐项挑错 | 两项 PASS；失败先确认修复范围再复审 |

任一阶段发现会改变总体方案的决定性事实缺失，应回到 P1；只有用户或内部资料能给出答案时标记 `BLOCKED`。

独立评审是风险审视，不是逐项挑错。只有会导致目标、边界、责任、安全、总体结构、重大返工或验收失败的问题才进入评审结论。评审为 `FAIL` 或 `BLOCKED` 时，先列出主要问题和最小修复，暂停等待用户确认修复哪些；不得由主代理直接改稿或把低收益边缘适配列成阻断项。

## 3. 确认语义

- “本轮全部按推荐”：接受当前一轮问题的推荐项，继续访谈或进入对齐摘要。
- “后续全部按推荐”：授权主代理为剩余分支逐项选择有证据的推荐项，形成完整决策清单后进入对齐摘要。
- “确认”“按这个设计”：用户已经看到对齐摘要时，允许开始设计。
- “继续”：只有紧接完整对齐摘要时才视为确认；其他情况下只继续当前阶段。
- “跳过访谈，直接设计”：按“后续全部按推荐”处理；不能绕过决策清单和最终确认。

不能从用户沉默、简短补充资料或“看着办”推断已经完成对齐。含义不清且会改变方案时，只追问这一处。

## 4. 每轮沟通格式

工作中的对话保持短而可核对：

```markdown
当前状态：P1 研究输入与访谈

已确认：……
本轮调研输入：……
需要你决定：……
```

用户回答后只更新发生变化的内容：

```markdown
新增确认：……
仍需决定：……
发现冲突：……
下一步：……
```

状态信息用于协作，不复制进正式方案。

## 5. 停止条件

以下情况不得继续生成正式方案：

- 用户目标、成功结果或范围存在未解决冲突；
- 不同兼容目标会改变长期协作规则，但用户尚未选择；
- 系统负责什么、影响哪些用户或外部系统仍不明确；
- 身份、权限、数据或合规边界缺失，导致安全方案无法成立；
- 会改变总体方案的质量要求缺失；
- 架构或安全评审为 `BLOCKED`；
- 任一独立评审为 `FAIL` 且尚未修订复审。

评审结论为 `FAIL` 或 `BLOCKED` 时，向用户展示：问题、主要影响、最小修复、不修复后果和推荐选择。用户确认前不改稿；确认后只修已选择的项目，并重新评审受影响的门禁。用户不接受阻断修复时，停止发布，不把问题改写成低风险。

缺少不会影响总体方案的实现细节不阻塞。把它放入研发交接项即可。
