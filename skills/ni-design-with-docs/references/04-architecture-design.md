# 产品与 L0/L1 架构设计

## 1. 从目标到架构

按以下链路推导：

```text
用户问题
→ 用户场景
→ 产品能力
→ 平台能力
→ 一级架构模块
→ 运行链路与主要接口
→ 验收
```

不要从微服务、数据库、缓存、消息队列或技术框架倒推需求。

## 2. 架构驱动因素

只保留真正影响结构的业务、功能、质量和约束因素。质量要求必须尽量可观察，例如兼容程度、延迟范围、失败处理、恢复目标、权限边界；没有依据的数字标记待确认。

## 3. 架构重要事项

以下事项通常应在基线阶段决定或至少确定边界：

- 产品能力和非目标；
- 系统责任边界；
- 一级模块职责；
- 核心领域对象关系；
- 跨系统主要契约；
- 数据与信任边界；
- 兼容与版本策略；
- 权限模型和失败语义；
- 会改变总体结构的容量、性能和可靠性要求；
- 跨团队长期所有权。

以下事项通常留给详细设计：

- 内部类与方法；
- 数据库表和索引；
- 内部 DTO；
- 缓存键和线程池；
- 不改变公共契约的重试实现；
- 具体框架和库版本。

如果某个实现细节已经成为外部长期契约、安全约束或不可逆迁移，则提升为架构事项。

## 4. 关键决策格式

每个真正重要的决策写清：

- 要解决的问题；
- 采用的方向；
- 主要依据；
- 接受的代价；
- 不采用的结构性方向及原因（如存在）；
- 什么变化会触发复审。

不要输出“各有优劣，视情况而定”。证据不足时明确待决定。

## 5. L0

L0 回答：这项能力在整个平台里是什么，与谁交互，边界在哪里。

通常包含：用户或外部参与者、目标产品/平台能力、外部系统、主要责任和关键依赖。除非部署形态本身是核心决策，L0 不展示数据库、缓存、消息队列等实现组件。

## 6. L1

L1 回答：这项能力由哪些一级模块共同承担。

每个一级模块只要求说明：

- 责任；
- 关键输入；
- 关键输出；
- 依赖或协作对象；
- 本次状态：已有复用、已有调整、本次新增。

模块之间的责任必须能覆盖核心用户场景，且不存在同一关键职责由多个模块同时兜底的模糊设计。

## 7. 产品形态

产品架构基线必须说明用户如何接触和使用能力，包括适用的：

- 入口；
- 配置或操作方式；
- 核心流程；
- 用户可见状态与反馈；
- 错误或限制如何暴露；
- 与现有产品行为的兼容关系。

不要把产品形态简化成前端页面，也不要把技术接口当成用户交互。
