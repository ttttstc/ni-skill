# 第一性原理与最小充分设计

## 1. 先写推导链，不先画架构

在工作底稿中先回答：

1. 用户真正要得到什么结果；
2. 哪些事实和约束不能改变；
3. 系统负责什么，责任在哪里结束；
4. 最少需要哪些产品行为、系统责任和协作关系；
5. 这些变化如何被验证。

然后再选择结构。不得从微服务、数据库、缓存、消息队列、框架或“标准分层”倒推需求。

对已有能力上的增量需求，在工作底稿中补一条差异推导链：

```text
当前能力 / 当前行为 → 目标差异 → 产品方案 → 系统规格 → 架构实现 → 验收主场景
```

只有差异会影响研发理解或总体设计时才进入正式报告。当前行为必须来自用户确认或可靠资料；全新能力或没有有意义现状时，不生成空差异小节。

## 2. 最小充分方案

优先顺序：

1. 使用访谈已经确认可以复用的能力；
2. 调整已经确认的责任或协作关系；
3. 只有当前责任无法承载时才新增责任；
4. 只有新增责任需要独立生命周期、所有权或伸缩边界时才考虑新增模块。

选择方案时同时检查：

- 是否完整覆盖核心用户路径；
- 是否引入了目标之外的新能力；
- 是否增加了新的长期协作约束；
- 是否能用更少的模块、状态或配置完成同一结果；
- 删除某个元素后是否仍能满足目标和约束。

如果删除后不影响用户结果、分工、安全或验收，就删除。

## 3. 不制造新名词

沿用用户资料和现有系统中的名称。新增名称必须对应真实新增的产品概念、责任边界或外部契约，并能用一句话说明必要性。

警惕没有独立责任却被命名为“中心、引擎、平台、底座、编排层、桥接层”的抽象。不要用新名称掩盖原有模块的一次职责调整。

正式报告首次出现必要新概念时，直接写清它负责什么；不要另建百科式术语章节。

## 4. 先闭合产品方案，再设计系统

先闭合用户方案：

- 目标直接描述具体需求和用户或系统结果，不把写文档、帮助研发、统一认知或建设能力当目标；

- 谁在什么入口触发；
- 用户做出什么选择；
- 系统显示什么状态；
- 成功、等待、部分成功和失败如何反馈；
- 用户如何重试、取消、回退或继续；
- 处理超时或用户不能取消时，页面显示什么，系统如何结束；
- 用户从入口到结果会经历什么。

涉及多角色、多状态或分支时，优先用一张用户流程图表示交互；简单单路径可以用短步骤。产品方案回答用户怎样完成任务，不要把同一条路径拆成重复的“产品场景”。

### 系统规格约束系统必须做到什么

产品方案闭合后，再写系统规格：

- 系统必须遵守哪些核心规则；
- 权限和数据必须遵守什么规则；
- 什么状态或结果才算成功、等待、失败、超时或取消；
- 哪些失败必须停止、拒绝、重试、降级或等待处理；
- 哪些层数、大小、容量或兼容限制会改变总体方案。

系统规格是产品要求对系统的约束，不是接口契约。它不重复用户操作，不写字段、表、类方法或内部实现。

系统规格也是系统行为和约束的唯一权威来源。不要在它与验收之间增加独立 Story、行为规格或 Gherkin 层，也不要把相同规则在多个章节完整改写。简单规则使用自然语言；复杂条件组合只有在 Given / When / Then 更短、更准确时才按需使用。

正式报告先用“总体设计结论”告诉读者最终方案，再按产品方案、系统边界和责任、系统规格、主要流程的顺序展开。系统规格先于流程：读者先知道系统必须做到什么，再理解各部分怎样协作实现。

产品能力必须能追踪到系统责任和验收：

```text
产品方案 → 系统边界与责任 → 系统规格 → 主要流程与协作约束 → 验收主场景
```

架构设计中的每项关键责任、决定和协作约束，应能追踪到产品要求、系统规格、质量要求或安全要求。每个影响主要产品结果、硬限制、关键异常、安全边界或架构级质量的要求，应在验收主场景中有验证入口。简单方案可用稳定标题追踪，不强制编号。

## 5. 系统边界与影响范围

访谈结束后，由设计者根据已确认输入归纳：

- 系统负责交付的结果；
- 系统明确不承担的相邻责任；
- 直接参与的用户、角色、团队和外部系统；
- 每个对象是新增责任、调整协作、保持不变还是外部约束。

不要要求用户自己提供架构结构，也不要用代码扫描补全内部现状。只写理解用户路径、系统协作、安全、质量和验收必需的对象。

## 6. 关键架构决策

一个事项只有满足以下至少一项时，才进入正式决策：

- 改变用户结果或系统边界；
- 形成跨团队或对外长期协作约束；
- 影响数据、身份、权限或信任边界；
- 影响兼容、版本、迁移或回滚；
- 影响关键质量目标或故障处理；
- 以后修改会造成大范围返工。

建议使用短分块，避免把理由塞进表格：

```markdown
### 决定 1：{一句话结论}
- 结论：{决定采用什么}
- 理由：{为什么这项选择最直接地满足目标和约束}
```

只有存在两个以上结构性可行方向时才比较方案。一个方向已经由硬约束唯一确定时，直接说明选择和依据。正文中的决定是权威结论；即使结构图或流程图已经体现，也不能省略会影响开发的决定。

决策数量由问题决定。不要把一般原则、现状事实或实现建议包装成架构决策。

## 7. 研发可接手的深度

方案需要明确到研发可以继续详细设计和任务拆分：

- 用户行为和状态；
- 产品方案、系统规格和用户可见结果；
- 系统边界与影响范围；
- 系统责任及所有权；
- 跨边界关键协作约束；
- 关键运行和失败语义；
- 安全控制与残余风险；
- 质量目标和可观察验收；
- 迁移、兼容和回滚边界。

具体实现只有在它已经成为长期协作约束、安全要求、无法回退的迁移或整体限制时才进入方案。其余作为后续详细设计问题列出，而不是写成项目“非目标”。

## 8. 业界标准怎么使用

业界标准只用于设计和评审时检查遗漏，不直接变成报告目录：

- 用 [ISO/IEC/IEEE 42010](https://www.iso.org/standard/74393.html) 检查不同参与者关心的问题是否有合适表达；
- 用 [arc42](https://docs.arc42.org/home/) 的上下文、总体策略、运行场景、关键决策、质量和风险检查总体方案是否闭合；
- 用 [C4 系统上下文](https://c4model.com/diagrams/system-context)的思路检查人与外部系统是否说清，但不强制生成 L0、L1 或固定层级图；
- 用 ISO/IEC 25010 和 SEI 质量场景检查质量要求，具体见 `references/06-testing-and-output.md`；
- 用 OWASP 威胁建模检查安全问题、控制和验证，具体见 `references/08-security-review.md`。

这些方法服务于当前问题。没有实际内容时，不机械补章节、图或术语。
