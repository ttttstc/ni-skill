# 系统边界输入与定向调研

## 1. V1 的系统边界来自访谈

V1 不扫描代码、仓库、配置或内部接口来逆向现状。主代理在访谈结束后，根据用户已经确认的信息归纳：

- 系统负责交付什么结果，以及责任在哪里结束；
- 哪些用户、角色、团队或外部系统与本需求直接相关；
- 哪些对象新增责任、调整协作、保持不变或形成外部约束；
- 哪些数据、权限、秘密或高价值操作跨越边界；
- 哪些边界仍未知，并会不会阻塞总体设计。

用户不需要自己画架构图。设计者负责把访谈结果整理成简短文字、影响表或必要的边界图。不能从产品名称、常见做法或公开资料推断用户内部模块和责任。

## 2. 工作底稿怎么记录

工作底稿可以使用：

| 对象 | 与需求的关系 | 预期责任或影响 | 依据 | 状态 |
|---|---|---|---|---|
| ... | ... | ... | 用户资料 / 访谈确认 / 外部事实 | 已确认 / 待确认 |

只记录理解总体方案必需的对象。没有参与本次用户路径、系统协作、安全或验收的模块不进入清单。

规则：

- 用户确认的内部事实可以作为设计输入；与资料冲突时必须指出；
- 文档只支撑它明确记载的结论，不能从名称推断完整能力；
- 无法确认的边界标记“待确认”，不能自动创造模块或责任；
- 正式报告只保留已确认、且会影响总体设计的边界与影响范围。

## 3. 定向公开调研

先列出会改变决策的具体问题，再取证。问题可以包括：

- 标准或协议规定了什么边界；
- 相关产品或平台公开承诺什么行为；
- 官方规范有哪些限制或兼容要求；
- 某设计是否引入已知安全、版本或演进风险。

有多个互不依赖的问题时，可以并行委派取证；只有一个问题时直接处理。不要为了满足数量启动宽泛调研任务。

来源优先级：官方标准与规范、官方产品文档、官方设计或参考实现、可信技术资料。社区经验只能补充，不能单独支撑关键架构结论。

## 4. 调研输入与正式引用

访谈前把相关证据压缩为：

```markdown
- 事实：……
  来源：……
  对本轮选择的影响：……
```

这是给用户做决定的输入，不是报告章节。

正式报告只在关键事实或决策附近保留真正支撑结论的一手来源。以下内容留在工作底稿：

- 搜索过程和资料清单；
- 未采用的行业做法；
- 为理解问题整理的教程和术语；
- 与最终范围、决策、协作约束或验收无关的事实；
- 调研子代理的原始输出。

引用必须说明它支撑哪个事实或限制。行业标准用于检查设计是否遗漏，不自动变成用户的内部事实或业务要求。
