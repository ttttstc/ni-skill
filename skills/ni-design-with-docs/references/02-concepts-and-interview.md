# 调研输入、概念解释与访谈

## 1. 访谈的目的

访谈不是收集尽可能多的信息，而是让用户决定会改变以下结果的分支：

- 用户行为和产品边界；
- 系统边界与影响范围；
- 系统责任和长期协作约束；
- 安全、数据、兼容与质量要求；
- 可观察的验收结果。

答案不会改变这些结果的问题，不在产品架构访谈中询问。

## 2. 先准备调研输入

提问前，先找出足以帮助用户判断的最小证据。来源可以是：

- 用户提供的产品、架构和接口资料；
- 用户已经确认的产品、平台和组织事实；
- 官方标准、协议和产品文档；
- 与当前分支直接相关的参考实现或公开限制。

每条调研输入只写三件事：事实、来源、对当前选择的影响。不先给完整方案，也不堆砌资料。

## 3. 概念只在决策点解释

当一个概念会影响用户选择时，在问题附近用一句话解释：

```text
这里的“调用深度”指从入口工作流开始计算的连续调用层数，不等同于仓库依赖层数。
```

只有同名概念存在真实语义冲突时，才补充边界或对比。不要先输出 3–7 个名词的教程，也不要默认在正式报告中设置术语章节。

正式报告只有在研发可能因概念歧义做出不同实现时，才保留一句定义；能通过统一用词解决的，不增加名词解释。

## 4. 问题格式

每轮通常 3–5 题，同一轮的问题应互不依赖。推荐使用：

```markdown
1. **{用户需要决定的事情}**
   - 推荐：A。{基于调研输入和当前目标的理由}
   - 选项：A / B / C
   - 影响：{不同选择会改变的产品、架构、安全或验收结果}
```

要求：

- 选项互斥，表达具体结果，不用模糊程度词；
- 推荐项放在最前，允许用户快速回复“本轮全部按推荐”；
- 没有充分依据时明确说明“不预设推荐”；
- 不用推荐项替用户决定内部事实、商业承诺或合规责任；
- 不把多个相互依赖的决定塞进一个长问题；
- 问题和影响使用自然中文，不堆缩写。

## 5. 访谈顺序

先建立决策树。一个决定依赖另一个决定时，把它放在下游。每一轮只提出前置条件已经关闭的“当前前沿”，不要猜测上游答案。

按依赖关系推进，不固定轮数：

1. 真实目标、核心用户和成功结果；
2. 用户路径、产品行为和范围；
3. 系统负责什么、影响哪些人和系统、哪些关系不能改变；
4. 身份、权限、数据、秘密和信任边界；
5. 会改变结构的质量目标与演进要求；
6. 可观察的验收结果。

如果用户在最初输入中已经覆盖某一层，直接采用已确认答案。简单问题可以一轮结束，但仍要进入对齐摘要并等待确认。会影响方案的分支必须全部访问，不能留下静默假设。

公开文档中能够查明的标准、协议和产品限制由主代理调查，不把公开事实调查推给用户。V1 不通过代码或仓库扫描补全系统边界；内部责任、组织关系和既有约束来自用户资料与访谈。

## 6. 对齐摘要

最终对齐摘要不是访谈纪要。它使用确定句和状态标签：

```markdown
## 对齐摘要

- 目标：……
- 用户路径：……
- 本次范围：……
- 业务非目标：……
- 系统边界：……
- 影响范围：……
- 已确认约束：……
- 安全与数据边界：……
- 验收结果：……
- 非阻塞待定：……
- 阻塞项：无 / ……
```

摘要中不得出现用户没有确认的事实。推荐项只有在用户接受后才能写成已确认决定。

## 7. 推荐项快速路径

用户可以用两种方式减少交互：

- “本轮全部按推荐”：接受当前前沿的全部推荐项，然后重新计算下一轮前沿；
- “后续全部按推荐”：授权主代理遍历余下分支，为每项选择有依据的推荐项。

第二种方式仍必须生成完整的推荐决策清单。清单至少包含决策、选择、依据和影响，并进入最终对齐摘要。用户确认摘要前不得设计。

推荐阶段可以确定“需要有谁负责什么”或“双方必须共同遵守什么规则”，但在访谈事实足以支持新增边界前，不给责任创造模块名、分层名或技术实现名。

没有充分证据形成推荐，或者问题涉及只有用户掌握的目标、组织权限、商业承诺或合规责任时，快速路径暂停并提问。不得用默认假设伪造一个选择。
