# 图、运行流程、数据和协作约束

## 1. 先写图要回答的问题

每张图生成前先写一句：

> 这张图用于说明……

如果一句话说不出图要解决的理解问题，就不要画。图必须降低理解成本，不能只是把陌生名词连起来。

## 2. 按问题选择表达

| 需要解释的问题 | 优先表达 |
|---|---|
| 用户如何操作，系统如何反馈 | 用户流程图、活动图、时序图 |
| 一个对象有哪些状态和转换 | 状态图 |
| 多个角色在关键场景中如何协作 | 时序图、泳道活动图 |
| 数据跨越哪些信任边界 | 数据流图 |
| 系统负责什么、影响哪些对象 | 系统边界与影响范围图、影响表 |
| 多个系统如何承担关键责任 | 责任图、协作图 |
| 部署位置影响安全、可靠性或运维 | 部署图 |

用户交互涉及多角色、多状态、异步等待或异常分支时，优先画用户流程、时序或状态图。不要用 L1 架构图替代用户交互。

L0、L1、C4 和 4+1 都是可选工具。只有它们能降低当前问题的理解成本时才使用，不要求固定层级或数量。

## 2.1 核心内容的图形组合

正式报告只要包含下列内容，就按对应问题补图。图可以在多个章节引用，但不要重复绘制同一问题。

| 报告内容 | 首选图 | 需要回答的问题 | 例外 |
|---|---|---|---|
| 主要流程 | UML 时序图或 UML 活动图 | 谁在什么时候完成什么，失败后停在哪里 | 只有一个责任方且没有分支时，可用短步骤，并说明不画图的理由 |
| 核心状态 | UML 状态图 | 对象有哪些状态，什么条件会让它进入下一个状态 | 没有状态变化时，直接说明不需要状态图 |
| 跨模块或跨系统的数据 | 数据流图 | 数据从哪里来，经过谁，写到哪里，在哪一步检查 | 没有跨边界数据时，不画数据流图 |
| 两个以上系统或模块的责任关系 | 模块架构关系图 | 哪些对象协作，每个对象承担什么，本次改变了哪条关系 | 只有一个责任对象时，不画，并说明原因 |

“模块架构关系图”是当前方案的简化协作图，不是强制的 L0、L1 或全系统分层图。只画已经确认的系统或模块，不为了凑图新增“中心、引擎、平台”等名称。

当核心数据同时有状态变化且跨越边界时，UML 状态图和数据流图都要有。模块关系图只说明责任和协作，不代替主要流程图或数据流图。

### 2.2 图的最低表达要求

- UML 时序图或活动图必须有参与者、关键动作和成功或失败分支；
- UML 状态图必须有状态、触发条件和状态结果；
- 数据流图必须有数据名称、来源、流经对象、去向和关键检查点；
- 模块架构关系图必须有模块名称、主要关系和责任变化；
- 不要用类图、接口图或调用栈图代替上述四类问题；
- 图中不写接口字段、数据库表、类方法或实现步骤。

## 3. 图的可读性

- 使用用户资料和现有系统中的名称；
- 节点和连线标签以中文为主；
- 一张图只承载一个主要问题；
- 只展示解释该问题必需的参与者和关系；
- 用“新增责任、调整协作、保持不变、外部约束”标识真正相关的影响；
- 图下或对应正文写清关键判断，不逐个节点复述；
- Mermaid 过密时拆图，不缩写成只有作者能懂的字母。

必须检查图、正文、协作约束、状态和验收没有冲突。图用于降低理解成本，正文中的关键决定、责任和协作约束是权威结论。不能因为图中已经画出，就省略会影响开发的文字规则。

## 4. 主要运行流程

对每个影响总体设计的场景，说明：

- 触发者和前置条件；
- 主要步骤及责任方；
- 关键状态或数据变化；
- 成功结果；
- 失败发生在哪里；
- 谁能感知，谁负责处理；
- 是否可以重试、补偿、取消或回滚。

存在并发、重复、乱序或异步结果合并时，按适用性明确：

- 多次操作是同一业务动作还是彼此独立；
- 是否可能重复生成业务结果；
- 顺序是否影响用户结果或数据正确性；
- 超时、取消或部分失败后如何停止、恢复或继续。

只写决定系统协作方式的场景。普通页面操作或内部调用细节不展开。

主要流程涉及两个以上角色、系统或模块时，正式报告必须附 UML 时序图或 UML 活动图。图下只补充读者需要知道的关键判断，不逐项复述普通动作。影响开发的责任、决定和约束仍要在对应正文中明确写出。

## 5. 数据怎么流动

按适用性说明：

- 哪些业务信息跨越模块或系统边界；
- 数据的权威来源和所有者；
- 何时读取、写入、同步或派生；
- 一致性、顺序、幂等和保留要求；
- 敏感级别、地域或租户边界；
- 失败后如何发现不一致并恢复。

不需要为了完整描述所有数据实体。只有影响跨边界语义、迁移、安全或验收的数据进入方案。

正式报告中的数据流图只画本次相关的数据。箭头标业务信息，不画字段名；在图或图下标出权威来源、所有者、敏感信息和检查点。数据流图表达“数据怎么走”，不表达调用时序。

核心状态发生变化时，正式报告附 UML 状态图，并在正文说明状态变化如何影响用户结果、任务处理或恢复。

## 5.1 模块架构关系

模块架构关系图只用于回答“谁与谁协作”。它至少标出：

- 已确认的系统或模块名称；
- 每个对象在本次需求中的主要责任；
- 关键数据或结果的流向；
- 新增责任、调整协作、保持不变和外部约束。

不要把模块架构关系图画成全系统目录。若图中的对象超过读者一次能理解的范围，按业务问题拆图，而不是缩小文字或引入编号。

## 6. 关键协作约束

只定义独立团队、系统或模块必须长期共同遵守的规则。正式报告优先使用短分块：

### 约束 1：{一句话说明必须共同遵守的规则}

- **规则**：{必须做什么或禁止做什么}
- **涉及对象**：{系统、模块或团队}
- **生效阶段**：{在流程的哪个阶段执行}
- **违反后**：{系统停止、拒绝、等待、降级或进入什么状态}

协作约束正文是权威结论。结构图和流程图不能替代它。不要复述普通责任和流程步骤；只有不同团队独立决定后可能产生冲突、长期不兼容或错误结果时，才提升为协作约束。

可以检查：

- 身份和授权；
- 数据所有权和状态变化；
- 重复、顺序和并发处理；
- 超时、失败、重试和补偿；
- 限额与资源边界；
- 审计和问题定位所需信号。

兼容、版本和废弃要求放到“如何上线和回退”，不要塞进协作约束表。

不要生成接口路径、字段、错误码和内部数据结构。

## 7. Given / When / Then 只用于可观察的复杂场景

Given / When / Then 是可选表达工具，不是独立行为规格层。仅在多个前置条件共同决定结果、权限或状态组合容易歧义、外部兼容行为需要精确定义时使用。简单系统规则和普通验收优先用自然语言。

它只描述调用方或用户能够构造和观察的条件、动作与结果：

```gherkin
Given 调用方只有只读权限
And 被调用工作流声明写权限
When 系统创建被调用工作流运行
Then 实际权限不得超过调用方拥有的只读权限
```

不要用它描述内部模块调用，例如“Resolver 调用 GraphBuilder”。内部责任、协作顺序和状态变化继续使用架构正文、UML 时序图、活动图或状态图；Given / When / Then 不能替代这些图。

## 8. 质量要求要写成可判断结果

不要只写“高性能、高可靠、安全、可扩展”。改写为场景：

```markdown
- 场景：下游在调用期间不可用。
- 期望：入口在明确超时后返回可识别失败；不会把未知状态报告为成功；恢复后可以安全重试。
- 验证：故障注入和重复请求测试。
```

不同数值会改变总体结构时，应回到访谈；否则把数值留给详细设计或容量测试。正式报告不能用没有依据的数字制造确定感。
