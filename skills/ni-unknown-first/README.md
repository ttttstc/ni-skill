# ni-unknown-first

> Vibe Coding 的 Unknown 分诊器。  
> 它不替你 brainstorm、不替你 grill、不替你 review，也不直接替你实现。  
> 它负责判断：**当前最阻塞下一步行动的 Unknown 是什么，以及下一步应该进入什么处理模式。**

---

## 1. 一句话解释

`ni-unknown-first` 是一个用于 AI 编程、产品规划、架构设计、设计打磨、写作工作流的 **Unknown 阶段诊断器 / 分诊器 / 提示词交接器**。

它的核心动作是：

```text
诊断当前 Unknown → 推荐处理模式 → 生成下一阶段任务包 → 支持本对话承接
```

它不是要消灭所有 Unknown。真实工程里的 Unknown 永远存在。它只判断：

> 当前是否存在会阻塞下一步行动、导致方向错误、明显返工或验收失败的 Unknown。

---

## 2. 为什么需要它

很多 AI 协作失败，不是因为 AI 不会执行，而是因为 AI 在关键未知还没显性化时过早行动。

常见情况：

- 只有一个模糊想法，却让 AI 直接实现；
- 提出一个功能，但真实痛点没有验证；
- 知道方向，但不知道第一版验证什么；
- 说“做得高级一点”，但没有质量标尺；
- 有方案，但关键决策没有锁定；
- 要改现有代码库，但还没看清系统地形；
- 代码已经生成，但不知道怎么验收；
- 实现过程中出现新事实，原计划和成功标准发生偏移。

`ni-unknown-first` 的作用是让 AI 在行动前先停一下，回答：

```text
现在最该先处理的 Unknown 是什么？
下一步应该让 AI 扮演什么角色？
这一步处理到什么程度就可以前进？
```

---

## 3. 核心概念

### 3.1 Unknown 不是普通问题

Unknown 指的是：如果不先处理，AI 很可能会错误行动的信息缺口。

例如：

- “按钮叫什么名字？”通常不是关键 Unknown；
- “第一版到底验证什么？”通常是关键 Unknown；
- “是否需要多租户权限隔离？”在企业系统里可能是关键 Unknown；
- “什么样叫高级？”在设计或写作任务里可能是关键 Unknown。

---

### 3.2 阻塞型 Unknown

一个 Unknown 只有满足以下任一条件，才算当前阶段的阻塞型 Unknown：

1. 会改变产品方向；
2. 会改变第一阶段目标；
3. 会改变架构边界；
4. 会改变数据模型；
5. 会改变用户主流程；
6. 会影响权限、安全、隐私或不可逆操作；
7. 会改变验收标准；
8. 如果现在不解决，后续会产生明显返工；
9. 如果现在不解决，AI 很可能按错误方向执行。

其他 Unknown 不是不存在，而是可以作为“保留 Unknown”进入后续观察、实现记录、测试或验收。

---

### 3.3 多重 Unknown

真实任务通常同时存在多个 Unknown。

`ni-unknown-first` 采用这个原则：

> **诊断可以多标签，行动必须单线程。**

也就是说：

- 可以同时识别主 Unknown 和次级 Unknown；
- 当前轮只处理一个最阻塞的主 Unknown；
- 不把产品访谈、方案脑暴、架构质询、代码扫描、验收设计混进同一个提示词。

---

### 3.4 可行动状态，不是无 Unknown 状态

`ni-unknown-first` 不会说“没有 Unknown”。因为真实任务里 Unknown 永远存在。

它只会判断：

```text
当前没有阻塞下一步行动的主 Unknown。
```

这意味着：

- 不是所有问题都解决了；
- 而是剩余 Unknown 可以通过假设、实现记录、原型、测试、验收或后续迭代处理；
- 用户可以带着剩余不确定性前进。



### 3.5 用户起点诊断

同一个 Unknown，用户起点不同，下一步 AI 的工作方式也不同。

`ni-unknown-first` 会轻量判断三件事：

| 类型 | 含义 | 用途 |
|---|---|---|
| 已显性说明 | 用户已经明确说出的目标、约束、事实、标准 | 内部记住，避免重复追问；跨会话版才压缩为最小背景 |
| 可能隐性知道 | 用户能判断但尚未表达的品味、偏好、经验、背景 | 引导下游用样例、反例、对比或原型显化 |
| 当前判断盲区 | 用户目前可能无法判断的领域、质量、代码库或验收问题 | 引导下游建立判断框架、做调研、扫代码或设计验收 |

它不会把用户起点当成用户画像，也不会评价用户能力。它只用于决定下一阶段 AI 应该怎么问、怎么展开、怎么交接。默认情况下，用户起点不作为独立章节输出，避免任务包过长或产生误解。

示例：

```text
用户：这个页面不够高级，但我说不上来。

内部判断：
- 用户已经明确“当前质量不满足预期”；
- 用户可能能通过对比判断“高级 / 不高级”；
- 当前缺少可执行的设计约束。

对任务包的影响：
- 不继续追问“你喜欢什么风格”；
- 让下游用样例、反例、对比或轻量原型帮助用户显化标准。
```

---

### 3.6 真正的行家视角

下一阶段任务包里的 AI 角色，不应该只按关键词机械选择。

`ni-unknown-first` 会判断：

1. 当前任务处在什么层级；
2. 这个产出服务什么决策；
3. 哪种行家最能帮助关闭当前主 Unknown。

例如：

| 用户请求 | 关键词角色 | 更可能的真正行家 |
|---|---|---|
| 做一个 AI 周报工具 | 软件工程师 | 项目管理专家 + 风险治理顾问 |
| 写一篇公众号文章 | 写手 | 编辑总监 + 选题策划 |
| 页面不够高级 | UI 设计师 | 品牌设计评审 + 信息架构师 |
| 方案怕有坑 | 执行工程师 | 严厉方案评审 + Pre-mortem 主持人 |
| 改现有系统 | 代码实现者 | 代码库导航员 + 架构守门人 |

这个行家视角只是高质量假设，不是最终真理。后续如果用户判断、真实约束或实现发现推翻它，下一次 `/ni-unknown-first` 应重新修正。

## 4. 它和其他能力的关系

`ni-unknown-first` 不是替代品，而是分诊器。

| 专门能力 | 它擅长什么 | ni-unknown-first 的作用 |
|---|---|---|
| brainstorming | 方案探索、MVP 拆解 | 判断是否该进入方案脑暴 |
| office-hours | 产品访谈、真实痛点挖掘 | 判断是否存在伪需求风险 |
| grill-me / grilling | 严厉质询方案 | 判断是否该进入计划风险质询 |
| codebase scan | 代码库地形探索 | 判断是否需要先探索代码库 |
| review / QA | 验收、测试、风险检查 | 判断是否进入验收未知处理 |
| research / prototype | 调研、样例、原型 | 判断是否需要下游模式使用这些方法关闭 Unknown |

一句话：

> `ni-unknown-first` 负责分诊，不负责治疗。  
> 它可以建议去哪个科室，但不限制医生怎么治。

## 5. 十类 Unknown

| Stage | 中文名 | 用户状态 | 主风险 | 推荐处理模式 |
|---|---|---|---|---|
| 0 | 想法空白 | 只有模糊产品冲动 | AI 任意补全需求 | 想法访谈 / 盲点扫描 |
| 1 | 伪需求风险 | 有功能请求但 pain 未验证 | 做对功能、做错问题 | 产品访谈 / Framing Challenge |
| 2 | 行动未知 | 方向成立但第一步不清楚 | MVP 过大或切错 | 方案脑暴 / MVP 裁剪 |
| 3 | 质量未知 | 知道要做什么但不知道什么叫好 | 功能可用但质量不对 | 质量标准建立 / 样例对比 |
| 4 | 表达未知 | 看得出不对但说不清 | 反馈循环空转 | 隐性标准显化 / 偏好翻译 |
| 5 | 决策未知 | 方案存在但关键决策未锁 | 架构/流程返工 | 关键决策访谈 |
| 6 | 计划风险 | 方案看似完整但未经质询 | 隐含假设爆雷 | 方案质询 / Pre-mortem |
| 7 | 代码库未知 | 要改现有系统但不清楚地形 | 局部修改破坏整体 | 代码库扫描 / 安全变更路径 |
| 8 | 实现偏移 | 实现中现实偏离计划 | 静默扩大范围 | 偏差复盘 / 标准修订 |
| 9 | 验收未知 | 产物已出但不知道是否达标 | 误合入/误发布 | 验收评审 / QA / 理解测试 |

这些阶段不是严格线性流程。一个任务可能从“伪需求风险”跳到“代码库未知”，也可能在实现后回到“决策未知”。

## 6. 使用方式

### 6.1 安装

```bash
mkdir -p ~/.claude/skills
cp -R ni-unknown-first ~/.claude/skills/
```

或解压 zip 后复制：

```bash
unzip ni-unknown-first-skill.zip
cp -R ni-unknown-first ~/.claude/skills/
```

### 6.2 基础调用

```text
/ni-unknown-first
我想做一个把资料自动变成文章的写作工作流。
```

### 6.3 只诊断，不展开

```text
/ni-unknown-first
请只诊断当前 Unknown，并生成下一阶段任务包。不要展开完整访谈。

我的想法是：我想做一个 AI 项目风险助手。
```

### 6.4 阶段完成后重新诊断

```text
/ni-unknown-first
上一阶段已经确认：真实 pain 是风险信息分散，PM 发现太晚。第一版不做完整周报，只做风险线索提取和人工确认。请重新判断当前最阻塞的 Unknown。
```

## 7. 本对话承接：省去复制提示词

`ni-unknown-first` 默认会输出下一阶段任务包。这个任务包有两个出口：

### 出口 A：本对话承接

如果你想在当前对话继续，不需要手动复制提示词。

直接回复：

```text
继续
```

或者：

```text
按这个继续
```

AI 应该承接上一轮推荐处理模式，继续处理当前主 Unknown。

### 出口 B：复制到其他上下文

如果你要切换到其他 AI、新会话、专门 skill 或代码 agent，再复制“下一阶段任务包”。

---

## 8. 重要语义：继续 ≠ 进入下一个 Unknown

这是 `ni-unknown-first` 最容易误用的地方。

当一次诊断输出：

```text
主 Unknown：表达未知
推荐处理模式：隐性标准显化
```

你回复：

```text
继续
```

正确行为是：

```text
进入「隐性标准显化」模式，继续处理“表达未知”。
```

错误行为是：

```text
把主 Unknown 推进成下一个 Unknown。
```

规则如下：

```text
“继续” = 承接上一轮推荐处理模式，用来处理当前主 Unknown。
“再次运行 /ni-unknown-first” = 重新诊断，并判断是否推进 Unknown 队列。
```

只有当下游模式处理完当前主 Unknown，并满足关闭条件后，再次运行 `/ni-unknown-first`，才会判断是否将后续 Unknown 提升为新的主 Unknown。

---

## 9. 下游模式不受诊断器限制

`ni-unknown-first` 自身不执行下游任务，但它可以把任务交接给下游处理模式。

一旦你回复“继续”或复制任务包进入下一阶段，后续行为由下游模式决定。

如果下一阶段需要：

- 调研；
- 原型；
- 样例；
- 反例；
- 代码库探索；
- 方案推演；
- 严厉质询；
- 验收设计；
- 测试规划；

那就应该使用这些方法。

`ni-unknown-first` 不应该机械禁止下游调研、原型、代码扫描或完整分析。它只要求下游模式说明：

1. 当前要关闭哪个 Unknown；
2. 为什么需要使用这种方法；
3. 阶段停止条件是什么；
4. 产出如何回流到下一次诊断。

## 11. 状态管理

默认情况下，`ni-unknown-first` **不创建任何状态文件**。

它优先使用：

1. 当前用户输入；
2. 当前对话上下文；
3. 用户提供的文档、spec、notes；
4. 可访问的代码库信息；
5. 上一次输出中的 Unknown 队列或待承接模式。

如果你希望跨会话保留状态，可以明确要求：

```text
/ni-unknown-first
保存当前 unknown 状态，供下次继续使用。
```

推荐保存到用户全局目录，而不是工程目录：

```text
~/.claude/ni-unknown-first/projects/{project-id}/state.md
```

只有当你明确要求团队共享或项目内沉淀时，才写入项目目录：

```text
.ai/ni-unknown-first/state.md
```

写入项目目录前，必须先确认，避免污染工程。

## 12. 能力边界

`ni-unknown-first` 能做：

- 识别当前 Unknown 类型；
- 判断主 Unknown 和次级 Unknown；
- 判断哪些 Unknown 阻塞下一步；
- 内部诊断用户起点：已显性说明、可能隐性知道、当前判断盲区；默认不暴露为任务包章节；
- 判断真正的行家视角：任务层级、推荐行家、选择理由；
- 生成下一阶段中文任务包；
- 支持本对话承接；
- 给出关闭条件；
- 判断当前是否可进入下一步；
- 列出保留 Unknown；
- 在上下文变化后重新诊断。

`ni-unknown-first` 不做：

- 不直接写代码；
- 不替代 brainstorming；
- 不替代 office-hours；
- 不替代 grill-me；
- 不替代 review / QA；
- 不默认创建项目文件；
- 不假装能看到当前上下文之外的信息；
- 不追求消灭所有 Unknown；
- 不把多个阶段任务混进同一个任务包；
- 不限制下游模式使用调研、原型、代码探索、测试或评审等方法。

## 13. 设计原则

1. **先诊断，再行动**：先判断当前面对什么 Unknown，再决定下一步。
2. **多重诊断，单步行动**：可以识别多个 Unknown，但一次只处理主 Unknown。
3. **证据化判断**：诊断必须说明触发证据、缺失证据和关闭证据。
4. **最小干预**：默认不展开完整访谈，优先输出下一阶段任务包。
5. **可关闭**：每个主 Unknown 都必须有关闭条件。
6. **用户起点驱动但默认隐藏**：根据用户已明确、隐性知道和无法判断的部分调整下一阶段任务包，但不默认输出为独立章节。
7. **真正行家驱动**：AI 角色按任务层级和决策场景选择，不按关键词机械选择。
8. **可交接**：下一阶段任务包必须包含角色、角色选择依据、当前主 Unknown、目标、可用方法、输出格式和停止条件；本对话承接版不默认暴露大段上下文和用户起点。
9. **可承接**：本对话继续时，用户只需回复“继续”。
10. **不误推进**：“继续”只承接推荐处理模式，不推进到下一个 Unknown。
11. **下游自由**：进入下游模式后，该调研就调研，该原型就原型，该扫描代码就扫描代码。
12. **不污染工程**：默认不写文件，项目内状态必须显式 opt-in。
