# 真正的行家视角

## 为什么需要

同一个任务，在不同层级上需要的“行家”不同。不要只根据关键词机械选择 AI 角色。

例如：

- “做一个项目周报工具”不一定首先需要软件架构师，可能需要项目管理专家、组织协同顾问或风险治理专家。
- “写一篇文章”不一定首先需要写手，可能需要编辑、选题策划、读者洞察者或事实核查者。
- “优化一个页面”不一定首先需要 UI 设计师，可能需要信息架构师、转化率专家或品牌设计顾问。

真正的行家由两个问题决定：

1. 当前任务处在什么层级？
2. 这个产出服务什么决策？

## 任务层级

可以按以下层级判断：

| 层级 | 含义 | 常见真正行家 |
|---|---|---|
| 意图层 | 用户只表达了模糊目标 | 产品访谈官、问题定义顾问、编辑策划 |
| 决策层 | 产出服务于是否做、做什么、先做什么 | 产品经理、战略顾问、架构负责人、技术负责人 |
| 方案层 | 已确认方向，需要比较方案 | 方案架构师、MVP 设计师、流程设计师 |
| 执行层 | 已确认方案，需要安全落地 | 工程实现者、代码库导航员、测试工程师 |
| 质量层 | 需要判断什么叫好 | 设计评审、编辑总监、QA、领域专家 |
| 验收层 | 需要判断是否达标 | 验收官、审计者、用户代表、技术评审 |

## 选择规则

选择下一阶段任务包中的 AI 角色时，应遵守：

1. 不按关键词选角色；按任务层级和决策用途选角色。
2. 如果当前 Unknown 会影响产品方向，优先选择产品 / 用户 / 业务行家。
3. 如果当前 Unknown 会影响架构、数据、权限、安全，优先选择架构 / 安全 / 工程行家。
4. 如果当前 Unknown 是质量或表达问题，优先选择能建立判断标准的行家，而不是直接执行者。
5. 如果当前 Unknown 是验收问题，优先选择审计、QA、用户代表或技术评审角色。
6. 行家视角是高质量假设，不是最终真理；后续可随用户判断和事实变化修正。

## 输出要求

默认诊断中不需要长篇解释，但应该输出：

```markdown
## 真正的行家视角

- 任务层级：{意图层 / 决策层 / 方案层 / 执行层 / 质量层 / 验收层}
- 推荐行家：{角色}
- 选择理由：{为什么这个角色比关键词角色更合适}
```

在下一阶段任务包中，AI 角色应体现该行家视角。
