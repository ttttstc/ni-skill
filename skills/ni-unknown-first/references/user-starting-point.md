# 用户起点诊断

## 为什么需要

同一个 Unknown，用户起点不同，下一阶段任务包也不同。

例如同样是“行动未知”：

- 用户是领域专家但不会写代码：下一阶段可以直接拆 MVP 和实现切口。
- 用户不懂领域也不懂技术：下一阶段应先建立判断框架和样例。
- 用户已有原型但说不清问题：下一阶段应优先做对比、反例和偏好归纳。

用户起点诊断不是用户画像，也不是长篇访谈。它只是判断：用户当前已经知道什么、隐性知道什么、误以为什么、还无法判断什么。

## 关键原则：内部使用，默认不暴露

用户起点主要用于**内部诊断和任务包生成**，不应该默认作为独立章节暴露给用户。

原因：

1. 本对话承接时，上下文本来就在当前对话里，重复输出会产生噪音。
2. 用户起点容易越写越长，导致任务包变重。
3. “可能隐性知道 / 当前判断盲区”如果直接暴露，容易让用户误解为能力评价。
4. 它真正的价值是影响下游工作方式，而不是成为一段可阅读报告。

只有用户明确要求“详细诊断”“解释为什么这么判断”“跨会话完整提示词”时，才可以简短展示用户起点。

## 四类起点信息

| 类型 | 含义 | 内部处理方式 |
|---|---|---|
| 已显性说明 | 用户已经明确说出的目标、约束、事实、标准 | 不重复追问；必要时压缩为最小背景 |
| 可能隐性知道 | 用户能判断但没有表达的品味、偏好、经验、背景 | 在下游任务包中要求用样例、对比、选项显化 |
| 可能误解 / 假设 | 用户把症状当问题、把手段当目标、把实现当需求 | 在下游任务包中要求挑战 framing |
| 当前无法判断 | 用户缺少领域知识、质量标准、代码库地形或验收能力 | 在下游任务包中要求先建立判断框架、调研、代码扫描或验收设计 |

## 诊断规则

1. 只基于当前上下文判断用户起点，不要臆测用户背景。
2. 如果信息不足，把它写成“可能”，不要写成事实。
3. 不要用用户起点标签评价用户能力；它只用于决定下一阶段 AI 如何工作。
4. 当用户已经给出足够明确的信息时，不要重复追问。
5. 当用户隐性标准难以语言化时，优先通过样例、反例、原型、对比帮助显化。
6. 默认不在输出中展示用户起点；只让它影响任务包规则。

## 何时可以展示

仅在以下情况展示用户起点：

- 用户要求详细诊断；
- 主 Unknown 判断存在争议，需要解释依据；
- 用户要求生成跨会话完整提示词；
- 用户显式问“你为什么这么判断”。

展示时应保持简短：

```markdown
## 用户起点依据（简版）

- 已明确：...
- 隐性标准：...
- 当前盲区：...
```

## 对下一阶段任务包的影响

用户起点必须影响任务包的工作方式，但不必暴露为章节：

- 如果用户已经是领域专家，任务包应少讲常识，多聚焦决策和取舍。
- 如果用户缺少领域判断，任务包应先建立判断框架和参考标准。
- 如果用户有隐性偏好但说不清，任务包应使用样例、反例、对比或原型。
- 如果用户已经明确答案，只是需要执行，任务包应避免过度诊断。
