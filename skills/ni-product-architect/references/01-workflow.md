# 工作流与阶段门禁

## 总原则

产品架构基线不是边写边想的长文。先收敛事实和决策，再生成正式文档。

整个过程维护四类状态：

- 已确认事实：有用户确认或可靠来源支撑；
- 假设：当前用于推演但尚未证实；
- 未知项：当前缺少答案；
- 待决定：必须由用户或证据关闭的架构问题。

假设不能伪装成约束，未知项不能通过“最佳实践”自动补齐。

## 阶段退出条件

| 阶段 | 退出条件 |
|---|---|
| S0 任务理解 | 能用一句话准确说明用户、问题和目标 |
| S1 概念对齐 | 不存在会影响方案的核心概念歧义 |
| S2 目标与范围 | 目标、非目标、主要用户、范围和关键约束足以支撑设计 |
| S3 现状分析 | 能区分已有复用、已有调整、本次新增和非本次范围 |
| S4 调研 | 影响关键决策的外部事实已有足够证据，关键冲突已显式标记 |
| S5 决策 | 不存在阻塞 L0/L1 的待决定事项 |
| S6 架构 | 产品能力、L0/L1、一级职责和关键运行关系闭合 |
| S7 契约与验收 | 主要接口、全局约束、测试场景和验收标准可追踪 |
| S9 评审 | 所有硬门禁通过 |

缺少非关键细节不阻塞；记录到“详细设计边界”即可。

## 访谈节奏

不要一次抛出完整调查问卷。每轮只选择当前决策前沿的 3–5 个问题，复杂情况最多 7 个。

用户回答后先给出简短收敛：

```text
已确认：……
仍未知：……
待决定：……
发现冲突：……
```

如果没有新的阻塞问题，自动进入下一阶段，不为了“多问几轮”继续提问。

## 阻塞处理

以下情况停止生成正式基线：

- 目标或边界存在互相冲突且用户未选择；
- 核心兼容目标不明确且不同答案会改变架构；
- 现状事实不足以判断是否复用或改造关键能力；
- 关键安全、合规、数据约束缺失且无法从公开来源确认；
- 独立评审发现必须由用户补充的决定性事实。

此时输出 `BLOCKED` 的原因，并批量提出最少必要问题。
