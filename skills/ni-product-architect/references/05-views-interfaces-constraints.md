# 架构视图、主要接口与全局约束

## 1. 按问题选择视图

图不是装饰，也不限于 UML。每张图必须回答一个明确问题。

常用选择：

| 要回答的问题 | 优先视图 |
|---|---|
| 用户、系统和外部依赖是什么 | 系统上下文图、用例图、C4 上下文视图 |
| 一级能力和模块怎么分 | 能力图、L0/L1 架构图、组件图、C4 容器视图 |
| 核心业务如何运行 | 时序图、活动图、进程视图 |
| 核心对象如何变化 | 状态机图 |
| 数据如何跨边界流动 | 数据流图 |
| 部署边界为何重要 | 部署图、物理视图 |
| 多角度理解复杂系统 | 4+1 中与当前问题有关的视图 |

不机械补齐 4+1，也不为了“专业”固定画若干 UML 图。

Markdown 中优先使用可渲染的 Mermaid。若某种视图没有标准 Mermaid 语法，可使用 flowchart 清楚表达并在标题中说明视图目的。

## 2. 图文一致性

必须检查：

- 图中的一级模块在正文中有职责定义；
- 正文中的关键模块不会在总体图中无故消失；
- 关键接口与运行关系能够在对应视图中解释；
- 状态图与正文生命周期一致；
- 图中的“已有复用、已有调整、本次新增”与能力差距表一致。

一张图如果不能减少理解成本，就删除。

## 3. 主要接口规格

只定义会影响跨模块协作和后续返工的契约。建议表格字段：

| 项 | 内容 |
|---|---|
| 接口/交互 | 名称或用途 |
| 提供方 | 谁负责 |
| 使用方 | 谁调用 |
| 触发时机 | 什么时候发生 |
| 关键输入 | 只列影响语义的输入 |
| 关键输出 | 只列影响语义的输出 |
| 交互方式 | 同步、异步、事件、文件等 |
| 权限 | 身份与授权边界 |
| 幂等 | 是否要求以及按什么业务键判断 |
| 失败语义 | 主要错误分类、可否重试、谁感知 |
| 兼容 | 版本或向后兼容要求 |
| 约束 | 其他长期契约 |

不要在基线阶段生成完整 OpenAPI、每个字段、内部 DTO 或内部方法签名。

## 4. 全局约束

按适用性检查，不强制每项都写一章：

- 权限、安全和信任边界；
- 数据所有权、敏感级别和跨域流转；
- 兼容、版本和废弃策略；
- 性能、容量和限额；
- 可靠性、幂等、重试和故障隔离；
- 可观测性和审计；
- 灰度、迁移和回滚；
- 多租户、地域或合规限制；
- 团队和平台责任边界。

只写会影响总体设计的要求。细节实现留给详细设计。
