# 选模块决策算法

> 本文是 ni-formatter 选模块的决策依据。核心原则一句话：**够用就停，不堆**。模块是给重点用的，不是给装饰用的。

---

## 决策算法

```
1. 判断文章类型（6 种原型之一，方法见下）
2. 必选：verdict —— 来自核心论点。没有核心论点不输出（硬规则）
3. 按文章类型加模块（见映射表）
4. 实检触发点：每个候选模块在文章里真有触发场景才放，没有就划掉（G1）
5. 总数检查 ≤ 5；超了砍掉优先级最低的
6. 输出，并用 G3 对话腔告诉用户穿了哪几件、为什么
```

第 4 步是关键。映射表给的是「这类文章通常适合哪些模块」，不是「必须放满」。文章里找不到 callout 的触发点（没有警告、没有踩坑），就别放 callout——哪怕映射表建议了。

---

## 文章类型映射表

文章原型沿用 ni-writer 的 6 种。每种给推荐模块组合。

| 文章原型 | 必选 | 推荐加 | 说明 |
|---------|------|--------|------|
| 技术方法论型 | verdict | part + steps | 有章节、有落地路径，part 切分、steps 收落地动作 |
| 架构原理深度型 | verdict | part（+ callout 按需） | 章节多，part 必加；有边界条件警告时加 callout |
| 现象解读型 | verdict | callout + quote | 一口气顺下来，不用 part；金句和反直觉判断用 callout/quote 锚 |
| 工具分享型 | verdict | callout + quote | 工具的坑用 callout，惊艳点用 quote |
| 调查实验型 | verdict | quote（+ callout 按需） | 过程叙事为主，发现的金句用 quote；踩坑用 callout |
| 产品体验型 | verdict | quote（+ callout 按需） | 真实感受的金句用 quote；注意事项用 callout |

注意：

- **part 只给技术章节**。非技术原型（现象解读 / 工具分享 / 调查实验 / 产品体验）默认不加 part——它们靠口语化转场顺下来，加 part 会把文章切碎。
- **steps 只给技术方法论型**，而且要文章里真有操作流程。架构原理深度型偏纯分析，通常没有 steps。
- **quote ≤ 2**：一个留给开头名言，一个留给文中最尖的金句。
- **callout ≤ 3**：技术警告、易踩坑、反直觉判断。

---

## 怎么判断文章类型

按优先级：

1. **看 ni-writer 自检报告**——如果 article.md 带了 ni-writer 的四层自检报告，里面通常标了文章原型，直接用。
2. **看结构特征**——有中文序数小标题（一、二、三）+ 落地路径 → 技术方法论型；纯机制分析、量化推演 → 架构原理深度型；一口气顺下来无小标题 → 非技术原型。
3. **拿不准就问用户**——别猜。一句话：「这篇我归成技术方法论型，靠 part 切章节、steps 收落地。你觉得对吗？」

---

## 总数控制

总模块数上限 5。verdict 占 1，剩 4 个名额分给 part / callout / quote / steps。

各模块自身上限：

| 模块 | 上限 |
|------|------|
| verdict | = 1（必选） |
| part | ≤ 文章 H2 数 |
| callout | ≤ 3 |
| quote | ≤ 2 |
| steps | ≤ 1 |

如果按映射表选完超过 5 个（技术方法论型 part 可能很多），优先保 verdict 和 steps，part 数量压缩——不是每个 H2 都必须加 part，只给真正需要视觉分段的大章节加。

## 典型组合示例

| 文章 | 类型 | 选中模块 | 数量 |
|------|------|---------|------|
| 「怎么评估 AI 编程工具」 | 技术方法论型 | verdict + part×2 + steps | 4 |
| 「服务网格的代价」 | 架构原理深度型 | verdict + part×3 | 4 |
| 「我注意到一个现象」 | 现象解读型 | verdict + callout + quote | 3 |
| 「这个 Prompt 救了我」 | 工具分享型 | verdict + quote + callout | 3 |

非技术文章模块普遍少（3 个左右），这是对的。模块少不是没排版，是排版克制。
