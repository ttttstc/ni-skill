# agent-legible — 代码库的 Agent 可读性审计

> 给「要被 AI coding agent 使用」的 TS/JS 代码库做体检:Agent 能不能正确理解、用对你的代码。

你的任务:审计一个 TS/JS 代码库,判断它对 AI coding agent 有多「可读」,产出一份审计报告 + 修复草稿。

## 为什么需要这个

一个 AI agent 在生成代码时,不带人的隐性经验。它对一个组件 / SDK 方法的理解,**只来自代码里字面写下来的东西**:类型声明、注释、示例、导出关系、调用频率。

所以一个组件如果只暴露成类型声明,Agent 只知道它「可以用」;只有当声明里写清使用场景、边界、反例和示例,Agent 才知道它「应该怎么用」。

终点态长这样:

```ts
/**
 * Pie or donut chart for part-of-whole breakdowns.
 *
 * Use for small slice counts, such as request share by region.
 * Do NOT use for time series or precise ranking — use LineChart
 * or BarChart instead.
 *
 * @example
 * <PieChart donut data={[{ label: "Free", value: 320 }]} />
 */
export declare function PieChart(props: PieChartProps): JSX.Element;
```

这段注释不只说 `PieChart` 存在,还说清它适合占比、不适合趋势 / 排序、那种情况改用谁。这就是「对 Agent 可读」。这个 skill 做的,就是找出你代码库里**还没到这个程度**的地方。

## 审计两件事

### 一、意图外化 —— 每个 Agent 接口面符号的可读等级

「Agent 接口面」= Agent 生成代码时会去引用 / 调用的东西:包的 public exports、组件库的组件、SDK / API 客户端方法、公共工具函数、作为契约的类型与接口。**不审**内部实现、私有函数、测试。

每个符号评 L0–L3:

| 等级 | 状态 | Agent 能知道 |
|---|---|---|
| L0 失明 | 只有类型签名,零文档 | 只知道「能调」,不知道怎么调对 |
| L1 命名可读 | 有名字 + 类型,顶多一句「是什么」 | 能猜用途,不知边界 |
| L2 用途明确 | 写清「做什么、典型场景」 | 知道何时该考虑它 |
| L3 边界完整 | L2 +「不适合什么 / 改用什么」+ ≥1 个 `@example` | 知道何时该用、何时不该用 |

L3 = PieChart 级,终点态。**风险 = 等级 × 调用频率**:高频 L0 最危险,稀有符号文档差影响小。

详细评级标准见 `references/legibility-rubric.md`。

### 二、分层 —— 代码库有没有「给 Agent 用」的结构

借 Atomic Design 的分层。检查三层是否存在且可发现:

- **原子层**:design tokens / 稳定常量 / 枚举——Agent 不该重新发明的视觉与配置原子。审计点:有没有集中的、有文档的 token 来源?还是 Agent 会硬编码颜色和魔法值?
- **能力层**:就是上面那批符号。审计结果即这层的质量。
- **任务规则层(recipes)**:针对「某类任务」的可复用生成规则——做 Code Review / QA Report / 架构说明时,信息怎么组织、证据放哪、暴露哪些操作。绝大多数代码库**完全没有这层**。审计点:有没有 `recipes/`、`AGENTS.md` / `CLAUDE.md` 里的任务剧本、或等价物?缺失就标出「最该先建 recipe 的任务类」。

## 产出:审计报告

写到被审仓库根目录的 `agent-legibility-report.md`(或用户指定路径),四个部分:

1. **总览**——扫了多少符号、L0–L3 分布、一句话概况。
2. **失明清单**——L0 / L1 符号,**按风险(等级 × 频率)排序**,表格:符号 ｜ 文件 ｜ 当前等级 ｜ 调用次数 ｜ 缺什么。
3. **分层覆盖**——三层各自「有 / 部分 / 缺」,缺的说清。
4. **修复建议**——按优先级排序的 actionable 清单。Top N 高危符号给 PieChart 式 JSDoc 草稿;缺的 recipe 给 `recipe.md` 骨架。

报告模板与审计步骤见 `references/audit-method.md`。

## 原则

- **审 Agent 视角,不审人视角。** 一段注释对人够用 ≠ 对 Agent 够用。审的是「字面写下来的,够不够一个没有隐性经验的 Agent 用对」。
- **高频优先。** 稀有符号文档差影响小,高频符号失明才是真风险。报告必须按调用频率排序,不能只列清单。
- **不改代码,只审计 + 给草稿。** 草稿(JSDoc / recipe 骨架)放报告里,落盘由人确认——因为「意图」要人来定,自动填可能填错。
- **抓不准就标存疑。** 一个符号是不是 agent-facing 有时模糊,标「存疑」让用户定,不硬归类。
- **抓不到就报错。** 不是 TS/JS、找不到接口面、仓库过大——显式说,不假装审完了。

## 硬规则

- 只支持 TS/JS。其他语言显式拒绝,不硬审。
- 只审 Agent 接口面,不审内部实现 / 私有代码 / 测试。
- 报告的失明清单**必须按调用频率 × 等级排风险**,不能只是个无序清单。
- 给出的草稿必须明确标注「未经人确认,可能误解原意图」。
- 不自动修改任何被审代码。

## 验收

- 报告含全部四个部分,失明清单确实排了序。
- 抽查 3 个被标 L0 的符号——确实没有边界文档。
- 抽查报告里给的 L3 草稿——确实达到 PieChart 级(用途 + 边界 + 反例 / 替代 + 示例)。
- 交付前自查:报告里「最危险的符号」是不是真的又高频又失明?如果排在前面的其实是冷门符号,排序错了,回炉。

## 降级

| 场景 | 降级路径 |
|---|---|
| 不是 TS/JS 项目 | 明说只支持 TS/JS,建议用户手动对照 rubric 自查。 |
| 找不到明确的接口面(无 index / 无 exports) | 让用户指定要审的目录或文件,不瞎猜。 |
| 仓库过大,符号太多 | 先审用户指定的子目录 / 单个 package,报告里标注「本次只覆盖 X」。 |
| 调用频率无法准确统计 | 用 grep 估算,报告里标注是估算值。 |

降级显式标注。
