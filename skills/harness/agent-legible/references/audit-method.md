# 审计方法与报告模板

## 审计步骤

### 1. 定位 Agent 接口面

找出「Agent 生成代码时会引用 / 调用」的符号集合:

- 包的 public exports —— 看 `package.json` 的 `main` / `exports` 字段、根 `index.ts` 的导出。
- 组件库 —— 导出的 React / Vue 组件。
- SDK / API 客户端 —— client 类的 public 方法。
- 公共工具函数、作为参数 / props 契约的类型与接口。

**排除**:内部实现、私有函数(下划线前缀 / 未导出)、测试、构建脚本、示例代码。

接口面定位不清(没有 index、没有 `exports` 字段)→ 让用户指定要审的目录或文件,不瞎猜。

### 2. 枚举符号

用 Glob / Grep 把接口面的导出符号列出来。仓库大就先锁定一个 package / 子目录,报告里标注覆盖范围。

### 3. 逐个评级

对每个符号,按 `legibility-rubric.md` 评 L0–L3。判 L3 必须四样齐全(用途 / 反向边界 / 替代 / `@example`)。

### 4. 估调用频率

grep 符号名在整个仓库(及——如果能拿到——下游用法)里的引用次数,作为频率近似。精确不了就估,报告里标「估算」。频率是**排风险**用的:风险 = 等级 × 频率。

### 5. 分层检查

- **原子层**:找有没有集中的 design tokens / 常量 / 主题定义,且有文档。没有 → Agent 会硬编码魔法值。
- **能力层**:即第 3 步的评级结果。
- **任务规则层**:找 `recipes/`、`AGENTS.md` / `CLAUDE.md` 里的任务剧本、skill 定义,或等价物。没有 → 列出这个仓库里「最该先建 recipe 的 2–3 类任务」(看它实际被用来干什么)。

### 6. 写报告

按下面模板写到 `agent-legibility-report.md`。

## 报告模板

```markdown
# Agent 可读性审计报告

> 仓库:{repo}　覆盖范围:{全部 / 子目录 X}　审计时间:{date}

## 1. 总览

- 接口面符号总数:N
- 等级分布:L0 _ ／ L1 _ ／ L2 _ ／ L3 _
- 概况:{一句话——这个库对 Agent 的可读性大致什么水平}

## 2. 失明清单(L0 / L1,按风险排序)

| 符号 | 文件 | 等级 | 调用次数 | 缺什么 |
|---|---|---|---|---|
| PieChart | charts/pie.ts | L0 | 42 | 用途 / 边界 / 反例 / 示例 全缺 |
| ... | | | | |

## 3. 分层覆盖

| 层 | 状态 | 说明 |
|---|---|---|
| 原子层(tokens) | 有 / 部分 / 缺 | ... |
| 能力层(符号) | 见上 | L0/L1 占比 X% |
| 任务规则层(recipes) | 缺 | 建议先为 {任务类} 建 recipe |

## 4. 修复建议(按优先级)

### P0 —— 高频失明符号

为下列符号补 PieChart 级 JSDoc。草稿如下
(**未经确认,可能误解原意图,落盘前请人工核对**):

\`\`\`ts
/**
 * {草稿}
 */
\`\`\`

### P1 —— 建任务规则层

建议新建 recipes/{task}.md,骨架如下:
{recipe 骨架}

### P2 —— 其余
{...}
```

## 注意

- 报告的失明清单**必须按风险(等级 × 频率)排序**。如果排在最前的是个冷门符号,排序错了。
- 草稿一律标注「未经确认」。这个 skill 给的是起点,不是定稿——意图判断权在人。
- 覆盖范围不全时(只审了子目录),在总览里显眼标注,别让读者以为审了全库。
